## 1. 本番構成

### 1.1 採用構成：案1「単一VM 全部入り」（確定）

Windows Server 単一VMに、アプリケーション・PostgreSQL・Zabbix Agent・バッチをすべて同居させる構成。**冗長化は行わない。**（出典：技術スタック 1章・2章）

```
利用者ブラウザ
   │ HTTPS / TLS1.2+
   ▼
┌──────────────────────────────────────────────┐
│ Windows Server（単一VM）                      │
│  IIS（リバースプロキシ / URL Rewrite + ARR）  │
│   └─ Next.js（Windows サービス常駐）          │
│        ├─ PostgreSQL                          │
│        └─ アップロード画像（データディスク）  │
│  Zabbix Agent                                 │
│  タスクスケジューラ（pg_dump / 削除バッチ）   │
└──────────────────────────────────────────────┘
   │ 退避                    │ 送信              │ SMTP/API
   ▼                         ▼                   ▼
オブジェクトストレージ   Zabbix Server        メール送信サービス
（バックアップ保管）     （別ホスト）          （プロバイダ ※未決）
```

**不採用が確定しているもの**

| 項目 | 判断 | 理由 |
|---|---|---|
| Vercel / サーバレス / AWS RDS | 不採用 | 2026-07-26 時点の旧案。これらを前提とした設計・実装を行わない |
| Redis | 不採用 | 単一VM構成のため。セッションは PostgreSQL に保持する |
| Docker | 不採用 | Windows コンテナの制約が利点を上回る |
| 冗長化（多重化・クラスタ） | 行わない | 案1の前提 |

### 1.2 サーバースペック

| 項目 | 推奨 | 最小 |
|---|---|---|
| CPU | 4 vCPU | 2 vCPU |
| メモリ | 16 GB | 8 GB |
| OSディスク | 100 GB SSD | 80 GB SSD |
| データディスク | 100 GB SSD（別ボリューム） | OSディスク同居も可 |

- 同時接続100人・予約登録5件/分（要求機能の性能要件）に対して余裕がある想定
- メモリ16GB推奨の根拠は Windows Server 本体 + PostgreSQL + Node.js + IIS の同居分
- **PostgreSQL のデータとアップロード画像は OS ディスクと別ボリュームに置く**（OS再構築時にデータを巻き込まないため）

### 1.3 ミドルウェア構成

| 用途 | 採用 | 運用上の要点 |
|---|---|---|
| Node.js | 22 LTS | `package.json` の `engines` でバージョン固定 |
| PostgreSQL | 17（EDB の Windows インストーラ） | `btree_gist` 拡張が必要（予約時間帯の重複防止に使う排他制約のため） |
| リバースプロキシ | IIS + URL Rewrite + ARR | Node を直接インターネットに公開しない |
| プロセス常駐 | Windows サービス（nssm または node-windows） | 障害時の再起動アクションと自動起動を設定する |
| TLS証明書 | win-acme（Let's Encrypt 自動更新） | 更新失敗の検知を監視項目に含める |
| 画像保存 | データディスク上のディレクトリ | 保存先を差し替えられる形で実装する |

**※補完** — 上記のうち「Windows サービスの実行アカウント」については、devops-infra-engineer の設計方針として *専用サービスアカウント・最小権限・管理者権限で常駐させない* ことが定められているが、アカウント設計の具体（作成主体、パスワード管理方法）は既存ドキュメントに記述がない → 残タスク C-3。

### 1.4 スケーラビリティ前提（サイジングの根拠）

| 時期 | ユーザー数 | 拠点数 |
|---|---|---|
| 初期 | 500 | 20 |
| 1年後 | 1,000 | 30 |
| 3年後 | 2,000 | 50 |

同時接続想定100人、スループット 予約登録5件/分。（出典：要求機能）

### 1.5 概算コスト（月額目安）

| 提供形態 | 目安 |
|---|---|
| 国内VPS（Windows Server プラン 8GB） | 1〜2万円 |
| Azure / AWS の Windows VM（4vCPU/16GB） | 2.5〜5万円 |
| バックアップ用オブジェクトストレージ | 数百円 |
| Zabbix Server 用の小型VM（Linux・別ホスト） | 3,000〜5,000円 |

- 契約時点で実見積もりを取得すること
- **オンプレに新規調達する場合、Windows Server ライセンスと CAL / External Connector の要否を事前に確認する**（クラウドVMは時間課金にライセンスが含まれるため、この論点は発生しない）
- **※未決** クラウド提供元（国内VPS / Azure / AWS）→ 残タスク A-4

## 2. 可用性要件

### 2.1 SLA

- **SLA 99.9%（計画メンテナンス時間を除く）**（出典：要求機能）
- **許容される非計画停止時間は月あたり約42分**
  - 計算根拠：43,200分/月 − 計画メンテナンス約1,304分/月 = 約41,896分。その 0.1% が約42分

### 2.2 計画メンテナンス枠

- **週1回、0:00〜5:00** に実施する
- コート利用時間（10:00〜22:00）外のため、利用者への影響はないものとする
- **実施はシステムメンテナンス通知として全ユーザーに事前通知する**（要求機能の通知要件）
- **※未決** 実施曜日 → 残タスク A-2（技術スタックでは火〜木の早朝を推奨）

### 2.3 メンテナンス枠で行う作業（確定している範囲）

| 作業 | 枠内実施 | 根拠 |
|---|---|---|
| Windows Update | 原則この枠内 | 技術スタック 4.1 |
| アプリケーションのデプロイ | 原則この枠内 | 技術スタック 4.1 / 4.5 |
| 復旧に時間のかかる作業（リストア、大規模マイグレーション） | 必ず枠内 | 非計画停止の許容が月約42分しかないため |

- **Windows Update が枠外に再起動を起こさない設定**（アクティブ時間 / 更新の一時停止 / WSUS）を必ず入れる、という方針は決まっている
  - **※未決** どの方式を採るか、適用の承認フローは未定 → 残タスク B-5
- 枠内に収まらない場合の**中断・切り戻し判断基準を手順に定める**方針は決まっている
  - **※未決** 判断時刻・基準値そのものは未定 → 残タスク B-4

### 2.4 単一障害点

案1は単一VM構成であり、サーバー・ディスク・電源・回線がいずれも単一障害点となる。この点は第9章「受け入れたリスク」に明記のとおり、**承知の上での選択**である。（出典：技術スタック 5章）

| 項目 | 内容 | 出典 |
|---|---|---|
| 取得方式 | `pg_dump` をタスクスケジューラから実行 | 技術スタック 4.2 |
| 取得時刻 | **毎日 03:00** | 要求機能 |
| 保持期間 | **30日** | 要求機能（DB要件・可用性要件の双方に記載） |
| 保管先 | **取得後、必ずオブジェクトストレージ等の別ロケーションへ退避する** | 技術スタック 4.2 |

| 配置制約 | 保存先を DB と同一ディスクにしない | 案1の前提（単一VM構成ではサーバー障害でバックアップごと失われるため） |

### 3.1 メンテナンス日の重複（重要・未決）

**バックアップ時刻 03:00 は、メンテナンス枠 0:00〜5:00 の内側にある。** メンテナンス実施日は両者が重なるため、作業順序を定めることが要求機能・技術スタックの双方で明示的に求められている。

- **※未決** 作業順序（バックアップ完了を待って作業を開始する等）→ 残タスク A-3

### 3.2 リストア

- **リストア手順書とリストア試験まで設計に含める。取得だけの設計は未完成とみなす**（devops-infra-engineer の設計方針）
- **※未決** リストア試験の実施頻度・合否基準・実施者 → 残タスク B-2

## 4. 監視要件

### 4.1 監視基盤

- **Zabbix による24時間体制の監視**（出典：要求機能）
- **Zabbix Server は監視対象と同居させない。** 別の小型 Linux VM か外形監視SaaSを併用する
  - 理由：同居するとサーバーごと落ちたときに検知できない（出典：技術スタック 4.3）
- 監視対象VMには Zabbix Agent for Windows を導入する

### 4.2 監視項目

| 分類 | 項目 | 閾値 | 出典 |
|---|---|---|---|
| リソース | CPU 使用率 | **80% 以上でアラート** | 要求機能 |
| リソース | メモリ使用率 | **85% 以上でアラート** | 要求機能 |
| リソース | ディスク空き容量（ログ / バックアップ / DB） | ※未決（残タスク B-6） | 技術スタック 4.3 |
| サービス | Windows サービス稼働状態（Next.js アプリ / PostgreSQL） | 停止でアラート | 技術スタック 4.3 |
| 外形監視 | ログイン | 応答 / 応答時間 | 技術スタック 4.3 |
| 外形監視 | スイムレーン表示 | **画面表示 3秒以内**（要求機能の性能要件） | 技術スタック 4.3 |
| 外形監視 | 予約API | **予約登録 5秒以内**（要求機能の性能要件） | 技術スタック 4.3 |
| アプリ | アプリケーションログのエラー率 | ※未決（残タスク B-6） | 技術スタック 4.3 |
| 証明書 | TLS証明書の有効期限 | 失効前に通知 | 技術スタック 2.3 / 4.3 |
| ジョブ | バックアップジョブの成否 | 失敗でアラート | 技術スタック 4.2 / 4.3 |

**リソース監視だけで終わらせない**ことが方針として明示されている。上表の外形監視・ジョブ監視は要件の一部である。

- **※未決** アラートの通知先・対応者の定義 → 残タスク A-5

## 5. ログ要件

### 5.1 前提：Windows に logrotate は存在しない

ローテーションは**アプリケーション側（pino / winston 等のローテーション機能）またはタスクスケジューラのスクリプトで明示的に実装する。** 「そのうち回る」前提にしない。（出典：技術スタック 4.4 / devops-infra-engineer 設計方針）

### 5.2 ログ要件一覧

| 項目 | 要件 | 出典 |
|---|---|---|
| ログレベル | **INFO 以上を記録** | 要求機能 |
| 記録対象 | 利用者のログイン状態、すべてのデータベース操作に関する状態 | 要求機能（エラーハンドリング） |
| 記録対象 | 拠点スタッフの操作は全てログに記録（誰が操作したかはログイン時刻から推測） | 要求機能 |
| ローテーション | **月曜日〜日曜日で記録し、5世代まで管理**（＝週次5世代） | 要求機能 |
| 監査ログ保持 | **180日** | 要求機能 |
| メール送信 | 配信失敗はシステムログに記録し、3回まで自動リトライ | 要求機能 |
| 出力禁止 | **個人情報・パスワード・トークンをログに出力しない**（Prisma のクエリログ設定を含む） | 技術スタック 4.4 |

- ログ出力先のディスク容量監視と、ローテーション失敗時のアラートを設ける（devops-infra-engineer 設計方針）
- **※補完** 保持期間の定義が複数ドキュメントに分散しており整合が取れていない（要求機能：ログ5世代・監査180日 ／ 保護方針：アクセスログ90日）。ディスクサイジングと削除バッチの実装に直結するため整理が必要 → 残タスク B-7

## 6. インシデント対応要件

### 6.1 対応SLA（確定）

| 重大度 | 定義 | 初期対応 | 復旧 |
|---|---|---|---|
| 重大度1 | サービス全体が利用不可 | **3日以内** | **5日以内** |
| 重大度2 | 一部機能が利用不可 | **3日以内** | **7日以内** |
| 重大度3 | 軽微な不具合 | **7日以内に対応** | — |

（出典：要求機能「運用・保守要件」）

### 6.2 サポート方針

- **ユーザーサポート対応は行わない。** メールでの問い合わせはシステム管理者に送信される（出典：要求機能）

### 6.3 未決事項

- **※未決** 障害時の連絡体制、通知先、重大度の判定者、時間外の扱い → 残タスク A-5
- **※補完** インシデント対応SLA（3日／5日）と SLA 99.9%（非計画停止 月約42分）は整合しない。復旧に3日かかれば月次可用性は大きく割り込む。両者の関係の整理が必要 → 残タスク A-1 / A-5

## 7. デプロイ / CI・CD 要件

### 7.1 デプロイ方式

- CI/CD は **GitHub Actions**
- GitHub Actions の Linux ランナーからオンプレ Windows Server へは直接デプロイできないため、**本番VMに Windows セルフホストランナーを置く方式**を案1では採用する（最も安価）
- **セルフホストランナーはプライベートリポジトリでのみ使用すること。** パブリックリポジトリでは第三者のPRから任意コードを実行される（出典：技術スタック 4.5）

### 7.2 デプロイ手順の順序（確定）

```
1. ビルド成果物の配置
2. prisma migrate deploy
3. Windows サービス再起動
```

**各段の失敗時の切り戻し手段をセットで用意する**ことが方針として決まっている。
- **※未決** 切り戻しの具体手段（成果物の世代保持、マイグレーションのロールバック方針）→ 残タスク B-3

### 7.3 Prisma 運用ルール（確定）

| ルール | 内容 |
|---|---|
| 本番マイグレーション | **`prisma migrate deploy` を使う。`migrate dev` / `migrate reset` は本番で実行しない**（DBリセットの危険があるため） |
| `db push` | **使用しない。** 予約時間帯の重複を防ぐ排他制約（`EXCLUDE USING gist`）と部分一意インデックスは Prisma スキーマで表現できず、マイグレーションSQLに手書きで追加する。`db push` はこれを失う |
| スキーマ変更 | `prisma migrate dev --create-only` でSQLを生成し、必要な手書きSQLを追記してから適用する |
| 日時カラム | `@db.Timestamptz` を明示する |
| 外部キー | `@@index` を明示する（Prisma は自動作成しない） |

- **デプロイはサービス停止を伴うため、原則メンテナンス枠（0:00〜5:00）内で実施する**（技術スタック 4.1）

### 7.4 Secrets 管理（確定方針）

| 環境 | 管理方法 |
|---|---|
| ローカル開発 | `.env.local`（Git管理外） |
| CI | GitHub Secrets |
| 本番サーバ | 環境変数ファイルを **NTFS ACL でサービスアカウントのみ読取可**に絞る |

- Secrets をコードに置かない。`.env*` が `.gitignore` されているか確認する

### 7.5 CI の構成方針

- CI は最小から積む：`lint` → 型チェック → `test` → `build`
- `prisma generate` をビルド前に実行する
- `node_modules` をキャッシュする
- **※未決** Windows ランナーでのビルド検証を持つか（本番が Windows のため、Linux ランナーのみだと改行コード・パス区切り・ファイル名の大文字小文字の差異を取りこぼす）→ 残タスク C-1

## 8. セキュリティ運用要件（インフラ領域）

| 項目 | 要件 | 出典 |

| 通信 | **すべて暗号化（TLS 1.2 以上）** | 要求機能 |

- **※未決** ファイアウォール規則、PostgreSQL 5432 の非公開、管理アクセス経路（RDP）の制限 → 残タスク C-2

## 9. 案1で受け入れたリスク（確定・蒸し返さない）

案1は単一障害点を持つ構成であり、**以下を許容した上での選択**である。（出典：技術スタック 5章）

| リスク | 内容 |
|---|---|
| **SLA** | 単一VM構成の実効可用性は **99.5% 程度**。要件の **99.9%（非計画停止 月約42分）は契約上保証できない** |
| **RPO** | 日次バックアップのみのため **最大24時間**。障害時は最大1日分の予約が失われる |
| **RTO** | 手動リストアのため **数時間**。月42分の枠には収まらない |

この前提は覆さない。**その中で復旧時間を短くする方向で設計する**。

### 9.1 将来「案2」への移行に備えた設計上の約束（確定）

案2 = アプリVM + マネージドPostgreSQL（月4〜7万円、RPO数分・バックアップ自動化）。ユーザー数増加や停止許容度の低下が起きたら移行する。初期から次を守れば移行コストはほぼゼロになる。

1. **DB接続は `DATABASE_URL` 環境変数のみで切り替わるようにする**
2. **画像の保存・取得はローカルパスをコード全体に散らさず、保存先を差し替えられる層を1つ挟む**
3. **セッション・キューをサーバーのメモリ上に持たない**（PostgreSQL に保持する）
