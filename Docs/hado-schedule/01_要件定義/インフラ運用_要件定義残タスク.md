## A. 最優先で決めるべき事項（優先度：高）

### A-1. RTO / RPO の目標値（未決）

**なぜ必要か**
RTO（目標復旧時間）と RPO（目標復旧時点）は、バックアップ方式・監視設計・障害対応手順・利用規約の可用性表明のすべての前提になる数値です。要求機能に SLA 99.9% は書かれていますが、**「壊れたときにどこまで戻ってよいか／どれだけで復旧するか」は一切定義されていません。**

案1の実測見込みは **RTO 数時間・RPO 最大24時間**（技術スタック 5章）です。これは目標値ではなく現状値であり、「この値を目標として受け入れる」という合意そのものが取られていません。

**決まらないと何が起きるか**
- バックアップ頻度を決められない。日次03:00のみで良いのか、WAL アーカイブ（PITR）を追加すべきかが判断できないまま基本設計に入る
- 実際の障害時に「どこまで復旧すればよいか」の基準がなく、対応が長期化する
- 最悪ケース：**土曜夜にサーバーが壊れると、直近の03:00以降に登録された予約が全部消える。** 翌日曜日にコートへ来た利用者の予約が存在しない、という事象が起きる。誰の責任で、どう救済するかが未定義
- SLA 99.9% を利用規約や拠点への説明資料に書いてしまうと、実態（99.5%程度）と乖離した表明になる

**選択肢と推奨案**

| 案 | RPO | RTO | 追加コスト | 備考 |
|---|---|---|---|---|
| 案a：現状追認 | 24時間 | 数時間（実測は8時間程度を見込むべき） | なし | 実測値をそのまま目標にする。最も安価だが、上記の「予約が消える」事象を受容することになる |
| 案b：バックアップ増回 | 6〜12時間 | 数時間 | ほぼなし（ジョブ追加のみ） | `pg_dump` を1日2〜4回に増やす。予約DBは小さいため取得時間の影響は限定的 |
| 案c：WAL アーカイブ（PITR） | 数分 | 数時間 | ストレージ微増 + 設計工数 | PostgreSQL の継続的アーカイブ。単一VM構成のままでも RPO を大幅に短縮できる。**退避先が別ロケーションであることが前提** |

**推奨：案c（RPO 15分以内 / RTO 8時間以内）を目標値とする。** 予約は当日・翌日利用が多く、失われた予約は復元手段がありません（利用者の記憶に頼るしかない）。WAL アーカイブは案1のまま導入でき、冗長化も追加VMも不要です。RTO は手動リストア前提のため 8時間（＝メンテナンス枠1回分より長い）を上限として明示し、**「SLA 99.9% は目標であり保証値ではない」ことを A-5 の合意事項とセットで文書化する**ことを推奨します。

### A-2. メンテナンス実施曜日（未決）

**なぜ必要か**
「週1回 0:00〜5:00」は決まっていますが**曜日が決まっていません。** 曜日はメンテナンス通知バッチの実装、Windows Update の適用スケジュール（アクティブ時間設定）、デプロイのリリース計画、監視の抑止（メンテナンス中のアラート抑止ウィンドウ）すべてに直結します。

**決まらないと何が起きるか**
- Zabbix のメンテナンス期間（アラート抑止）を設定できず、**毎回の計画メンテナンスで障害アラートが誤発報する**。誤報が続くとアラートが信用されなくなり、本当の障害を見逃す
- Windows Update の「アクティブ時間」設定を確定できず、既定の自動更新のまま運用開始 → **昼間に勝手に再起動して非計画停止になる**（許容は月42分しかない）
- 全ユーザーへの事前通知（要件）の送信タイミングを実装できない
- リリース計画が立てられず、デプロイのたびに日程調整が発生する

**選択肢と推奨案**

| 曜日 | 利点 | 欠点 |
|---|---|---|
| 火・水・木の早朝 | 作業が延長しても翌営業日に対応者が動ける。週末のコート利用ピークから最も遠い | なし（実質的な欠点は小さい） |
| 月曜早朝 | 週初にリリースできる | 日曜夜＝週末利用直後で、直前の予約データ量が多い。作業が延びると月曜に影響 |
| 土・日の早朝 | 平日業務に影響しない | **コート利用のピーク直前。** 作業延長時の影響が最大。対応者を確保しにくい |

**推奨：水曜日 0:00〜5:00（火曜深夜）。** 技術スタックの推奨（火〜木の早朝）に沿い、かつ前後に平日が2日ずつ確保できます。**あわせて「メンテナンスを実施しない週があってよいか（毎週固定枠を確保するが作業がなければスキップ）」も同時に決めること。** 通知バッチの実装方針（毎週必ず通知するのか、作業がある週だけ通知するのか）が変わります。

### A-3. メンテナンス実施日のバックアップ（03:00）と作業の順序（未決）

**なぜ必要か**
**バックアップ時刻 03:00 はメンテナンス枠 0:00〜5:00 の内側にあります。** 要求機能・技術スタックの双方が「順序を定めること（要決定）」と明記していますが、未決のままです。これは要件定義工程で決めるべき運用ルールです。

**決まらないと何が起きるか**
- **最悪ケース：0:00 から破壊的マイグレーションを開始 → 03:00 に自動バックアップが起動し、壊れかけた中間状態のDBをダンプ → 前日の正常なバックアップを上書き（30日保持なので上書きはされないが、最新バックアップが使えない状態になる）→ 04:00 に切り戻しを判断したときに、直前の正常な状態に戻せない**
- あるいはマイグレーション中のテーブルロックと `pg_dump` が競合し、バックアップが失敗またはデプロイがハングする
- どちらも「本番で戻せない」に直結します

**選択肢と推奨案**

| 案 | 内容 | 評価 |
|---|---|---|
| 案a：バックアップ完了を待って作業開始 | 03:00 のバックアップ完了（想定30分以内）を確認してから 03:30 に作業開始 | 安全だが、作業可能時間が 03:30〜05:00 の1.5時間に圧縮される。大規模作業に不足 |
| 案b：作業前に手動バックアップを取得し、定期バックアップをスキップ | 0:00 に手動フルバックアップ → 作業 → 定期ジョブはメンテナンス日のみ無効化 | 作業時間を最大化でき、作業直前の状態が確実に保全される。ジョブ無効化の戻し忘れが事故要因 |
| 案c：定期バックアップの時刻をメンテナンス枠外へ移動 | 例：毎日 06:00 に変更 | 恒久的に競合が消える。ただし **03:00 は要求機能に明記された確定要件**のため、変更には要件そのものの改訂承認が必要 |

**推奨：案b を基本とし、ジョブ無効化の戻し忘れを防ぐため「無効化ではなくスキップ判定」で実装する。**
具体的には、バックアップスクリプトの冒頭で「メンテナンス実施中フラグファイル」の有無を確認し、存在すればスキップして正常終了ログを残す方式です。手順書に「作業開始前に手動バックアップ取得 → フラグ作成」「作業完了後にフラグ削除」を記載し、**フラグが翌日も残っていたら Zabbix でアラートを上げる**（＝バックアップが2日連続で取られていない状態の検知）ことを合わせて設計します。案c を採る場合は要求機能側の改訂が必要である点に注意してください。

### A-4. クラウド提供元・インスタンスの決定（未決）

**なぜ必要か**
国内VPS / Azure / AWS のいずれかが未決です。提供元によって、月額コストが2〜3倍変わるだけでなく、**バックアップ退避先（B-1）、ネットワーク設計、ライセンス（CAL の要否）、SLA の実効値、対応可能な運用作業（スナップショット取得の可否）が全部変わります。**

**決まらないと何が起きるか**
- 実見積もりが取得できず、予算承認が下りない → 構築着手が遅れる
- バックアップ退避先を決められない（同一クラウド内のオブジェクトストレージが最も安価だが、提供元が未定だと選べない）
- **提供元のインフラSLA が不明なまま、こちらの SLA 99.9% を論じている状態。** 国内VPS の多くは 99.99%〜99.9% を謳いますが、これはハードウェアの可用性であってVM単体の連続稼働を保証するものではありません。**上位のインフラSLA を超える可用性は原理的に提供できない**ため、提供元の SLA が判明して初めて自社 SLA の実現可能性が確定します
- Windows Server ライセンス / CAL の要否が確定しない（オンプレ調達時のみ発生する論点）

**選択肢と推奨案**

| 提供形態 | 月額目安 | 利点 | 欠点 |
|---|---|---|---|
| 国内VPS（Windows Server プラン） | 1〜2万円 | 最安。ライセンス込み。国内リージョンで低遅延 | スナップショット・オブジェクトストレージ等の周辺サービスが弱いことがある。**バックアップ退避先を別途契約する必要**が出る |
| Azure（Windows VM） | 2.5〜5万円 | Windows との親和性が高い。Blob Storage への退避が容易。VMスナップショットで RTO を短縮できる | 国内VPSより高い |
| AWS（Windows VM） | 2.5〜5万円 | S3 への退避が容易。エコシステムが厚い | 同上 |

**推奨：Azure。** 理由は3点です。(1) バックアップ退避先（B-1）を同一クラウド内の Blob Storage で完結でき、追加契約と経路設計が不要。(2) **VM スナップショット / Azure Backup により、A-1 の RTO（手動リストア＝数時間）を大幅に短縮できる**。案1の最大の弱点である RTO に直接効きます。(3) Windows Server ライセンスが時間課金に含まれるため CAL 論点が消えます。
コスト最優先であれば国内VPSですが、その場合は**バックアップ退避先とスナップショット代替手段を必ずセットで決めてください**（決めないと案1のリスクが実測値より悪化します）。

### A-5. 障害時の連絡体制と対応者（未決）

**なぜ必要か**
Zabbix による24時間監視は要件ですが、**アラートを誰が受け取り、誰が判断し、誰が復旧するのかが一切定義されていません。** 監視は「検知」までしかできず、対応者がいなければ検知は無意味です。またインシデント対応SLA（重大度1で3日以内初期対応）が定義されている以上、その起算点と対応主体を決めるのは要件定義工程の責務です。

**決まらないと何が起きるか**
- Zabbix のアクション（通知先）を設計できず、**アラートがどこにも飛ばない監視が構築される**
- 深夜のメンテナンス枠（0:00〜5:00）で障害が起きたとき、誰も起きていない
- インシデントSLA の「3日以内に初期対応」の起算点（検知時刻か、受付時刻か、営業日換算か）が不明で、SLA を満たしたかどうか判定できない
- **要求機能に「ユーザーサポート対応は行わない」と明記されている一方で、利用者が障害に気づいたときの申告経路が定義されていない。** システム管理者へのメールが唯一の経路だが、その受信者と応答期待値が未定義

**加えて整理が必要な矛盾**
インシデント対応SLA（重大度1＝**5日以内に復旧**）と、SLA 99.9%（非計画停止**月約42分**）は両立しません。重大度1が1回起きて5日で復旧すれば、その月の可用性は約84%になります。この2つの要件の関係（SLAは目標値であり、インシデントSLAが契約上の約束、等）を明文化してください。

**選択肢と推奨案**

| 決めるべきこと | 選択肢 | 推奨 |
|---|---|---|
| アラート通知先 | メール / チャット（Slack・Teams）/ 電話 | 重大度別に分ける。障害系はチャット＋メール、サービス全断は電話も |
| 対応時間帯 | 24時間オンコール / 平日日中のみ / 平日日中＋週末朝の目視確認 | **平日日中対応＋深夜の自動復旧**。運用者が確保できない前提であれば、人ではなく「Windows サービスの自動再起動」「VMの自動再起動」で一次復旧を賄う設計にする |
| 重大度の判定者 | システム管理者が単独判定 / 判定基準表による機械的判定 | **判定基準表を作る**（「ログインできない＝重大度1」等）。人の裁量に任せると SLA 判定が揺れる |
| 障害の申告経路 | システム管理者宛メールのみ | 現状の要件どおり。ただし**受信アドレスと、そのメールボックスの監視（見落とし防止）**を決めること |
| SLA 起算点 | 検知時刻 / 受付時刻 / 翌営業日 | **検知時刻起算・営業日換算**を明示 |

**推奨：まず「運用担当者が誰か（何人か）」を確定させてください。** これが1人なのかチームなのかで、上記すべての現実的な答えが変わります。1人運用であれば、24時間オンコールは実現不可能なので、**「深夜・週末は自動復旧のみ、人の対応は翌営業日」と明記し、それが SLA 99.9% と両立しないことを関係者が合意した記録を残す**のが正しい進め方です。C-6 とセットで決めてください。

### A-6. ドメイン取得と証明書の運用主体（未決）

**なぜ必要か**
TLS 1.2 以上は要件、証明書は win-acme による Let's Encrypt 自動更新と決まっています。しかし**サービスのドメイン名そのものと、その取得者・管理者・DNS の管理主体・更新費用の負担者が一切決まっていません。** 証明書はドメインに紐づくため、ドメインが決まらないと証明書運用は設計できません。

**決まらないと何が起きるか**
- **ドメイン更新失念でサービスが全断する。** 証明書の期限は監視項目に入っていますが、**ドメインの有効期限は監視項目に入っていません。** ドメインが失効すれば証明書更新も名前解決も同時に落ち、復旧には再取得（他者に取得されていれば復旧不能）が必要です。これは案1のどの障害よりも復旧が困難な事象です
- win-acme の Let's Encrypt 更新は **HTTP-01 チャレンジで 80番ポートの受信が必要**（または DNS-01 チャレンジで DNS レコードの自動書き換え権限が必要）。どちらを使うかはファイアウォール設計（C-2）と DNS 管理権限に依存するため、決まらないとネットワーク設計が確定しない
- メール送信（A-7）の SPF / DKIM / DMARC レコードを設定するにも DNS の管理権限が必要。担当が不明だと送信ドメイン認証を設定できず、**通知メールが迷惑メール判定される**（予約通知・パスワードリセットが届かない ＝ 機能不全）

**選択肢と推奨案**

| 決めるべきこと | 選択肢 | 推奨 |
|---|---|---|
| ドメイン名 | 未定 | 早期に確保する（取得は安価かつ先着） |
| 取得・名義 | 個人名義 / 法人名義 | **法人（サービス運営主体）名義。** 個人名義は退任・連絡不能時にサービスごと失う |
| 登録事業者 | お名前.com / Route53 / Azure DNS 等 | **A-4 で決めるクラウドと同じ事業者の DNS を推奨**（Azure なら Azure DNS）。DNS-01 チャレンジの自動化と SPF/DKIM 設定が同一コンソールで完結する |
| 更新方式 | 自動更新 ON / 手動 | **自動更新 ON ＋ 支払いカードの有効期限管理**。カード失効による更新失敗が典型的な事故 |
| 証明書チャレンジ方式 | HTTP-01 / DNS-01 | HTTP-01（80番開放が前提。ワイルドカード不要なら簡単）。DNS を自動操作できるなら DNS-01 の方が 80番を閉じられる |
| 監視 | — | **証明書の有効期限に加えて、ドメインの有効期限も監視項目に追加する**（外形監視SaaS か、期限日を手動でカレンダー登録） |

### A-7. メール送信プロバイダ（未決）

**なぜ必要か**
本システムはメール依存度が非常に高く、**メールが送れないと初回登録もパスワードリセットもできず、実質的にサービスが機能しません。**（要求機能：初回/再設定時のランダム文字列通知、予約編集通知、チーム申請・承認通知、メンテナンス通知）。プロバイダはインフラの外部依存であり、可用性・コスト・運用（バウンス処理・送信ドメイン認証）の設計対象です。

**決まらないと何が起きるか**
- 通知機能の実装方式（SMTP か API か）が決まらず、実装着手できない
- 送信ドメイン認証（SPF / DKIM / DMARC）を設定できず、**通知メールが迷惑メールに振り分けられる**。パスワードリセットが届かないという問い合わせが多発するが、要求機能では「ユーザーサポート対応は行わない」ため受け皿がない
- 送信上限・レート制限が不明。**メンテナンス通知は全ユーザー（3年後2,000人）への一斉送信**であり、無料枠や秒間レート制限に抵触して一部に届かない可能性がある
- 「配信失敗時は3回リトライ」の要件はあるが、**バウンス（宛先不達）の扱いが未定義。** 無効アドレスへの送信を続けると送信元評価が下がり、正常な宛先にも届かなくなる

**選択肢と推奨案**

| プロバイダ | コスト | 利点 | 欠点 |
|---|---|---|---|
| Amazon SES | 従量（1,000通あたり$0.10程度） | 最安。大量送信に強い | サンドボックス解除の申請が必要。バウンス処理を自前で実装する必要がある |
| SendGrid | 無料枠後 月$20程度 | 管理画面でバウンス・開封状況が見える。導入が容易 | SES より高い |
| 自前SMTP（同一VM上） | 0円 | 追加契約不要 | **非推奨。** IPレピュテーションがなく、ほぼ確実に迷惑メール判定される。単一VMのため送信キューも失われる |

**推奨：SendGrid（初期）。** 想定送信量（2,000ユーザー規模の通知）は無料枠〜低額枠に収まり、**バウンス・スパム報告の自動抑止が標準で備わっている**ため、運用者が少ない体制（C-6）では管理コストの差が価格差を上回ります。コスト最優先なら SES ですが、その場合は**バウンス処理（SNS 経由での通知受信と送信停止リスト管理）の実装工数を見積もりに含めてください。**
いずれの場合も、**送信元ドメイン（A-6）の SPF / DKIM / DMARC 設定を要件に含めること**、および **「メール送信の失敗率」を Zabbix の監視項目に追加すること**を推奨します（現在の監視項目に入っていません）。

## B. バックアップ・可用性・運用ポリシー（優先度：高〜中）

### B-1. バックアップ退避先の具体（提供元・暗号化・鍵管理）— 優先度：高

**なぜ必要か**
「オブジェクトストレージ等の別ロケーションへ退避する」方針は決まっていますが、**具体的な退避先・転送方式・保持設定・暗号化・アクセスキーの管理が未定義**です。単一VM構成では、退避が実装されていなければサーバー障害でバックアップごと消えます。バックアップには個人情報（メールアドレス、プロフィール、予約履歴）が丸ごと含まれるため、保護方針との整合も必要です。

**決まらないと何が起きるか**
- 「退避する」とだけ書かれた手順書のまま構築が進み、**実際にはローカルディスクにしか置かれていない状態で運用開始する。** サーバー障害＝全データ消失
- 退避先の認証情報（アクセスキー）を本番VM上に平文で置いてしまう。**VM が侵害されたとき、攻撃者はバックアップも同時に削除・窃取できる**（ランサムウェアの典型的な被害拡大経路）
- 暗号化なしで個人情報を含むダンプを外部ストレージに置くと、保護方針「個人情報は暗号化して保管」に違反する
- 退避先側の保持期間を設定し忘れ、30日保持要件が守られない（または無制限に増えて課金が膨らむ）

**選択肢と推奨案**
- 退避先：A-4 で決めるクラウドと同一事業者のオブジェクトストレージ（Azure Blob / S3）を推奨。国内VPSを選ぶ場合は別途契約
- 暗号化：**ダンプファイルをアップロード前にパスワード付きで暗号化**（保存先の暗号化機能だけに頼らない）。復号鍵はバックアップとは別の場所に保管する
- 認証情報：**書き込み専用（削除・上書き不可）の権限に絞る**。加えてストレージ側で世代保持（バージョニング / イミュータブル設定）を有効にし、VM 侵害時にバックアップを消せない構成にする
- 保持：ストレージ側のライフサイクルルールで31日経過分を自動削除
- **リストア試験（B-2）は必ず「退避先から取得して復元する」経路で行うこと。** ローカルのダンプから戻すだけでは退避経路の検証にならない

### B-2. リストア試験の実施頻度・合否基準・実施者 — 優先度：高

**なぜ必要か**
「リストア手順書とリストア試験まで設計に含める。取得だけの設計は未完成」という方針はありますが、**試験の頻度・手順・合否基準・実施者が未定義**です。バックアップは「取れていること」ではなく「戻せること」でしか価値が測れません。

**決まらないと何が起きるか**
- **バックアップが毎日成功していても、実際には復元できないファイルが30日分溜まる。** よくある原因：`pg_dump` のバージョンとリストア先の不一致、`btree_gist` 拡張の未インストール、排他制約（`EXCLUDE USING gist`）を含むスキーマの復元順序エラー、文字エンコーディングの不一致
- 本システムは **`EXCLUDE USING gist` の手書きSQLを含む特殊なスキーマ**を持つため、素直に戻らないリスクが通常より高い
- RTO 目標（A-1）の実測値が取れない。「数時間」が本当に数時間なのか、8時間なのか24時間なのかを誰も知らないまま運用に入る
- 障害発生時、初めて手順書を読みながらリストアすることになり、RTO を大幅に超過する

**選択肢と推奨案**

| 頻度案 | 評価 |
|---|---|
| 四半期に1回 | 最低ライン。推奨 |
| 半期に1回 | 許容範囲だが、スキーマ変更が多い時期には不足 |
| 年1回 | 不足。1年間の変更が一度に検証されるため、失敗時の原因切り分けが困難 |

**推奨：四半期に1回＋「破壊的マイグレーションを含むリリースの直後」に実施。**
- 実施環境：本番とは別（ステージング環境 B-9、または一時的に作成する検証VM）。**本番へのリストア試験は絶対に行わない**
- 合否基準：(1) 退避先から取得して復元が完了する、(2) **復元にかかった実時間を記録し、RTO 目標（A-1）以内である**、(3) 復元後にレコード件数と直近予約データが一致する、(4) 排他制約とインデックスが復元されている
- 記録：実施日・所要時間・発生した問題を残し、RTO 目標の妥当性を毎回見直す
- 初回は**構築完了時（リリース前）に必ず1回実施**し、その実測値をもって A-1 の RTO を確定させることを推奨します

### B-3. デプロイのロールバック手段 — 優先度：高

**なぜ必要か**
デプロイ手順（成果物配置 → `prisma migrate deploy` → サービス再起動）と「各段の失敗時の切り戻し手段をセットで用意する」方針は決まっていますが、**具体的な切り戻し手段が未定義**です。特に **DB マイグレーションは Prisma に自動ロールバック機能がなく、`migrate deploy` は down マイグレーションを持ちません。**

**決まらないと何が起きるか**
- **メンテナンス枠（0:00〜5:00）内でマイグレーションが失敗し、戻せないまま朝を迎える。** 非計画停止の許容は月約42分しかないため、この時点で月次SLAは即座に破綻する
- アプリのみ切り戻してDBスキーマが新しいまま、という不整合状態になる（旧コード × 新スキーマ）
- 部分適用されたマイグレーションが残り、次回の `migrate deploy` も失敗し続ける

**選択肢と推奨案**

| 対象 | 切り戻し手段の選択肢 | 推奨 |
|---|---|---|
| アプリ成果物 | 前バージョンのディレクトリを保持して切り替え / 再ビルド | **世代保持方式**（例：`app_20260726_0100` のようにリリース単位でディレクトリを作り、シンボリックリンクまたは IIS の物理パス切替で戻す）。直近3世代を保持 |
| DBスキーマ | 逆方向マイグレーションSQLを事前作成 / バックアップからリストア | **破壊的変更を含むリリースでは、作業直前の手動バックアップ（A-3 案b）からのリストアを正規の切り戻し手段とする。** ただしリストアには時間がかかるため、所要時間を計測して枠内に収まるか事前に確認する |
| 破壊的マイグレーション | 自動適用 / 人の承認を挟む | **人の承認を挟む。** カラム削除・型変更・NOT NULL 追加を含む場合は自動適用しない（残タスク B-6「マイグレーション自動実行の範囲」と同じ論点） |
| 順序 | — | 旧コード × 新スキーマの共存期間を作らないため、**後方互換なマイグレーションを原則とする**（カラム削除は「使用停止リリース → 次リリースで削除」の2段階） |

**あわせて決めること：緊急リリース（ホットフィックス）を枠外に行ってよいか。** 現在の方針は「デプロイは原則メンテナンス枠内」ですが、重大度1の障害修正を次の水曜まで待つことはできません。**枠外リリースの許可条件と承認者**を定義してください。

### B-4. メンテナンス作業の中断・切り戻し判断基準 — 優先度：中

**なぜ必要か**
「枠内に収まらない場合の中断・切り戻し判断基準を手順に定める」方針はありますが、**基準そのものが未定義**です。深夜の作業中に「あと少しで終わりそう」という判断で延長するのは、最も事故が起きやすいパターンです。

**決まらないと何が起きるか**
- 04:50 まで粘って失敗し、切り戻す時間もなく 05:00 を超える。**朝10:00 のコート利用開始までにサービスが戻らない**
- 判断基準がないと、作業者の主観で毎回結論が変わる

**選択肢と推奨案**
**推奨：「04:00 チェックポイント」方式。**
- 04:00 時点で作業が完了していない、または完了見込みが立たない場合は**無条件で切り戻しを開始する**（切り戻しに必要な時間を1時間確保する）
- 切り戻しの所要時間は B-2 のリストア試験で計測した実測値を用い、実測が1時間を超える場合はチェックポイントを前倒しする
- 「延長する」という選択肢を手順書に置かない。延長が必要な作業は、そもそも複数回の枠に分割して計画する

### B-5. Windows Update の適用方針 — 優先度：高

**なぜ必要か**
「Windows Update が枠外に再起動を起こさない設定を必ず入れる」方針は決まっていますが、**どの方式を採るか、誰がいつ適用を承認するか、緊急パッチの扱いが未定義**です。Windows Server の既定設定は自動更新・自動再起動であり、**何もしなければ既定のまま運用開始します。**

**決まらないと何が起きるか**
- **昼間に Windows Update が再起動を起こし、コート利用時間中にサービスが停止する。** 再起動と更新適用で10〜30分の停止となり、**1回で月間許容（約42分）のほぼ全部を消費する**
- 逆に更新を止めっぱなしにすると、既知の脆弱性が放置される。要求機能は SAST/DAST による継続監視を求めており、OS の未適用パッチはそれと矛盾する
- 更新起因の障害が起きたとき、いつ何が適用されたかの記録がなく原因を特定できない

**選択肢と推奨案**

| 方式 | 内容 | 評価 |
|---|---|---|
| アクティブ時間の設定 | 再起動を抑止する時間帯を指定 | 最低限。ただし最大18時間しか指定できず、完全な制御にはならない |
| グループポリシー / レジストリで「ダウンロードのみ・インストールは手動」 | 自動再起動を完全に止める | **推奨。** 適用タイミングを人が完全に制御できる |
| WSUS | 更新を集中管理し、承認したものだけ配信 | 単一VM1台のために WSUS を建てるのは過剰 |
| 自動更新を無効化 | — | **非推奨。** パッチが永久に当たらなくなる |

**推奨：「自動ダウンロード・手動インストール」に設定し、メンテナンス枠（A-2 で決めた曜日）で適用する。**
- 適用サイクル：**月1回**（毎月第1メンテナンス日）を定例とし、緊急度の高い脆弱性（CVSS 9.0以上、リモートコード実行等）は臨時枠で適用する
- 適用前に必ず A-3 の手動バックアップ（またはVMスナップショット）を取得する
- **適用後の再起動をもって、サービス自動起動が正しく動くかの実地検証を兼ねる**（自動起動設定が壊れていないかを月1回確認できる）
- 適用履歴（日時・KB番号・再起動有無）を記録する
- **クラウドVM（A-4）を選ぶ場合、VM スナップショットを更新前に取得できると切り戻しが容易になる。** これは A-4 の提供元選定にも影響します

### B-6. 監視閾値の具体値（ディスク / 応答時間 / エラー率） — 優先度：中

**なぜ必要か**
CPU 80% / メモリ 85% は要件で確定していますが、**それ以外の監視項目には閾値がありません。** 閾値のない監視項目は Zabbix に設定できず、実質的に監視されません。

**決まらないと何が起きるか**
- **ディスク枯渇でサービスが停止する。** 単一VMにログ・DB・バックアップ・アップロード画像がすべて同居しており、**ディスク枯渇は本構成で最も現実的な障害シナリオ**です。PostgreSQL はディスクフルで書き込み不能になり、予約登録が全面停止します
- 応答時間の閾値がないと、性能要件（画面表示3秒 / 予約登録5秒）を満たしているかを継続的に判定できず、劣化の兆候を見逃す
- エラー率の閾値がないと、「一部機能が利用不可（重大度2）」の状態を検知できず、利用者からの申告でしか気づけない

**選択肢と推奨案（すべて推奨値。承認が必要）**

| 項目 | 警告 | 障害 | 補足 |
|---|---|---|---|
| ディスク空き容量（OS / データ / バックアップ 各ボリューム） | 空き20% | 空き10% | **障害レベルは対応猶予から逆算すること。** 100GB の10%＝10GB は、ログ増加ペースによっては数日しか猶予がない |
| 外形監視 応答時間（画面表示） | 3秒超過が5分継続 | 10秒超過またはタイムアウト | 要件値3秒を警告閾値に使う |
| 外形監視 応答時間（予約API） | 5秒超過が5分継続 | 15秒超過またはタイムアウト | 要件値5秒を警告閾値に使う |
| アプリケーションのエラー率 | 5分間で1%超 | 5分間で5%超 | 母数が小さい時間帯（深夜）は件数ベースの下限を併用する |
| TLS証明書 有効期限 | 残30日 | 残7日 | win-acme は残30日で更新するため、警告が出続ける場合は自動更新が失敗している |
| バックアップジョブ | — | 24時間以内に成功記録なし | A-3 のスキップフラグ残存も検知できるようにする |
| PostgreSQL コネクション数 | max_connections の70% | 85% | 残タスク B-3（DB接続・性能）と連動 |

**あわせて決めること**
- **外形監視用のアカウント**：ログインの外形監視には実アカウントが必要です。本番DBに監視専用ユーザーを作るか、ログイン画面の表示確認までに留めるかを決めてください（監視用アカウントは監査ログにも毎分記録される点に注意）
- **メンテナンス枠中のアラート抑止**：A-2 の曜日確定後、Zabbix のメンテナンス期間を設定する

### B-7. ログ・データ保持期間の整合 — 優先度：中

**なぜ必要か**
保持期間の定義が複数ドキュメントに分散し、**値が食い違っています。** 保持期間はディスクサイジング（B-6）、削除バッチの実装、バックアップ容量、法令対応のすべてに直結するため、要件定義工程で1つに揃える必要があります。

| 対象 | 要求機能の記述 | 保護方針の記述 | 状態 |
|---|---|---|---|
| 予約データ | 日付が過ぎた時点で**物理削除**。ただし紛争解決に必要な情報は**12ヶ月**保持 | 予約履歴は予約日から**24ヶ月**（紛争解決のため） | **矛盾** |
| アクセスログ | ログレベルINFO以上、週次5世代（＝実質約5週間） | アクセスログ **90日** | **矛盾** |
| 監査ログ | **180日** | （記載なし） | 要求機能のみ |
| 退会ユーザー | 退会時点で**物理削除** | 非アクティブは最終ログインから12ヶ月 | 整合の確認が必要 |
| バックアップ | 30日保持 | （記載なし） | — |

**決まらないと何が起きるか**
- 削除バッチの実装仕様が確定せず、実装できない（あるいは誤った期間で実装され、**復元不能な形で本番データを消す**）
- **バックアップ保持30日 vs 予約データの物理削除**の関係が未定義。日付経過で物理削除されたデータが、30日分のバックアップには残り続けます。「削除したはずの個人情報がバックアップに残っている」状態を、保護方針上どう扱うかが未整理です（開示請求・削除申請への回答に影響）
- ログのディスク使用量を見積もれず、B-6 のディスク閾値もサイジングも決められない

**推奨**
- **要求機能を正とし、保護方針側を改訂する**（要求機能がシステム要件の正本のため）。ただし保護方針は対外公開文書であり、**法令上「実態と異なる保持期間を公開している」ことになるため、改訂は必須**です
- 「監査ログ180日」と「ログファイル週次5世代」は別物として整理する（アプリケーションログ＝5世代、監査ログ＝180日、この2系統を別ファイル・別ディレクトリに出力する）
- **バックアップ内の削除済み個人情報の扱いを1文で定義する**（例：「バックアップは30日で自動廃棄されるため、削除申請から30日以内にすべての複製が消滅する」）
- なお、この整理は**個人情報保護方針の改訂を伴うため、本領域単独では決定できません。** 該当領域の担当と合わせて決定してください

### B-8. サービス終了時のユーザーデータ取り扱い方針 — 優先度：中

**なぜ必要か**
`要件定義残タスク.md` A-10「運用ポリシー」に項目名だけ挙がっており、**内容が未定義**です。インフラ観点では、サービス終了は「サーバーとストレージをいつ誰が停止・削除するか」という具体的な運用手順であり、要件定義工程で方針を決めておく必要があります。

**決まらないと何が起きるか**
- 終了時に**クラウド契約だけ解約してバックアップの退避先が放置される**（＝個人情報が外部ストレージに残り続け、課金も続く）
- 利用者への告知期間・データエクスポート提供の有無が決まっておらず、終了直前に慌てて設計することになる
- 保護方針では「開示請求」「削除申請」の権利を認めているが、サービス終了後の窓口が定義されていない
- 拠点（法人利用者）が予約実績を必要とする場合の引き渡し方法がない

**選択肢と推奨案**
- 告知期間：**終了3ヶ月前に全ユーザーへメール通知**（既存のメンテナンス通知の仕組みを流用できる）
- データエクスポート：終了1ヶ月前まで、利用者が自分の予約履歴を取得できる手段を提供するか（**提供しないと決めるのも可。決めていない状態が問題**）
- 消去対象と順序：本番VM のディスク → バックアップ退避先のオブジェクト → ログ → 監査ログ の順に、**それぞれ削除完了を記録として残す**
- 消去時期：**サービス停止後、紛争解決用データの保持期間（B-7 で確定する12ヶ月または24ヶ月）が経過した時点で完全消去**。それまでは最終バックアップ1本のみをオフラインで保管
- 契約解約：ドメイン（A-6）、クラウド（A-4）、メール（A-7）、Zabbix Server の解約順序と時期を定める（**ドメインは最後に解約する。** 先に解約すると終了告知ページも出せなくなる）

### B-9. ステージング環境の要否 — 優先度：中

**なぜ必要か**
既存ドキュメントには**本番環境と開発環境（ローカル）しか登場せず、両者の中間となる検証環境が定義されていません。** 本システムは `EXCLUDE USING gist` の手書きSQLを含むマイグレーションを持ち、`prisma migrate deploy` を本番に直接適用する運用です。**適用の事前検証をどこで行うのかが未定義**です。

**決まらないと何が起きるか**
- **本番が唯一のマイグレーション検証環境になる。** 深夜のメンテナンス枠で初めてマイグレーションを実行し、そこで初めて失敗を知る
- リストア試験（B-2）の実施場所がない（本番でのリストア試験は行えない）
- ペネトレーションテスト（要求機能）の実施先が本番しかなくなる。**本番への攻撃的テストは実サービスを壊すリスクがある**
- セルフホストランナー（本番VM上）で失敗するデプロイを繰り返すことになる

**選択肢と推奨案**

| 案 | コスト | 評価 |
|---|---|---|
| 常設ステージングVM | 月1〜2万円（本番と同等） | 最も安全だが、案1のコスト感（月2〜5万円）に対して倍増する |
| **必要時のみ作成する検証VM** | 使用時間分のみ（数百円〜数千円/回） | **推奨。** クラウドVM（A-4）なら数十分で作成・破棄できる。マイグレーション検証・リストア試験・ペネトレーションテストの直前に作る |
| ローカル開発環境で代替 | 0円 | **不可。** OS（Windows Server vs Windows 10/11）、IIS の有無、サービス常駐、NTFS ACL がすべて異なり、Windows 固有の問題を検出できない |

**推奨：「必要時のみ作成する検証VM」を要件として明記する。** あわせて、**検証VMには本番データをそのまま置かない**（個人情報の複製が増える）か、置く場合はマスキングするか、あるいは「リストア試験の直後に必ず破棄する」ルールを定めてください。B-2 のリストア試験は本番バックアップを使う必要があるため、**「試験終了後24時間以内にVMごと破棄する」**を推奨します。

## C. 構築・CI・体制（優先度：中）

### C-1. CI の Windows ランナー検証 — 優先度：中

**なぜ必要か**
CI は GitHub Actions と決まっていますが、**どのランナーで検証するかが未定義**です。本番は Windows Server ですが、GitHub Actions の既定は Linux ランナーです。

**決まらないと何が起きるか**
- **CI は全部グリーンなのに本番デプロイで失敗する。** 典型例：ファイル名の大文字小文字の差（Linux は区別、Windows は非区別 → Linux で通るインポートが Windows で失敗、またはその逆）、パス区切り（`/` と `\`）、改行コード（LF / CRLF）、パス長制限（Windows の260文字制限）
- 失敗に気づくのが深夜のメンテナンス枠、というのが最悪のパターン

**選択肢と推奨案**
- **推奨：Linux ランナーで `lint` / 型チェック / `test` を回し、`build` のみ Windows ランナーでも実行する1本を追加する。** Windows ランナーは Linux の2倍の課金レートですが、build のみなら影響は限定的です
- あわせて決めること：**Node.js バージョンを CI と本番で一致させる**（本番 22 LTS。`package.json` の `engines` と CI の `setup-node` を同じ値にする）、`prisma generate` をビルド前に実行する、`.gitattributes` で改行コードを固定する

---

### C-2. ファイアウォール規則と管理アクセス経路 — 優先度：中

**なぜ必要か**
「Node を直接インターネットに公開しない」方針はありますが、**開放ポートの一覧と管理アクセス（RDP）の経路が未定義**です。単一VMのため、1つの開放ミスが全データへの経路になります。

**決まらないと何が起きるか**
- **PostgreSQL の 5432 がインターネットに開いたまま構築される。** クラウドVMの既定セキュリティグループ次第で容易に起こり、総当たり攻撃の対象になります。DBが単一VM上にある本構成では、これが全個人情報の流出経路になります
- **RDP（3389）を全開放したまま運用する。** Windows Server への攻撃で最も多い侵入経路であり、ランサムウェア被害の典型的な起点です
- Let's Encrypt の HTTP-01 チャレンジ（A-6）に必要な 80番の扱いが決まらず、証明書更新が失敗する

**選択肢と推奨案（すべて推奨値。承認が必要）**

| ポート | 用途 | 推奨する公開範囲 |
|---|---|---|
| 443 | HTTPS（IIS） | インターネット全体 |
| 80 | HTTP（HTTPSへのリダイレクト、Let's Encrypt HTTP-01） | インターネット全体（リダイレクトとチャレンジ以外は応答しない） |
| 3389 | RDP（管理） | **管理者の固定IPのみ、またはVPN経由のみ。** 全開放しない |
| 5432 | PostgreSQL | **localhost のみ。** ファイアウォールで外部から遮断し、`postgresql.conf` の `listen_addresses` も `localhost` に限定する（二重に閉じる） |
| 10050 | Zabbix Agent | **Zabbix Server の IP のみ** |
| 3000 等 | Next.js（`next start`） | **localhost のみ。** IIS 経由でのみ到達させる |

**あわせて決めること**：管理アクセスに固定IP制限を使うのか VPN を使うのか。運用者が複数拠点から作業する場合（C-6）、固定IP制限は現実的でない可能性があります。

---

### C-3. サービスアカウント設計と Secrets 運用 — 優先度：中

**なぜ必要か**
「専用サービスアカウント・最小権限」「環境変数ファイルは NTFS ACL でサービスアカウントのみ読取可」という方針はありますが、**アカウントの作成主体、パスワードの管理方法、権限の具体、セルフホストランナーの実行アカウント、Secrets のローテーション方針が未定義**です。

**決まらないと何が起きるか**
- 構築時に楽な方へ流れ、**Administrator でサービスを常駐させる**。アプリの脆弱性がそのままサーバー全体の乗っ取りに直結する
- **セルフホストランナーが管理者権限で動く。** GitHub Actions のワークフローを書き換えられる者は、本番サーバー上で管理者としてコードを実行できることになる
- サービスアカウントのパスワードが誰も知らない／全員が知っている状態になる
- `.env` の ACL 設定が漏れ、`Users` グループに読取権が残る（NTFS の既定では継承で読める）

**選択肢と推奨案**
- サービスアカウント：**アプリ用・PostgreSQL 用・ランナー用を分ける**。それぞれログオン権限を「サービスとしてログオン」のみに限定し、対話ログオンを拒否する
- ランナーの権限：**管理者権限を与えない。** デプロイ先ディレクトリへの書き込みと、対象サービスの再起動権限（`sc.exe sdset` で個別付与）のみに絞る
- パスワード管理：パスワード管理ツールで保管し、**保管場所と参照できる人を明記する**（C-6 の体制と連動）
- ACL：`.env` は継承を切り、`SYSTEM` + サービスアカウントのみ。**構築時のチェックリストに「`icacls` の出力を確認する」を含める**
- ローテーション：**Secrets の棚卸しを年1回**（GitHub Secrets、DB接続文字列、メールAPIキー、ストレージアクセスキー）。担当者の交代時は即時ローテーション
- リポジトリ：**セルフホストランナーを使うため、リポジトリをプライベートに保つことをルールとして明文化する**（パブリック化は第三者PRからの任意コード実行に直結）

### C-4. ウイルス対策ソフトの除外設定 — 優先度：中

**なぜ必要か**
Windows Server は Microsoft Defender が既定で有効です。**除外設定の要否が既存ドキュメントで検討されていません。**

**決まらないと何が起きるか**
- **PostgreSQL のデータディレクトリがリアルタイムスキャン対象になり、I/O 性能が大きく低下する**。性能要件（予約登録5秒以内）に影響し、原因の特定も困難です
- スキャン中のファイルロックにより、**PostgreSQL の書き込みエラーやデータ破損が発生する**。DBのデータディレクトリはウイルス対策の典型的な除外対象です
- `node_modules` のスキャンで `npm ci` とビルドが極端に遅くなり、メンテナンス枠内にデプロイが収まらなくなる
- 逆に、除外しすぎるとマルウェア検知能力が落ちる

**選択肢と推奨案**
- 除外対象（推奨）：PostgreSQL のデータディレクトリと WAL ディレクトリ、`postgres.exe`、アプリのデプロイ先ディレクトリと `node_modules`、`node.exe`、バックアップ出力先ディレクトリ、ログ出力先ディレクトリ
- **アップロード画像の保存先は除外しない**（利用者がアップロードするファイルであり、むしろスキャン対象として残すべき）
- 除外設定は**構築手順書に明記し、構築後に設定が入っているかを確認する項目を設ける**
- **利用者アップロードファイルのウイルススキャン方針も併せて決めること**（プロフィール画像・チーム画像・拠点画像を受け付けるため。現在どのドキュメントにも記載がありません）

### C-5. サーバー全損時の再構築手順と調達リードタイム — 優先度：中

**なぜ必要か**
案1は単一VM構成であり、**VM そのものが失われるシナリオ（クラウド側の障害、誤削除、ランサムウェア）**が現実的に存在します。バックアップからのデータ復元手順（B-2）は議論されていますが、**「戻す先のサーバーをどう用意するか」が未定義**です。RTO（A-1）はデータ復元時間だけでなく、サーバー再構築時間を含めた値でなければ意味がありません。

**決まらないと何が起きるか**
- RTO「数時間」が非現実的な値になる。**Windows Server の OS 導入、PostgreSQL 17 + `btree_gist`、Node.js 22、IIS + URL Rewrite + ARR、nssm、証明書、ACL 設定をゼロから手作業で行えば、数時間では終わりません**（実測1〜2日規模）
- 再構築手順が個人の記憶にしかなく、担当者不在時に復旧できない
- ドメイン・証明書・DNS の切り替え（A-6）が手順に含まれず、サーバーが戻っても利用者からアクセスできない

**選択肢と推奨案**

| 案 | RTO への効果 | コスト |
|---|---|---|
| 手順書のみ（手作業で再構築） | 1〜2日 | 0円 |
| **VM イメージ／スナップショットの定期取得** | 数時間 | ストレージ代のみ（月数千円） |
| 構成管理の自動化（PowerShell DSC 等） | 半日程度 | 設計工数 |
| 予備VMを常時起動（コールドスタンバイ） | 1時間程度 | VM代が倍 |

**推奨：VM スナップショットの定期取得（週次）＋ 再構築手順書。**
- クラウドVM（A-4）を選べば標準機能で実現でき、**案1の最大の弱点である RTO に最も費用対効果高く効きます**。A-4 で Azure を推奨した理由の1つです
- スナップショットは OS とミドルウェア構成の復元用、`pg_dump` はデータの復元用と役割を分ける（スナップショットのDBは古いため、リストア（B-2）と組み合わせて使う）
- 手順書には **DNS の切り替え（新VMのIPへ）と証明書の再取得**を必ず含めること
- **代替サーバの調達リードタイムを明記する**（クラウドなら数十分、オンプレ調達なら数週間）。オンプレを選ぶ場合、RTO 目標（A-1）が物理的に達成不可能になる可能性があります

### C-6. 運用体制・役割分担・運用コストの負担者 — 優先度：中

**なぜ必要か**
本書の A-5（連絡体制）、B-2（リストア試験の実施者）、B-5（Windows Update の承認者）、C-3（パスワード管理者）はいずれも**「誰がやるのか」に依存**しています。この根本が未定義であるため、個別の運用ルールを決めても実行主体が定まりません。またクラウド費用（A-4）、ドメイン（A-6）、メール（A-7）、Zabbix Server はいずれも**継続課金**であり、**支払いが止まればサービスが止まります。**

**決まらないと何が起きるか**
- 運用ルールを詳細に作っても、実行されないまま形骸化する
- **支払いカードの失効・予算の未承認でクラウド／ドメインが停止し、サービスが全断する**。復旧が最も困難な停止要因の1つです
- 1人運用であるにもかかわらず24時間監視を前提に設計してしまい、実態と乖離した運用設計になる
- 担当者の不在・交代時に、アカウント・Secrets・手順が引き継がれない

**選択肢と推奨案**
- 最低限、次を明記する：**運用担当者は何人か／障害対応を行うのは誰か／対応可能な時間帯／その人が不在のときのバックアップ担当**
- **1人運用であることが判明した場合、A-5 の推奨（深夜・週末は自動復旧のみ）と B-5（月1回の定例パッチ適用）を採用し、SLA 99.9% が達成できないことを関係者の合意事項として文書化する**のが正しい進め方です。これは案1の決定を覆すものではなく、案1のリスク（技術スタック 5章）を体制面にも展開するだけです
- 費用：クラウド／ドメイン／メール／ストレージの**支払い方法と負担者、年間予算の上限**を決める。支払い方法の有効期限を A-6 の監視対象に含める
- 引き継ぎ：アカウント一覧・Secrets の保管場所・手順書の所在を1つの文書に集約する（**本書と残タスク書の所在も含める**）

## D. 将来検討（優先度：低）

### D-1. ログ集約

現状は単一VM上のローカル保持で足ります（技術スタック 6章）。将来、案2への移行やサーバー台数の増加が起きた場合に集約先を検討します。
なお、**単一VM構成ではサーバー障害時にログも同時に失われる**ため、障害原因の事後分析ができません。C-5 のスナップショットとは別に、重大障害の調査を重視するなら監査ログのみ外部退避することを将来の検討事項とします。

### D-2. 案2（マネージドPostgreSQL移行）の判断基準

移行の技術的な準備（`DATABASE_URL` のみで切替、画像保存先の抽象化、セッションをメモリに持たない）は確定事項として本書 9.1 に記載済みです。
**未決なのは「いつ移行するか」の判断基準**です。将来、次のいずれかを超えたら移行を検討する、といった数値基準を運用開始後に設定してください（例：ユーザー数1,000超、RPO 24時間が業務上許容できなくなった時点、月次の非計画停止が2回を超えた時点）。
