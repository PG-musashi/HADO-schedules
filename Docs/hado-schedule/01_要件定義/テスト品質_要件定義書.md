# テスト品質 要件定義書

作成日：2026-07-26
担当領域：テスト品質（QA / テストエンジニア）

## 0. 本書の位置づけ

本書は、既存の要件定義ドキュメントから **「テスト品質」領域について既に決まっている内容** を抽出・整理したものです。

- 出典は `アプリケーション要求機能.md`（以下「要求機能」）、`要件定義残タスク.md`、`技術スタック提案.md`、`.claude/agents/qa-test-engineer.md` / `test-quality-reviewer.md`。
- **新しい仕様は創作しません。** 出典に明記がなく、テスト設計上どうしても解釈が必要な箇所のみ「※補完」と明示しています。※補完の記述は決定事項ではなく、確認が必要な仮置きです。
- 未決事項は本書には書かず、`テスト品質_要件定義残タスク.md` に分離しています。
- 本書はテスト計画書・テスト仕様書そのものではありません。基本設計以降でそれらを起こすための **要件側の確定事項** をまとめたものです。

## 1. テスト範囲（テストレベル）

要求機能「テスト・品質要件」により、テスト範囲は以下の4レベルとする。

| # | テストレベル | 要件上の位置づけ | 主な検証対象（要件から導かれる範囲） |
|---|---|---|---|
| 1 | 単体テスト | 実施必須 | 予約バリデーション、定員・チーム枠の計算、権限判定、パスワード要件判定、日時（JST）処理 |
| 2 | 統合テスト | 実施必須 | API + DB（Prisma / PostgreSQL）を通した予約登録・編集・削除、重複予約の拒否、通知送信、認証・セッション |
| 3 | システムテスト | 実施必須 | 画面を通したエンドツーエンド動作、非機能要件（応答時間・同時接続・スループット）、対応ブラウザ、レスポンシブ |
| 4 | UAT（ユーザー受入テスト） | 実施必須 | 利用者視点での受入確認（**実施主体・合格基準は未定義。残タスク参照**） |

補足（テストレベルごとの前提）:

- 予約の整合性は **DB制約（`EXCLUDE USING gist` による時間帯重複防止）とトランザクション** で守られる設計方針（技術スタック提案 3章）。したがって **Prisma を丸ごとモックした単体テストでは「二重予約を防げること」を検証できない**。この観点は実DB（テストDB）に対する統合テストで担保する。
- 同時実行（先勝ち判定）の検証は、モックではなく実DBに対する並行実行テストで行う。

## 2. カバレッジ目標

| 項目 | 値 | 出典 |
|---|---|---|
| コードカバレッジ目標 | **80% 以上** | 要求機能「テスト・品質要件」 |

運用上の前提（既存ドキュメントで確定している考え方）:

- カバレッジは **実測値を報告する**。推測値・見込み値を成果物に記載しない（`qa-test-engineer` / `test-quality-reviewer`）。
- カバレッジ数値が目標を満たしていても、以下は品質未達として扱う（`test-quality-reviewer` のレビュー観点）。
  - 実装をそのままコピーしたアサーション
  - 常に真になるアサーション（存在チェックのみ等）
  - モックし過ぎて対象ロジックが実行されていないテスト
  - スキップ／コメントアウトされたまま放置されたテスト
  - 条件分岐の片側しか通っていないファイル
- 正常系のみのテストは不合格。**境界値と異常系を必ず含める**。

※補完：カバレッジの計測対象範囲（アプリコードのみか、設定・生成コードを除外するか）と、CI での閾値強制（下回ったらビルド失敗にするか）は出典に記載がないため未確定。残タスク側で扱う。

## 3. セキュリティテスト方針

要求機能「テスト・品質要件」および `要件定義残タスク.md` B-4 により、以下が確定している。

| フェーズ | 実施内容 | 出典 |
|---|---|---|
| 初回リリース**前** | セキュリティテスト（**ペネトレーションテスト**）を実施する | 要求機能「テスト・品質要件」 |
| 初回リリース**後** | 自動セキュリティスキャンツール（**SAST / DAST**）で継続監視する | 同上 |

関連する確定要件（セキュリティテストの検証対象となる仕様）:

- 通信はすべて暗号化（**TLS 1.2 以上**）
- パスワードはハッシング・ソルト処理により保管
- パスワード要件：**最小8文字、大文字・小文字・数字を含む**
- ログイン失敗 **3回連続で該当アカウントを30分ロック**
- セッションタイムアウト：**30分間アクティビティがない場合に自動ログアウト**
- API通信は認証トークンによる認証
- 個人情報に関するデータは暗号化して保管
- ログに個人情報・パスワード・トークンを出力しない（技術スタック提案 4.4）
- 拠点スタッフは **自拠点のみ管理・閲覧可能**（他拠点リソースへのアクセスは拒否＝IDOR 検証対象）

未決（残タスク側で扱う）：SAST/DAST の具体ツール選定、ペネトレーションテストの実施方法・委託先、レート制限の実装方式、CAPTCHA 等ボット対策の要否（`要件定義残タスク.md` B-4）。

## 4. 検証すべき非機能要件（数値）

要求機能「システム要件」より、**テストで検証すべき数値目標**は以下。

| # | 項目 | 目標値 | 出典 | テストレベル |
|---|---|---|---|---|
| N-1 | 応答時間（画面表示） | **3秒以内** | パフォーマンス要件 | システムテスト／負荷テスト |
| N-2 | 予約登録の完了時間 | **5秒以内** | パフォーマンス要件 | システムテスト／負荷テスト |
| N-3 | 同時接続ユーザー数 | **100人** | パフォーマンス要件 | 負荷テスト |
| N-4 | スループット（予約登録） | **5件／1分** | パフォーマンス要件 | 負荷テスト |
| N-5 | SLA | **99.9%**（計画メンテナンス時間を除く）＝非計画停止 月約42分 | 可用性・信頼性要件 | 運用監視での確認（テストでの直接検証は不可） |
| N-6 | バックアップ | 1日1回（03:00）、**30日保持** | 可用性・信頼性要件 | 運用テスト（リストア検証） |
| N-7 | 監査ログ保持 | **180日** | データベース要件 | 運用テスト |
| N-8 | ログ世代管理 | 月〜日で記録、**5世代** | データ保持・削除ポリシー | 運用テスト |
| N-9 | 監視アラート閾値 | CPU **80%** 以上／メモリ **85%** 以上 | 運用・保守要件 | 運用テスト |

負荷テストのシナリオ軸（`qa-test-engineer` で確定している方針）:

1. **スイムレーン表示の同時参照**（N-1、N-3 の検証）
2. **同一枠への同時予約**（N-2、N-4 および先勝ち判定の検証）

重要な前提（`技術スタック提案.md` 5章）:

- 案1（Windows Server 単一VM）の実効可用性は 99.5% 程度で、**要件の SLA 99.9% は構成上保証できない**とドキュメントに明記されている。したがって N-5 は「テストで合否判定する項目」ではなく、**要件と構成の乖離として残タスク側で扱う**。
- RTO は数時間、RPO は最大24時間（実測見込み）。**目標値は未決**。

※補完：N-1／N-2 の測定条件（測定点がサーバー応答か画面描画完了か、対象回線・端末、パーセンタイル値か最大値か）は出典に記載がない。残タスク側で扱う。

## 5. 重点テスト観点一覧（要件から導かれるもの）

要求機能の記述を **検証可能な形** に落としたもの。各行は「期待結果」が一意に判定できる粒度で記述している。優先度は `qa-test-engineer` / `test-quality-reviewer` の重大度定義に従う。

### 5.1 予約の整合性（最優先）

| ID | 検証内容 | 期待結果 | 出典 |
|---|---|---|---|
| R-01 | 定員ちょうどまで予約（参加登録）する | 定員に達するまでは成功する | 「定員となった場合は予約不可」 |
| R-02 | 定員+1 人目が参加登録する | **拒否される** | 同上 |
| R-03 | チーム枠 N・定員 M の予約に対し、チーム枠が埋まった状態で別チームが参加申請する | **拒否される** | 「チーム枠と定員を同時に設定できる」 |
| R-04 | チーム枠が埋まった状態で個人が参加登録する | 定員（チーム枠を除いた人数）に空きがあれば成功する | 「定員はチーム枠を除いた人数を設定する」 |
| R-05 | 定員（個人枠）が埋まった状態でチームが参加申請する | チーム枠に空きがあれば成功する | 同上 |
| R-06 | 同一コート・同一時間帯に重複する予約を登録する | **拒否される**（DB の排他制約で防がれること） | 予約の基本仕様／技術スタック提案 3章 |
| R-07 | 同一枠に対し **複数リクエストが同時に**到達する | 送信時刻を**マイクロ秒まで比較して先勝ち**。後発は拒否される | 「エラーハンドリング」 |
| R-08 | R-07 で送信時刻が完全に同一の場合 | **利用者の登録番号が大きい利用者が優先**される | 同上 |
| R-09 | 拠点の営業時間外の時間帯で予約を登録する | **拒否される** | 拠点「営業日内で営業時間を設定する」 |
| R-10 | コートの利用可能時間外の時間帯で予約を登録する | **拒否される** | コート「営業時間内で利用可能時間を設定する」 |
| R-11 | 拠点スタッフがコートを利用不可設定（予約による）にした時間帯に、一般利用者が予約する | **拒否される** | コート「利用不可な場合は拠点スタッフが予約を行う事で利用不可状態を設定する」 |
| R-12 | コートの営業時間を 10:00〜22:00 より短く設定しようとする | **拒否される**（デフォルトから短縮不可） | コート「10:00〜22:00から短縮することはできない」 |
| R-13 | スイムレーン表示の時間範囲 | **10:00〜22:00、30分刻み**で表示される | 概要／画面UI |
| R-14 | イベント予約で複数コートを同時に予約する | 成功する（複数コート同時予約が可能であること） | 用語定義「イベント予約」 |
| R-15 | 予約種別（個人／チーム／イベント／店舗）で定員を未設定のまま登録する | **拒否される**（定員は必須） | 予約「定員を必須で設定する」 |

未確定のため本一覧に含めていない観点（残タスク参照）：予約のキャンセル可能期限、参加者の追加/削除可能期間、同一ユーザーの同一時間帯重複予約の可否、チーム数上限とチーム参加の優先順序、利用不可設定が **既存予約** に与える副作用。

### 5.2 権限（4ロール × 主要操作）

対象ロール：**メンバー／チームリーダー／拠点スタッフ／システム管理者**

| ID | 検証内容 | 期待結果 | 出典 |
|---|---|---|---|
| P-01 | 予約者本人が自分の予約を編集・削除する | 成功する | 「予約の編集・削除は予約者のみが可能」 |
| P-02 | 予約者以外のメンバーが他人の予約を編集・削除する | **拒否される** | 同上 |
| P-03 | システム管理者が任意の予約を編集・削除する | 成功する | 「ただしシステム管理者は全予約の編集・削除が可能」 |
| P-04 | 拠点スタッフが **他拠点** のコート・予約・拠点情報を参照／操作する | **拒否される**（IDOR） | 拠点スタッフ「自拠点のみ管理・閲覧可能」 |
| P-05 | メンバーがコートの追加/削除、営業日設定など拠点スタッフ操作を行う | **拒否される** | 利用者の操作一覧 |
| P-06 | チームリーダーがチーム所属申請／リーグ戦所属チームを承認する | 成功する | チームリーダーの操作 |
| P-07 | メンバー（非リーダー）がチーム所属申請を承認する | **拒否される** | 同上 |
| P-08 | メンバーが所属チーム申請を2件目登録する | **拒否される**（1つのみ申請可能） | メンバー「所属チームの申請（1つのみ申請可能）」 |
| P-09 | メンバーがリーグ戦所属チーム申請を2件目登録する | **拒否される**（1つのみ申請可能） | メンバー「リーグ戦所属チームの申請（1つのみ）」 |
| P-10 | チームに リーダー1名 + メンバー10名目 を登録する | **拒否される**（リーダー1名＋9名まで） | チーム「リーダーが1名＋9名までメンバーを登録する」 |
| P-11 | 拠点スタッフが拠点の新規登録／削除を行う | **拒否される**（拠点の追加/削除はシステム管理者） | 拠点「拠点の新規登録はアプリ管理者が行う」 |
| P-12 | 拠点スタッフの操作がログに記録される | 全操作がログに記録される | 拠点スタッフ「操作は全てログに記録される」 |
| P-13 | リーグ戦チームの登録がシステム管理者の承認を経る | 承認前は有効化されない | 用語定義「リーグ戦チーム」 |

※補完：本一覧はロール×操作の代表ケースであり、**網羅的な CRUD 権限マトリクスは未作成**（`要件定義残タスク.md` A-3）。マトリクス確定後、本節を差し替えること。

## 6. テスト環境の前提

`qa-test-engineer` および `技術スタック提案.md` により、以下が確定している。**この前提を外すとテストが通っても本番で壊れる**ため、テスト実行の必須条件として扱う。

| # | 前提 | 理由 |
|---|---|---|
| E-1 | **開発用DBに対してテストを実行しない。** 専用のテストDB（`hado_schedules_test`）を用意し、`DATABASE_URL` を切り替える | 開発データの破壊防止 |
| E-2 | **テストDBは `prisma migrate deploy` で構築する。`prisma db push` は使用しない** | 排他制約（`EXCLUDE USING gist`）と部分一意インデックスは**マイグレーションSQLに手書き**されており、`db push` では入らない。制約なしのDBではテストが通っても本番で二重予約が発生する |
| E-3 | **`prisma migrate reset` を開発DBに向けて実行しない**（DB全消去）。テストDBに対してのみ使う | 事故防止。テスト実行前に接続先DBを必ず確認する |
| E-4 | 同時実行テストは Prisma の `$transaction` を**並行に走らせて**検証する | 先勝ち判定（R-07 / R-08）はモックでは検証不可能 |
| E-5 | テスト間でDB状態が漏れないよう、各テストの前後で確実に初期化する | 実行順序依存の排除（`test-quality-reviewer` 保守性観点） |
| E-6 | PostgreSQL に **`btree_gist` 拡張**が必要 | 予約の時間帯重複防止の排他制約が依存する。テストDBにも必須 |
| E-7 | 日時カラムは `@db.Timestamptz`。JST 固定要件と整合させる | タイムゾーン起因の誤判定防止 |

前提となる技術構成（`技術スタック提案.md`）:

- Next.js 16（App Router）／ TypeScript strict ／ React 19 ／ Tailwind CSS v4
- PostgreSQL 17（セルフホスト）／ Prisma
- 本番：Windows Server 単一VM（Docker 不採用、Redis 不採用）
- CI/CD：GitHub Actions + Windows セルフホストランナー
- 作業ディレクトリ：`Source/Next.js/hado-schedules/`

**テストフレームワークは未導入。** Jest + React Testing Library（単体）、Playwright（E2E）は **提案段階**であり採用未決（`要件定義残タスク.md` B-5、`技術スタック提案.md` 6章）。導入にはユーザー承認が必要。

## 7. テスト対象外（実装しない機能）

要求機能「実装しない機能」により、以下のテストは**作成しない**。

- チェックイン機能
- 決済機能
- レビュー機能
- レポート機能
- 利用分析機能
- キャンセル待ち機能
- 記載されていない通知機能

ただし「記載されていない通知が送信されないこと」の検証（M-09）は**対象内**とする。
