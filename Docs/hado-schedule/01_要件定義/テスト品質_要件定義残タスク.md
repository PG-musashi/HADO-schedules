作成日：2026-07-26

## 0. 本書の位置づけ

`テスト品質_要件定義書.md` に整理した確定事項に対し、**要件定義工程として不足している項目**を洗い出したものです。

- 各項目に「現状」「なぜ必要か」「決まらないと後工程で何が起きるか」「選択肢と推奨案」「優先度」を記載しています。
- 推奨案は QA 観点からの提案であり、**決定ではありません**。承認を得てから確定してください。
- 優先度の基準
  - **高**：基本設計・実装着手前に決めないと、手戻りが発生するか、リリース可否を判断できなくなる
  - **中**：実装期間中に決めればよいが、遅れるとテスト実施フェーズが圧迫される
  - **低**：リリース後の改善で対応可能

## A. 優先度：高

### T-01 テストフレームワークの採用決定と導入

- **現状**：Jest + React Testing Library（単体）、Playwright（E2E）は **提案段階で未導入**（`要件定義残タスク.md` B-5、`技術スタック提案.md` 6章）。`Source/Next.js/hado-schedules/` にテスト基盤が存在しない。
- **なぜ必要か**：カバレッジ80%以上という要件が既に確定しているのに、**それを測る手段が決まっていない**。テストレベル4段階（単体／統合／システム／UAT）のうち、自動化する範囲と使用ツールが未定のままでは、テスト工数もスケジュールも見積もれない。
- **決まらないと後工程で何が起きるか**：
  - 実装が先行し、テストしにくい構造（DB アクセスとビジネスロジックの密結合等）で書かれてから後付けでテストを入れることになり、リファクタリングの手戻りが発生する。
  - CI にテストが組み込まれないまま実装が進み、デグレードの検知が人力レビュー頼りになる。
  - 「カバレッジ80%」が測定されないまま **未達に気づかずリリース判定に到達する**。
- **選択肢**：

  | 案 | 構成 | 長所 | 短所 |
  |---|---|---|---|
  | 案A | Jest + React Testing Library + Playwright | 提案済み。情報量が多い | Next.js 16 / React 19 環境での Jest 設定に手間がかかる |
  | 案B | Vitest + React Testing Library + Playwright | 設定が軽量、ESM/TS と相性が良い、実行が速い | 既存提案からの変更。チームの習熟が必要 |
  | 案C | Playwright のみ（E2E中心） | 導入が最小 | 単体テストの粒度で境界値・異常系を書けず、カバレッジ80%到達が困難 |

- **推奨案**：**案A または案B のいずれかを早期に確定し、単体＋統合＋E2E の3層を揃える。** 案Cは不可（カバレッジ要件を満たせない）。あわせて、単体テストと **実DBを使う統合テスト** をコマンド分離すること（統合テストは `DATABASE_URL` をテストDBに向けて実行するため）。

### T-02 カバレッジ 80% の測定定義と CI での強制

- **現状**：「コードカバレッジ80%以上を目指す」以外の定義がない。測定対象、指標（行／分岐／関数）、除外範囲、未達時の扱いが未定。
- **なぜ必要か**：測定定義がないカバレッジ目標は**合否判定に使えない**。特に分岐カバレッジを見ないと、「条件分岐の片側しか通っていないファイル」を検出できず、数値だけ高い形骸化したテストを許してしまう。
- **決まらないと後工程で何が起きるか**：
  - 自動生成コード（Prisma Client 等）や設定ファイルを含めた／除いた数値がその都度変わり、**80%達成の是非で議論が発生する**。
  - 「目指す」という表現のまま未達でリリースされ、品質保証の根拠が失われる。
- **選択肢**：
  - 指標：行カバレッジのみ ／ 行＋分岐の両方
  - 対象：`app/`・`lib/` 等のアプリコードのみ ／ 全ファイル
  - CI：閾値未達で **失敗させる** ／ 警告のみ
- **推奨案**：**行カバレッジ80%以上かつ分岐カバレッジ70%以上**を目安とし、対象は自動生成コード・設定ファイル・型定義を除外したアプリケーションコードに限定する。CI では**閾値未達をビルド失敗**にする（警告のみでは形骸化する）。数値は必ず実測を報告し、推測値を記載しない。

### T-03 UAT の実施主体・受入基準・合格判定基準（**最重要**）

- **現状**：要求機能に「テスト範囲は単体／統合／システム／UAT とする」と書かれているのみで、UAT について **誰が・何を・どう判定するか が一切定義されていない**。
- **なぜ必要か**：UAT は「発注者が受け入れる」ことを確認する工程であり、その基準が要件定義に存在しないと **プロジェクトの完了条件が存在しない**ことになる。特に本システムは以下の事情があり、UAT の実施主体が自明でない。
  - 「ユーザーサポート対応は行わない」（要求機能 運用・保守要件）
  - 「本サービスは従業者を有しません」（`個人情報保護方針.md` 4.4）
  - 拠点スタッフは各拠点1アカウントの共有運用で、実利用者は各拠点に分散している
  → **UAT に参加できる実ユーザーが誰なのかが、既存ドキュメントから読み取れない。**
- **決まらないと後工程で何が起きるか**：
  - リリース直前に「誰が受け入れ判定をするのか」が問題化し、**リリースが停止する**。
  - 合格基準がないため、不具合が残っていても「これで良い」と言える根拠も、「まだ駄目だ」と言える根拠も持てない。開発側とユーザー側で終わらない受入交渉が発生する。
  - UAT 用のテスト環境・テストデータ・拠点/コートのマスタ準備が計画から漏れ、UAT 開始が数週間遅れる。
  - 検収条件が曖昧なまま運用開始し、稼働後の不具合対応の責任範囲が定まらない。
- **決めるべき項目**（最低限これだけは必要）：

  | # | 項目 | 内容 |
  |---|---|---|
  | 1 | 実施主体 | 誰が UAT を実施するか（拠点スタッフ代表／システム管理者／協力拠点のメンバー数名 等） |
  | 2 | 実施範囲 | 全ロール（メンバー／チームリーダー／拠点スタッフ／システム管理者）をカバーするか |
  | 3 | シナリオ | 実業務に沿った受入シナリオ（例：拠点が営業日を設定 → メンバーが予約 → 別チームが参加 → 予約者が編集 → 参加者に通知が届く） |
  | 4 | 期間・体制 | 実施期間、参加人数、実施環境（本番相当か） |
  | 5 | 合格判定基準 | 例：必須シナリオ100%成功、重大度1・2の不具合ゼロ、重大度3は是正計画の合意で可 |
  | 6 | 判定者 | 最終的に合格を宣言する人（承認者） |
  | 7 | 不合格時の扱い | 再テストの範囲と回数、リリース延期の判断ライン |

- **選択肢**：

  | 案 | 実施主体 | 長所 | 短所 |
  |---|---|---|---|
  | 案A | 協力拠点のスタッフ＋メンバー数名による実地 UAT | 実運用に最も近い。運用上の齟齬を発見できる | 参加者の確保・日程調整が必要。個人情報を含まないテストデータの準備が前提（T-05） |
  | 案B | システム管理者（発注者側担当）のみが代表して実施 | 調整が容易 | メンバー／チームリーダー視点の受入漏れが発生する |
  | 案C | 開発側がユーザー役を演じる擬似 UAT | 最も容易 | **受入テストとして成立しない**（発注者の受入意思が確認できない） |

- **推奨案**：**案A を基本とし、最低でも「メンバー」「チームリーダー」「拠点スタッフ」「システム管理者」の4ロールそれぞれに実施者を1名以上割り当てる。** 合格判定基準は「必須受入シナリオの100%成功」＋「重大度1・2の未解決不具合ゼロ」＋「重大度3は是正計画に合意していること」とし、判定者を1名明記する。案Cは受入テストとして無効なので採らない。

### T-04 リリース判定基準（Go / No-Go）

- **現状**：リリース可否をどの条件で判断するかの記述がない。
- **なぜ必要か**：T-03（UAT 合格基準）と対になる、**プロジェクト全体の出荷判定条件**。テスト・セキュリティ・非機能・運用の各結果を、どこまで満たせばリリースしてよいかを事前に合意しておかないと、判定が「感覚」になる。
- **決まらないと後工程で何が起きるか**：
  - リリース直前に判断が属人化し、未解決の重大不具合を抱えたまま公開してしまう。逆に、軽微な不具合でリリースが無期限に延びる。
  - 初回リリース前必須のペネトレーションテスト（要件）が「間に合わないから次回」となり、**要件違反のままリリースされる**。
- **選択肢**：判定項目をどこまで含めるか。
  - 最小：UAT 合格のみ
  - 標準：UAT 合格 ＋ カバレッジ80% ＋ 重大度1・2ゼロ ＋ ペネトレーションテスト実施と指摘対応
  - 厳格：上記 ＋ 非機能数値（3秒／5秒／100人／5件/分）の達成 ＋ リストア訓練成功
- **推奨案**：**「標準」を必須ラインとし、非機能数値の達成を含めた「厳格」を目標とする。** 判定チェックリスト（下記）を要件定義段階で確定させる。
  1. UAT 合格（T-03 の基準）
  2. 重大度1・2の未解決不具合ゼロ
  3. カバレッジ実測値が閾値以上（T-02）
  4. ペネトレーションテスト実施済み、High 以上の指摘が是正済み
  5. 非機能数値 N-1〜N-4 の測定結果が目標内
  6. バックアップからのリストア訓練が成功している
  7. ロールバック手順が用意され、実行手順が検証されている

### T-05 テストデータの準備方針（個人情報の取り扱い）

- **現状**：テストデータをどう用意するかの記述が **どのドキュメントにもない**。
- **なぜ必要か**：本システムはメールアドレス・プロフィール画像・自己紹介・予約履歴という個人情報を扱い、`個人情報保護方針.md` で「個人情報へのアクセスは職務上必要な者に限定」「暗号化して保管」と宣言している。**本番相当データをテスト環境にコピーしてよいかは、テスト設計以前にコンプライアンス上の判断が必要**。加えて、通知テストでは**実在メールアドレスへ誤送信する事故**のリスクがある。
- **決まらないと後工程で何が起きるか**：
  - 判断のないまま開発者が本番データをテスト環境へコピーし、**個人情報保護方針違反・APPI 違反**となる。テスト環境は本番と同等のアクセス制御がないことが多く、漏えい経路になる。
  - 通知テストで実ユーザーへメールが誤送信され、信用問題になる。
  - 逆に「本番データ禁止」だけ決めてデータ生成手段を用意しないと、**負荷テスト（同時接続100人）や境界値テスト（定員10名、チーム枠、拠点20〜50件）に必要な件数のデータが用意できず、テストが実施できない**。
- **選択肢**：

  | 案 | 内容 | 長所 | 短所 |
  |---|---|---|---|
  | 案A | 完全合成データ（シードスクリプトで生成） | 個人情報リスクなし。CI で再現可能 | 本番特有のデータ分布・異常データを再現できない |
  | 案B | 本番データのマスキング／匿名化コピー | 実データ分布に近い | マスキング処理の正しさ自体の検証が必要。マスク漏れ時のリスクが大きい |
  | 案C | 本番データをそのまま利用 | 準備が不要 | **保護方針違反。採用不可** |

- **推奨案**：**案A（完全合成データ）を原則とする。** 併せて以下を規定する。
  - テストデータのメールアドレスは **送信されても実在しないドメイン**（`example.com` / `example.jp` 等の予約済みドメイン）に限定する。
  - シードスクリプトを `prisma/seed` として管理し、テストDB構築（`migrate deploy` 後）に流す。境界値テストに必要なパターン（定員ちょうど、チーム枠が埋まった予約、営業時間外、利用不可コート等）を明示的に含める。
  - 案B が必要になった場合は、マスキング仕様と実施責任者を別途定義してから実施する。
  - **本番DBをテスト用途に直接参照しない**ことをルールとして明記する。

### T-06 負荷テストの環境・条件・合否判定

- **現状**：数値目標（画面表示3秒／予約登録5秒／同時接続100人／5件/分）は確定しているが、**どの環境で・どう測って・何をもって合格とするか**が未定義（`要件定義残タスク.md` A-9 に「パフォーマンステストの条件」として未完のまま残っている）。
- **なぜ必要か**：測定条件が違えば結果は容易に2〜3倍変わる。特に本番は **単一VM にアプリとDBが同居**する構成であり、開発PCで測った数値には意味がない。
- **決まらないと後工程で何が起きるか**：
  - 開発環境で測った「3秒以内」を根拠にリリースし、本番の同居構成でDBとアプリがCPUを奪い合って**要件未達が本番で判明する**。
  - 「3秒」が平均なのか最大なのかで合否が変わり、判定できない。
  - 負荷試験環境を用意するコスト・期間が計画から漏れ、リリース直前に実施不能となる。
- **選択肢**：
  - 環境：本番同等スペックの検証VM ／ 本番環境そのものをリリース前に使用 ／ 開発環境で相対比較のみ
  - ツール：k6 ／ JMeter ／ Playwright + 並列実行 ／ Artillery
  - 判定：平均値 ／ p95 ／ p99 ／ 最大値
- **推奨案**：
  - **本番同等スペック（4vCPU / 16GB、アプリ・DB同居）の検証VMで実施する。** 開発PC実行は不可。
  - 判定は **p95 で目標値以内、エラー率0%** を合格とする（平均値のみは実態を隠すため使わない）。
  - シナリオは確定済みの2本を使う。①スイムレーン表示の同時参照（100 VU）②同一枠への同時予約（先勝ち判定を含む）。
  - ツールは **k6**（CLI 完結、CI に組み込みやすい、Windows で動作）を推奨。
  - 測定点（サーバー応答完了か画面描画完了か）を明記する。**「画面表示3秒」は描画完了で測る**ことを推奨（利用者体験に一致するため）。

### T-07 同時実行（先勝ち判定）テストの実施方法

- **現状**：「マイクロ秒まで比較して先勝ち、同時刻は登録番号が大きい利用者を優先」という要件はあるが、**この判定をどこで行うか（アプリ／DB）が設計上未確定**で、テスト方法も未定義。
- **なぜ必要か**：この要件は本システムで**最も壊れやすく、最も検出しにくい**部分。通常のテストでは再現せず、本番で二重予約として顕在化する。また「マイクロ秒まで比較」を成立させるには、**どの時刻を基準にするか**（クライアント送信時刻／サーバー受信時刻／DB のトランザクション時刻）の定義が必要だが、要件には「リクエスト送信された時刻」としか書かれておらず、**クライアント時刻を信用する実装は改ざん可能**という問題がある。
- **決まらないと後工程で何が起きるか**：
  - 時刻の基準が曖昧なまま実装され、テストでは「先に投げた方が勝つ」ように見えても、実際には**ネットワーク遅延で後発が勝つ**ケースが本番で発生する。
  - クライアント時刻を基準にした場合、**時刻を偽装して常に先勝ちできる脆弱性**になる。
  - Prisma をモックした単体テストで「先勝ちのロジック」だけを検証し、**DB の排他制約が効いているかを一度も確認しないままリリース**される。
- **選択肢**：
  - 時刻基準：クライアント送信時刻（改ざん可能）／ **サーバー受信時刻** ／ DB の `clock_timestamp()`
  - 検証方法：単体テスト（比較関数のみ）／ **テストDBに対する並行 `$transaction` 実行** ／ 負荷ツールでの同時発射
- **推奨案**：
  - 時刻基準は **サーバー受信時刻**とし、要件の「リクエスト送信された時刻」の解釈を明文化する（※要確認）。
  - 検証は **テストDBに対して `$transaction` を並行実行**する統合テストを必須とする。あわせて、負荷ツールで同一枠へ同時POSTするシナリオを実施する。
  - **「排他制約を外すとこのテストが落ちる」ことを確認**してから、そのテストを正とする（落ちるべきときに落ちるテストであることの証明）。
  - 同時刻ケース（登録番号優先）は、時刻を固定した状態での判定として検証する。

### T-08 不具合管理方法と重大度定義

- **現状**：要求機能に **運用開始後のインシデント対応SLA**（重大度1〜3、初期対応・復旧期限）は定義されているが、**開発中・テスト中に見つかった不具合の管理方法と重大度定義がない**。
- **なぜ必要か**：T-03（UAT 合格基準）と T-04（リリース判定基準）は「重大度1・2の未解決ゼロ」のように**重大度を前提に書かれる**。重大度の定義がなければ、どちらの基準も運用できない。また、運用SLAの重大度定義（サービス全体／一部機能／軽微）は稼働中システム向けであり、**テスト中の不具合分類にそのままは使えない**（例：データ不整合は「一部機能が利用不可」ではないが放置できない）。
- **決まらないと後工程で何が起きるか**：
  - 不具合の重大度が報告者の主観で決まり、**重大な予約整合性バグが「軽微」に分類されてリリースされる**。
  - 不具合が Issue・チャット・口頭に分散し、**リリース判定時点で未解決件数が数えられない**。
  - 修正の再テスト（regression）が漏れ、同じ不具合が再発する。
- **選択肢**：
  - 管理場所：GitHub Issues（ラベル運用）／ 専用のバグ管理ツール（Redmine・Backlog 等）／ スプレッドシート
  - 重大度：運用SLAの3段階を流用 ／ テスト用に独立した4段階を定義
- **推奨案**：
  - 管理は **GitHub Issues + ラベル**（`bug/severity-1` 〜 `bug/severity-4`、`found-in/unit|integration|system|uat`）。既に GitHub Actions を使う前提であり、追加コストがない。
  - テスト中の重大度は以下の **4段階**を定義することを推奨（運用SLAの重大度とは別物として、対応表を添える）。

    | 重大度 | 定義 | 例 | リリース可否 |
    |---|---|---|---|
    | S1 致命 | データ破壊・情報漏えい・全体停止 | 二重予約が成立する、他拠点のデータが見える、パスワードがログに出る | **不可** |
    | S2 重大 | 主要機能が使えない／回避策なし | 予約登録が失敗する、通知が届かない、ロックが効かない | **不可** |
    | S3 中 | 機能は使えるが不便／回避策あり | 表示崩れ、エラーメッセージが不親切 | 是正計画の合意で可 |
    | S4 軽微 | 体裁・表記 | 文言誤り | 可 |
  - **予約整合性・権限・認証に関する不具合は原則 S1 または S2 として扱う**ことを明記する（このシステムの中核リスクであるため）。

### T-09 CI におけるテストDB（PostgreSQL）の用意方法

- **現状**：テストDBは `migrate deploy` で構築すること、`db push` を使わないことは確定している。しかし **CI 上でその PostgreSQL をどう起動するかが未定**。**Docker は不採用**、CI は **GitHub Actions の Windows セルフホストランナー**（`技術スタック提案.md`）という条件がある。
- **なぜ必要か**：一般的な CI での DB 用意手段は `services:` によるコンテナ起動だが、**Windows セルフホストランナー＋Docker 不採用では使えない**。また、GitHub Actions の `services:` は Linux ランナーでしか動作しない。この制約により、**実DBを使う統合テストを CI で回せない可能性がある**。
- **決まらないと後工程で何が起きるか**：
  - 統合テスト（＝予約整合性・排他制約・先勝ち判定という**最重要領域**）が CI で自動実行されず、手元実行頼みになる。実質的にデグレードを検知できない。
  - あるいは回避策として Prisma をモックした単体テストに置き換えられ、**「二重予約を防げること」を一度も検証しないテストスイート**が出来上がる（`test-quality-reviewer` が重大度「高」とする典型パターン）。
  - セルフホストランナーは**本番VM上に置く方針**であり、テスト用DBの扱いを誤ると本番DBを指したまま `migrate reset` を実行し、**本番データを全消去する事故**が起きうる。
- **選択肢**：

  | 案 | 内容 | 長所 | 短所 |
  |---|---|---|---|
  | 案A | セルフホストランナー上に PostgreSQL テストインスタンスを常設（別ポート／別DB名） | 追加インフラ不要 | 本番VM上にテストDBが同居。**接続先誤りの事故リスクが最も高い** |
  | 案B | 単体テストは GitHub ホストの Linux ランナー、統合テストのみセルフホストで実行 | 単体テストは高速・安全 | ジョブ構成が複雑になる |
  | 案C | CI 用に小型の Linux VM を1台用意し、そこで PostgreSQL + 統合テストを実行 | 本番と分離でき安全。`services:` 相当の使い方ができる | 月数千円のコスト増 |

- **推奨案**：**案C（CI 専用の小型VM）を推奨。** 既に Zabbix Server 用の小型 Linux VM を別ホストに置く計画があるため、構成の追加負担が小さい。案Aを採る場合は最低限、
  - テストDB名を `hado_schedules_test` に固定し、**接続先が `_test` で終わらない場合はテストを即座に中断する**ガードをテスト起動スクリプトに入れる、
  - テスト実行アカウントに本番DBへの権限を与えない、
  を必須条件とする。

### T-10 要件間の矛盾により受入判定できない箇所の解消

- **現状**：既存ドキュメント間に、**テストの期待値が一意に決まらない矛盾**が複数ある。

  | # | 矛盾内容 | 出典A | 出典B |
  |---|---|---|---|
  | 1 | お気に入り拠点の上限：**10件** / **上限なし** | 要求機能 メンバー「メイン画面から拠点のお気に入りを行う（上限10件）」 | 要求機能 予約検索・フィルター機能「お気に入り上限は設けない」 |
  | 2 | 予約履歴の保持期間：**12ヶ月** / **24ヶ月** | 要求機能「紛争解決に必要な情報は12ヶ月間保持」 | `個人情報保護方針.md` 5章「予約履歴：予約日から24ヶ月」 |
  | 3 | ログ保持：監査ログ **180日** / アクセスログ **90日** | 要求機能「監査ログは180日間保持」 | `個人情報保護方針.md` 5章「アクセスログ：90日間」 |
  | 4 | 予約データの扱い：「日付が過ぎた時点で**物理削除**」 vs 「予約履歴を保持」「自分が参加した予約の履歴を確認」 | 要求機能 データ保持・削除ポリシー | 要求機能 メンバーの操作／`個人情報保護方針.md` |

- **なぜ必要か**：これらは **すべてテストで合否を判定する項目**（境界値：11件目のお気に入りは登録できるか／削除バッチが何日後に何を消すか）。期待値が二通りある状態では、テストケースを書けないし、書いてもどちらかが誤りになる。
- **決まらないと後工程で何が起きるか**：
  - 実装者が片方の記述だけを見て実装し、テスト担当がもう片方を見てテストを書き、**「バグ」として無限に往復する**。
  - #4 が未解決のまま実装されると、**予約日翌日に履歴が消えてマイページの「過去の予約履歴」が常に空**という、リリース後に発覚する重大な仕様矛盾になる。個人情報保護方針との不整合はコンプライアンス問題にも波及する。
- **推奨案**：**要件定義工程の残作業として、上記4件を「どちらが正か」明示的に決定し、両ドキュメントを同時に更新する。** QA としての推奨は以下（※いずれも要確認）。
  - #1：上限を設けない（機能上の制約がなく、10件は下書き時の名残と推測される）
  - #2・#3：**個人情報保護方針側を要求機能に合わせる**（対外公表文書が実装より長い保持期間を約束すると、法的リスクが大きい）
  - #4：「予約データは日付経過後に削除するが、参加履歴として最低限の情報を保持期間まで残す」形に整理する
  - 決定後、`テスト品質_要件定義書.md` の該当観点を追加すること。

### T-11 未確定ビジネスルールに起因するテスト設計不能領域

- **現状**：`要件定義残タスク.md` A-2 で未決とされているビジネスルールが、そのままテスト設計不能領域になっている。
  - 予約のキャンセル可能期限・キャンセル料
  - 参加者の追加／削除可能期間
  - 同一ユーザーの同一時間帯における重複予約の可否
  - チーム枠ルールの厳密定義（チーム数上限、チーム参加の優先順序）
  - 拠点スタッフの「利用不可設定」が**既存予約**に与える副作用
- **なぜ必要か**：これらはすべて**予約整合性（最優先テスト領域）の中核**。特に「利用不可設定と既存予約の関係」は、既存予約を強制キャンセルするのか／設定を拒否するのか／併存させるのかで、**テストケースも通知要件（誰に通知するか）も全く変わる**。
- **決まらないと後工程で何が起きるか**：
  - 5.1 の重点観点が埋まらないまま実装に入り、**実装者の判断で暗黙の仕様が決まる**。テストは「実装をなぞるテスト」になり、仕様検証にならない（`qa-test-engineer` の設計原則1に反する）。
  - 「利用不可設定で既存予約が黙って消えた」等、**運用開始後に利用者からのクレームで初めて仕様の穴が判明**する。
- **推奨案**：**「利用不可設定と既存予約の関係」と「同一ユーザーの重複予約可否」の2件を最優先で確定する。** 前者は既存予約への通知要否に直結し、後者は予約整合性テストの境界条件そのものであるため。確定次第、本書 5.1 に観点を追加する。

### T-12 アクセシビリティ（WCAG 2.1 AA）検証の手段と合否基準

- **現状**：「アクセシビリティは WCAG 2.1 AA に準拠する」という要件のみ。**検証手段・対象画面・合否基準が未定義**。
- **なぜ必要か**：WCAG 2.1 AA は達成基準が約50項目あり、そのうち自動ツールで検出できるのは一般に3〜4割程度。「準拠する」とだけ書いて手段を決めないと、**実質的に検証されないまま「準拠」と主張する**ことになる。本システムはスイムレーン（横スクロールする2次元グリッド）という**キーボード操作・スクリーンリーダー対応が難しいUI**を中核に持つため、リスクが高い。
- **決まらないと後工程で何が起きるか**：
  - スイムレーンが実装完了してから「キーボードで予約ブロックに到達できない」と判明し、**UIコンポーネントの作り直し**になる（コンポーネント優先実装順の1位＝影響が最大）。
  - コントラスト比不足が Tailwind のカラー選定段階で作り込まれ、全画面の配色見直しが必要になる。
- **選択肢**：
  - 自動：axe-core（`@axe-core/playwright` で E2E に組み込む）／ Lighthouse
  - 手動：キーボードのみ操作でのシナリオ完走、スクリーンリーダー（NVDA）確認、コントラスト比測定
  - 対象範囲：全画面 ／ 主要画面（メイン、予約作成、予約詳細、マイページ、管理画面）のみ
- **推奨案**：**自動＋手動の併用**を必須とする。
  - 自動：`@axe-core/playwright` を E2E に組み込み、**主要画面で critical / serious 違反ゼロ**を合格条件にする（T-01 で Playwright を採用する前提）。
  - 手動：**マウスを使わずにキーボードのみで「拠点選択 → 日付選択 → 予約ブロック選択 → 予約作成 → 送信」を完走できること**を必須の受入項目にする。スイムレーンのグリッド操作パターン（矢印キー移動・Tab でのグループ移動）を設計段階で決めておく。
  - コントラスト比は Tailwind のカラーパレット確定時に一括検証する（後戻りを防ぐため設計工程で実施）。

### T-13 対応ブラウザ検証の手段（特に Safari）

- **現状**：対応ブラウザは Chrome / Firefox / Safari / Edge の最新版。**検証手段が未定義**。
- **なぜ必要か**：開発・本番とも **Windows 環境**であり、**Safari の実機検証手段がない**（Safari は macOS / iOS のみ）。「最新版」という定義も、いつ時点の最新かで判定が変わる。
- **決まらないと後工程で何が起きるか**：Safari だけ日付入力やスイムレーンのスクロール挙動が異なり、**リリース後に iPhone ユーザーから報告されて発覚する**。モバイル利用が想定される予約システムでは影響が大きい。
- **選択肢**：Playwright の WebKit エンジンで代替 ／ クラウド実機サービス（BrowserStack 等）／ 実機 Mac・iPhone を用意 ／ Safari を対応外にする
- **推奨案**：**Playwright の WebKit を CI での自動検証に使い、リリース前に実機 iPhone Safari で主要シナリオを1周する**併用案。WebKit エンジンは Safari と同一ではないため、自動検証だけを根拠に「Safari 対応済み」とはしない。「最新版」の定義は「**リリース時点の最新安定版および1つ前のメジャーバージョン**」とすることを推奨。

### T-14 メール通知テストの実施方法

- **現状**：通知要件（M-01〜M-09）は確定しているが、**テストでメールをどう検証するかが未定**。メール送信プロバイダも未決（`要件定義残タスク.md` B-2：Amazon SES / SendGrid）。
- **なぜ必要か**：通知はこのシステムの主要機能の一つであり、特に **「送信失敗時に3回リトライしログに記録する」** は失敗を意図的に起こさないと検証できない。実プロバイダに送るテストは、レート制限・コスト・誤送信リスクを伴う。
- **決まらないと後工程で何が起きるか**：
  - 通知テストが「送信関数が呼ばれたこと」のモック検証だけになり、**本文・宛先・全参加者への配信漏れが検証されない**。M-01/M-02 の「全員に通知」が担保できない。
  - リトライ処理が一度もテストされず、本番で無限リトライやリトライなしになる。
- **選択肢**：SMTP キャッチサーバ（MailHog / Mailpit）／ プロバイダのサンドボックス機能（SES サンドボックス）／ アプリ層のトランスポートをモックに差し替え
- **推奨案**：**送信基盤を抽象化し、テスト環境では SMTP キャッチサーバ（Mailpit 等）に向ける。** これにより宛先・件名・本文・配信件数を実際に検証できる。リトライは**キャッチサーバを意図的に停止**して失敗を起こし、3回リトライとログ記録を検証する。プロバイダ決定（B-2）と同時に、テスト時の送信先切り替え方法を仕様に含めること。

### T-15 SLA 99.9% と単一VM構成の乖離に対する受入方針

- **現状**：要件は SLA 99.9%（非計画停止 月約42分）。一方 `技術スタック提案.md` 5章は「単一VM構成の実効可用性は 99.5% 程度で、**99.9% は契約上保証できない**」と明記。RTO は数時間、RPO は最大24時間。**RTO/RPO の目標値は未決**。
- **なぜ必要か**：テスト・品質の観点では、**達成不能と分かっている要件を「合格」と判定することはできない**。リリース判定基準（T-04）に SLA を含めるかどうかが決められない。
- **決まらないと後工程で何が起きるか**：
  - 稼働後に停止が発生し、「SLA 99.9% と要件に書いてある」という指摘に対して、**構成上不可能だったという合意がないため責任問題になる**。
  - RTO/RPO 目標がないため、**リストア訓練の合否基準が作れない**（何分で復旧できれば合格か判定できない）。
- **選択肢**：要件側を実態に合わせて 99.5% に改める ／ 案2（マネージドPostgreSQL）へ前倒し移行する ／ 99.9% を「努力目標」と明記し契約保証から外す
- **推奨案**：**要件を実態に合わせて改訂するか、努力目標である旨を明記する。** そのうえで RTO/RPO 目標値を確定し（`要件定義残タスク.md` A-8）、それを合否基準としたリストア訓練を運用テスト（T-16）に含める。

### T-16 運用テスト（バックアップ／リストア／メンテナンス）の範囲

- **現状**：バックアップ（日次03:00、30日保持）、メンテナンス枠（週1回 0:00〜5:00）、監視閾値、ログローテーション（5世代）は要件として確定しているが、**これらを検証する工程が4つのテストレベルのどこにも位置づけられていない**。
- **なぜ必要か**：単一VM構成では**バックアップとリストアが唯一の復旧手段**。「取得できている」ことと「戻せる」ことは別問題であり、リストアを一度も試さないまま運用開始するのが最も危険。
- **決まらないと後工程で何が起きるか**：
  - 障害発生時に初めてリストアを試し、**手順の不備やダンプの破損が判明する**。
  - Windows Update がメンテナンス枠外に再起動を起こす設定漏れが検証されず、コート利用時間中に停止する。
  - ログローテーションが Windows で実装漏れ（`技術スタック提案.md` に「Windows に logrotate は存在しない」と警告あり）になり、**ディスク枯渇でサービス停止**する。
- **推奨案**：**システムテストに「運用テスト」を明示的に含める。** 最低限の項目：
  1. `pg_dump` の自動実行とオブジェクトストレージへの退避が成功する
  2. **取得したバックアップから復旧できる**（RTO/RPO 目標に対する実測を記録）
  3. メンテナンス枠内でのデプロイ手順とロールバック手順が完走する
  4. Windows Update が枠外に再起動を起こさない設定が有効
  5. ログが月〜日で5世代ローテーションされ、監査ログが180日残る
  6. 監視アラート（CPU80%／メモリ85%／サービス停止／証明書期限）が実際に発報する
  7. TLS 証明書の自動更新（win-acme）が動作し、失敗時に検知できる

### T-17 セキュリティテストの実施計画（時期・委託先・再テスト）

- **現状**：「初回リリース前にペネトレーションテストを実施」「以降 SAST/DAST で継続監視」は確定。しかし **実施時期・委託先・費用・指摘への対応期限・再テストの要否が未定**（`要件定義残タスク.md` B-4 で未決）。
- **なぜ必要か**：ペネトレーションテストは外部委託の場合、**見積り・契約・日程調整に数週間から数ヶ月かかる**。リリース直前に着手しても間に合わない。
- **決まらないと後工程で何が起きるか**：**要件で必須とされているペネトレーションテストを実施できないままリリースする**か、リリースが大幅に遅延する。指摘への対応期限が未定だと、High 指摘を抱えたままリリース判定に入ってしまう。
- **推奨案**：
  - 実施時期を **UAT と並行、リリース予定日の6〜8週前**に設定し、再テストの期間を確保する。
  - スコープに **本システム固有のリスク**を明示する：認証・セッション（二重ログイン後勝ち、ロック機構）、**IDOR（他拠点・他人の予約へのアクセス）**、権限昇格、予約の競合状態。
  - 指摘対応基準：**Critical / High は是正しリリース判定の必須条件、Medium は是正計画の合意で可**。
  - SAST は CI に組み込む（`要件定義残タスク.md` B-4 の候補：Dependabot / Snyk / Semgrep）。最低限 **Dependabot（無料、GitHub 標準）は初期から有効化**することを推奨。

### T-18 要件とテストケースのトレーサビリティ

- **現状**：要件に ID が振られておらず、テストケースとの対応付けの仕組みがない。
- **なぜ必要か**：カバレッジ80%は**コード**のカバレッジであって、**要件のカバレッジではない**。コードカバレッジ80%を達成しても、要件のうちどれがテストされていないかは分からない。UAT やリリース判定で「全要件が検証済み」と言うには要件側の網羅率が必要。
- **決まらないと後工程で何が起きるか**：要件変更時に**影響するテストケースを特定できず**、修正漏れが発生する。「この要件はテストされているか」という問いに答えられない。
- **推奨案**：`テスト品質_要件定義書.md` で付与した観点ID（R-xx / P-xx / A-xx / M-xx / U-xx / L-xx / N-x）を**テストコードのテスト名に含める**（例：`[R-07] 同一枠への同時予約でマイクロ秒の先着が優先される`）。追加ツールなしで grep によるトレースが可能になる。要求機能側にも要件IDを振ることを推奨。

### T-19 回帰テストの範囲と実行タイミング

- **現状**：CI でいつ何を実行するかが未定義。
- **なぜ必要か**：単体テストは高速だが、実DBを使う統合テストや E2E は遅い。全部を毎PRで回すと開発が止まり、回さないとデグレードを見逃す。
- **決まらないと後工程で何が起きるか**：CI が遅すぎて**テストをスキップする運用が常態化**する、あるいは重い E2E が PR ごとに回って開発速度が落ちる。
- **推奨案**：
  - **PR ごと**：lint / 型チェック / build / 単体テスト（現在 `技術スタック提案.md` 7章で計画されている最小CIに単体テストを追加）
  - **develop へのマージ時**：＋ 実DBを使う統合テスト（予約整合性・権限・認証）
  - **リリース前 / 日次**：＋ E2E 全シナリオ、アクセシビリティ自動チェック、負荷テスト
  - **予約整合性に関わるコードの変更時は、統合テストを必須**とする（パスフィルタで強制）

### T-20 テスト実施体制・スケジュール・環境の確保

- **現状**：誰がテストを実施するか、いつ実施するか、どの環境を使うかが未定義。「本サービスは従業者を有しません」（`個人情報保護方針.md`）という記述と、テスト工程の実施体制の整合が取れていない。
- **なぜ必要か**：T-03（UAT）、T-06（負荷テスト用VM）、T-09（CI用DB）、T-17（ペネトレーションテスト委託）はいずれも**人・環境・費用の事前確保が必要**。
- **決まらないと後工程で何が起きるか**：実装完了後に「テスト環境がない」「実施者がいない」ことが判明し、テスト工程が丸ごと圧縮される。**最初に削られるのは非機能テストと UAT**で、結果として最もリスクの高い領域が未検証のままリリースされる。
- **推奨案**：要件定義完了時点で、以下を確保計画として明記する。
  - 環境：開発 / テスト（統合・E2E用、DB分離）/ 検証（本番同等スペック、負荷・UAT用）/ 本番 の**4環境**、または最低でもテスト環境と検証環境の兼用を明示
  - 費用：負荷検証VM、CI用VM、ペネトレーションテスト委託費
  - 体制：UAT 参加者（4ロール分）、判定者

## C. 優先度：低

### T-21 日時・タイムゾーン依存テストの方針

- **現状**：JST 固定という要件はあるが、テストで日時をどう扱うかの方針がない。
- **なぜ必要か**：予約システムは日時が中核であり、「今日」「明日」に依存したテストは**時間の経過で落ちる**。CI が深夜に走ると日付が変わって落ちる、といった不安定テストの原因になる。
- **決まらないと後工程で何が起きるか**：時々落ちる不安定なテストが蓄積し、**「落ちても気にしない」文化**が生まれてテストスイート全体が信用を失う。
- **推奨案**：時刻を固定できる仕組み（フェイクタイマー、または現在時刻をアプリ層で1箇所に集約して差し替え可能にする）を**実装方針として先に決める**。テストDB の `Timestamptz` と JST の変換は、境界（0:00 / 22:00 / 日付跨ぎ）で必ず検証する。

### T-22 テスト成果物の定義と保管

- **現状**：テスト計画書・テスト仕様書・テスト結果報告書を作るかどうかが未定義。
- **なぜ必要か**：UAT の合格判定（T-03）とリリース判定（T-04）には、判断の根拠となる記録が必要。特にペネトレーションテスト結果と非機能テスト結果は、後から参照する場面が生じる。
- **決まらないと後工程で何が起きるか**：判定の根拠が残らず、稼働後の障害時に「リリース前に何を確認したか」を再構成できない。
- **推奨案**：重量級のドキュメントは不要。**①テスト計画（本書の確定版）②UAT シナリオと結果 ③非機能テスト結果（実測値）④ペネトレーションテスト報告と是正記録 ⑤リリース判定チェックリスト** の5点に絞り、`Docs/hado-schedule/` 配下で Git 管理する。
