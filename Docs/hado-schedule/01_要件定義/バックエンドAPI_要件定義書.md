# バックエンドAPI 要件定義書

作成日：2026-07-26
担当領域：バックエンド・API（backend-api-developer）

## 0. 本書の位置づけ

本書は、既存の要件定義ドキュメントから**バックエンド／APIが満たすべき要件として既に決まっている内容**を抽出・整理したものです。新しい仕様の創作は行いません。

- 一次情報：`アプリケーション要求機能.md`
- 技術前提：`技術スタック提案.md`
- 個人情報の扱い：`個人情報保護方針.md`
- 未決事項：`バックエンドAPI_要件定義残タスク.md`（本書と対になる文書）

### 記法

| 記法 | 意味 |
|---|---|
| （出典なし・通常記述） | 既存ドキュメントに明記されている確定事項 |
| **※補完** | 既存ドキュメントの記述からサーバー実装上の解釈として補った内容。**確定事項ではない**ため、承認を得るまでは仮とする |
| **※未決** | 決まっていないため本書では確定させない。詳細は残タスク文書を参照 |

### 対象範囲

**対象**：Next.js の Route Handlers として実装するサーバーサイドの業務ルール、通知処理、性能、ログ・監査ログ、権限判定。

**対象外**：

- DBスキーマの詳細設計（テーブル定義、インデックス、排他制約SQL）→ database-architect の領域。本書は「APIから見て何が保証されている必要があるか」までにとどめる
- 画面のレイアウト・遷移 → ui-ux-designer の領域
- 認証方式そのものの選定（NextAuth 採用可否等）→ auth-security-engineer の領域。本書はAPIから見た要求のみ記載
- **実装しない機能のAPI**（第9章）

## 1. 技術前提（確定事項）

`技術スタック提案.md` で確定済みの前提のうち、API実装に影響するものを再掲します。

| 項目 | 内容 | APIへの影響 |
|---|---|---|
| フレームワーク | Next.js 16.2.6（App Router） | API は Route Handlers で実装する |
| 言語 | TypeScript（strict） | |
| DB | PostgreSQL 17（セルフホスト）、`btree_gist` 拡張あり | 予約の時間帯重複防止に排他制約を使う前提でコードを書く |
| ORM | Prisma | マイグレーションSQLに手書きされた排他制約・部分一意インデックスを前提とする |
| 本番構成 | Windows Server 単一VM（アプリ・DB同居） | 外部キュー・マネージドサービスを前提にした設計にしない。バッチはタスクスケジューラ起動 |
| キャッシュ | Redis 不採用 | セッション・非同期ジョブの保持先は PostgreSQL を前提とする |
| リバースプロキシ | IIS（URL Rewrite + ARR） | クライアントIPは転送ヘッダ経由になる（ログ記録時に留意） |
| タイムゾーン | JST 固定 | 日時は `timestamptz` で保持し、境界の扱いを1箇所に集約する |

> Next.js 16 の Route Handlers / middleware / caching の仕様は学習データと差異がある可能性があります。**実装着手時に `node_modules/next/dist/docs/` を確認すること。** 本書執筆時点では `node_modules` が未取得のため、バージョン固有のAPI仕様には踏み込んでいません。

## 2. リソースと権限の前提

### 2.1 対象リソース

| リソース | 概要 |
|---|---|
| 拠点（Venue） | 複数存在。営業日・営業時間を持つ。新規登録はシステム管理者 |
| コート（Court） | 1拠点に複数存在しうる。利用可能時間・利用可能種別（HADO / HADO WORLD）・利用可能設備を持つ |
| 予約（Reservation） | 個人予約／チーム予約／イベント予約／店舗予約の4種別 |
| 参加登録（Participation） | フリー募集の予約に対する個人参加、および他チームのチーム枠への参加 |
| チーム（Team） | リーダー1名＋メンバー9名まで |
| リーグ戦チーム（LeagueTeam） | 通常チームと別編成。システム管理者の承認が必要 |
| 利用者（User） | メンバー／チームリーダー／拠点スタッフ／システム管理者 |
| 監査ログ（AuditLog） | 操作・データ変更の記録 |

※ APIのエンドポイント一覧は**※未決**（残タスク BE-01）。上記はリソースの粒度のみを示す。

### 2.2 権限（ロール）

| ロール | サーバー側で担保すべき主な制約 |
|---|---|
| メンバー | 自分のプロフィール・自分が登録した予約のみ編集／削除可。所属チーム申請は1つのみ、リーグ戦所属チーム申請も1つのみ |
| チームリーダー | メンバーの権限に加え、チーム所属申請／リーグ戦所属チーム申請の承認、チームとしての予約登録・編集・削除、他チームの空きチーム枠への参加申請、チーム情報の編集 |
| 拠点スタッフ | **自拠点のみ**管理・閲覧可。コートの追加／削除・編集、設備編集、営業日／営業時間設定、自拠点コートの予約の登録／削除／編集、イベント予約。**各拠点1アカウントの共有運用** |
| システム管理者 | 全リソースの登録／編集／削除。全予約の編集／削除。チーム／リーグ戦チーム登録申請の承認。拠点の追加／削除 |

**サーバー実装上の原則**

- 権限チェックは各ハンドラの入口で行う。クライアントが申告したロール・ユーザーID・拠点IDを信用しない。
- リソースの**所属関係**まで検証する（そのコートはその拠点のものか、その予約は自拠点のものか、その参加登録は自分のものか）。
- 拠点スタッフのアクセスは常に「自拠点スコープ」で絞り込む。ID直指定による他拠点リソースへの到達（IDOR）を許さない。

## 3. 予約に関する業務ルール（サーバーサイドで担保する）

本システムで最も壊れやすい領域です。以下はすべて**サーバー側で判定**し、クライアントの計算結果を信用しません。

### 3.1 定員とチーム枠は独立して判定する

- 各予約（個人／チーム／イベント／店舗）は**定員を必須**で設定する。
- 各予約に**チーム枠**を設定でき、チーム数の上限を指定できる。
- チーム枠と定員は同時に設定でき、その場合**定員はチーム枠を除いた人数**を設定する。
- 例：チーム枠2枠・定員9名 → チーム参加は2チームまで、個人参加は9名まで。
- **定員に達した場合は予約（参加登録）不可。**

**サーバー実装上の要求**

- チーム枠の消費数と個人参加者数を**1つの数値に合算しない**。別々のカウンタとして判定する。
- 境界判定は「定員ちょうどは受け入れ可、超過は不可」（`<` と `<=` の取り違えを起こさない）。**※補完**：要求機能.md は「定員となった場合は予約不可」と記載しており、定員ちょうどの登録は成立し、その次の登録から不可と解釈する。
- 判定は後述の 3.2 と同一トランザクション内で行う。

### 3.2 同時実行時の競合制御（先勝ち判定）

要件（`アプリケーション要求機能.md` エラーハンドリング）：

- 同時にアクセスが発生した場合、**リクエスト送信された時刻をマイクロ秒まで比較し先勝ち**とする。
- **全く同時刻の場合、利用者の登録番号が大きい利用者を優先**する。

**サーバー実装上の要求**

- アプリ側の時刻比較のみに依存せず、**DBの制約とロックで二重確定を物理的に防ぐ**。「存在チェック → INSERT」だけの実装はレースコンディションで破れる。
- Prisma では**インタラクティブトランザクション**（コールバック形式）を用い、**分離レベルを明示**する。既定の Read Committed では定員チェックと INSERT の間に割り込まれる。
- 行ロックが必要な箇所は `$queryRaw` のタグ付きテンプレートで `SELECT ... FOR UPDATE` を発行する（Prisma Client API 単体では行ロックを取得できない）。
- 最終防衛線は**排他制約／一意制約**。同一コート・同一時間帯の重複予約は `EXCLUDE USING gist` による排他制約で防ぐ前提とし、**制約違反（`P2002` 等）を捕捉して適切なエラーコードに変換する**実装を必ず入れる。未捕捉の500を返さない。
- 予約確定と参加登録は**アトミック**に行う。通知処理をトランザクション内に入れず、メール送信失敗で予約本体をロールバックしない（第5章）。

> **注意**：「リクエスト送信された時刻」の取得元（クライアント申告時刻はなりすまし可能・時計ずれあり）が定義されていません。**※未決**（残タスク BE-03）。

### 3.3 営業時間・利用可能時間の検証

- スイムレーンの表示範囲は **10:00〜22:00**、**30分刻み**。
- 拠点は営業日を設定し、営業日内に営業時間を設定する。
- コートは拠点の営業時間内で利用可能時間を設定する。
- 「拠点の営業時間はデフォルトから変更できるが、**10:00〜22:00 から短縮することはできない**」。

**サーバー実装上の要求**

- 予約時間が「コートの利用可能時間」および「拠点の営業時間」の**内側**であることを検証する。
- 予約対象日が拠点の**営業日**であることを検証する。
- 開始 < 終了、30分刻みへの整合、過去日時でないことを検証する。**※補完**（要求機能.md に明記はないが、スイムレーンが30分刻みであることから導かれる最低限の入力検証）。
- 日時は JST 固定。境界（22:00 ちょうどの終了は可、22:30 開始は不可）の扱いを1箇所に集約する。**※補完**。

### 3.4 編集・削除の権限ルール

- 予約者は予約登録後、予約内容を**編集**できる。
- **予約の編集・削除は予約者のみ**が可能。**ただしシステム管理者は全予約の編集・削除が可能**。
- 拠点スタッフは**自拠点のコートの予約**を登録／削除／編集できる。
- チームリーダーは**チームとして登録した予約**の編集／削除ができる。

**サーバー実装上の要求**

- 上記4つの判定を各ハンドラ入口で一貫して適用する。予約IDの所有者判定をクライアント申告に委ねない。
- 拠点スタッフの編集・削除は自拠点スコープに限定する。

> **矛盾あり**：「予約の編集・削除は予約者のみ（管理者は全予約可）」と、拠点スタッフの「コートの予約状況を登録／削除／編集する」が衝突しています。拠点スタッフが**利用者の登録した予約**まで操作できるのかが確定していません。→ 残タスク BE-08（優先度：高）。

### 3.5 予約種別ごとの追加条件

| 種別 | 登録者 | 特記事項 |
|---|---|---|
| 個人予約 | メンバー以上 | フリー募集とした場合、他利用者が参加登録できる |
| チーム予約 | チームリーダー | 他チームが空きチーム枠へ参加申請できる |
| イベント予約 | 拠点スタッフ | 拠点主催の試合・トーナメント等。**複数コートを同時予約することも可能**。リーグ戦チームを登録できる |
| 店舗予約 | 拠点スタッフ | 営業・運用目的（メンテナンス、施設点検）。**コートが利用不可な場合、拠点スタッフが予約を行うことで利用不可状態を設定する** |

**サーバー実装上の要求**

- イベント予約の複数コート同時予約は、**全コート分の確保が成功した場合のみ確定**する（部分成功を残さない）。**※補完**：要求機能.md に成否の粒度の記載がないため、予約整合性の観点から全件成功／全件失敗を仮置きする。→ 残タスク BE-10 で確定させる。

### 3.6 キャンセルポリシー

- 各予約には、予約登録を行った利用者が**キャンセルポリシーを記載**できる（自由記述）。
- キャンセルポリシーが編集された場合も「予約情報の編集」として参加者全員への通知対象となる。**※補完**。

## 4. 認証・セッションに関するAPI要件

`アプリケーション要求機能.md`「ユーザー認証・登録機能」「セキュリティ」より、APIが満たすべき事項。

| 要件 | サーバー実装上の要求 |
|---|---|
| メールアドレスによるユーザー登録。複数アカウント登録は可能 | メールアドレスの一意制約の要否は DB 設計と整合させる（「複数アカウント登録可」の解釈が要確認 → 残タスク BE-06） |
| **API通信は認証トークンによる認証を行う** | 全エンドポイントで認証を検証する。未認証で到達できるエンドポイントを作らない（ログイン・パスワードリセット等の明示的な例外を除く） |
| **2重ログイン不可・後勝ち**（既存接続は強制切断） | ステートレスJWT単独では旧トークンを無効化できないため、**サーバー側セッション（PostgreSQL）が必須**（技術スタック提案.md 第6章）。切断された側のリクエストに対する応答仕様は**※未決** |
| セッションは Secure / HttpOnly Cookie | |
| セッションタイムアウトは**30分間アクティビティなし**で自動ログアウト | 最終アクティビティ時刻をサーバー側で管理する |
| **ログイン失敗3回連続でアカウントを30分間ロック** | 失敗回数・ロック解除時刻をサーバー側で管理する |
| パスワード要件：最小8文字、大文字・小文字・数字を含む | **サーバー側でも検証する**（クライアント検証のみにしない） |
| パスワードはハッシング・ソルト処理で保管 | 平文・可逆暗号で保持しない |
| 初回／パスワード再設定時はランダム文字列をシステムがメール通知 | パスワードリセットトークンの保持期間は24時間（個人情報保護方針 第5章） |
| 多段階認証は行わない | MFA 関連APIを作らない |
| 通信は TLS 1.2 以上 | |

## 5. 通知処理の要件

### 5.1 通知イベント一覧（要求機能.md に明記されているもののみ）

| # | 契機 | 通知先 | チャネル | 出典 |
|---|---|---|---|---|
| N-1 | 予約情報が**編集**された | その予約に参加登録しているすべての利用者 | メール＋アプリ内 | キャンセルポリシー管理・通知機能 |
| N-2 | 予約者が予約を**削除**した | 参加登録者全員 | メール＋アプリ内 **※補完**（要求機能.md は「通知される」とのみ記載しチャネル未明記。N-1 と同等と解釈） | 予約 |
| N-3 | メンバーからチーム／リーグ戦チーム**登録申請**があった | チームリーダー | メール＋アプリ内 | 同上 |
| N-4 | メンバーからチーム／リーグ戦チーム**登録申請**があった | システム管理者 | メール＋アプリ内 | 同上 |
| N-5 | チームリーダーが登録申請を**承認／却下**した | 申請したメンバー | メール＋アプリ内 | 同上 |
| N-6 | システム管理者が登録申請を**承認／却下**した | 申請したメンバー | メール＋アプリ内 | 同上 |
| N-7 | システムメンテナンスを行う | すべてのユーザー | メール＋アプリ内 | 同上 |

> **上記以外の通知は実装しない。**「記載されていない通知機能」は実装しない機能に含まれる（要求機能.md「実装しない機能」）。予約作成時の予約者本人への確認通知、参加登録時の予約者への通知などは**要件に記載がないため実装対象外**。必要であれば要件追加の判断を仰ぐ。

### 5.2 送信失敗時の扱い

- **メール配信に失敗した場合は、システムログに記録し、3回まで自動リトライを行う。**

**サーバー実装上の要求**

- 通知処理は予約処理本体のトランザクション**外**に切り出す（非同期化）。メール送信失敗で予約や参加登録をロールバックしない。
- 3回のリトライ後も失敗した場合、**システムログに記録**する。記録内容に個人情報（宛先メールアドレス本文等）を含めない（第7章）。
- Redis 不採用・単一VM構成のため、非同期処理の待ち行列は**PostgreSQL 上に持つ**ことを前提とする（技術スタック提案.md 第5章「セッション・キューをサーバーのメモリ上に持たない」）。
- 具体的な非同期処理方式・リトライ間隔・リトライの単位（宛先ごとか通知イベントごとか）は**※未決**（残タスク BE-07）。メール送信プロバイダの選定そのものは `要件定義残タスク.md` B-2 で管理。

## 6. 性能要件

`アプリケーション要求機能.md`「パフォーマンス要件」より。

| 項目 | 目標値 | APIへの含意 |
|---|---|---|
| 画面表示の応答時間 | **3秒以内** | 画面が依存するAPIの応答時間はこの内側に収める必要がある。スイムレーン表示のAPIが該当 |
| **予約登録** | **5秒以内に完了** | トランザクション＋ロック取得を含めて5秒以内。通知送信の完了を待たない（非同期化の根拠） |
| 同時接続ユーザー | **100人** | Prisma の `connection_limit` を PostgreSQL の `max_connections` に整合させ、枯渇させない |
| スループット | **予約登録 5件/1分** | ピーク時の排他制約競合を許容できること |
| 監視 | 外形監視でログイン／スイムレーン表示／予約APIの応答時間を計測（技術スタック提案.md 4.3） | 上記しきい値を監視項目とする |

**サーバー実装上の要求**

- **N+1 クエリを作らない。** スイムレーン表示でコート×予約を個別取得しない。Prisma の `include` / `select` で関連をまとめて取得し、ループ内で `findUnique` を呼ばない。
- `select` で必要なカラムのみ取得する（性能と個人情報漏えい防止の両面）。
- Prisma Client はシングルトンにする（開発時のホットリロードによる接続枯渇を防ぐ）。
- トランザクションを不必要に長くしない（ロック競合を招く）。
- 日時カラムに関数を適用した絞り込みなど、インデックスが効かないクエリを避ける。
- スケーラビリティ想定：初期500ユーザー／20拠点 → 3年後2,000ユーザー／50拠点。

## 7. ログ・監査ログの要件

### 7.1 記録対象

- **利用者のログイン状態**と**すべてのデータベース操作に関する状態**をログファイルに記録する（要求機能.md エラーハンドリング）。
- **拠点スタッフの操作は全てログに記録される**（誰が操作したかはログイン時刻から推測）。拠点スタッフは各拠点1アカウントの共有運用のため、**操作をログイン時刻と紐づけて追跡可能**にする必要がある。
- ログレベルは **INFO 以上**を記録する。

### 7.2 保持・ローテーション

| 対象 | 保持 | 出典 |
|---|---|---|
| 監査ログ（ユーザーの操作・データ変更） | **180日** | 要求機能.md データベース要件 |
| ログファイル | 月曜日〜日曜日で記録し、**5世代**まで世代管理 | 要求機能.md データ保持・削除ポリシー |
| アクセスログ | 90日 | 個人情報保護方針 第5章（※要求機能.md の監査ログ180日との関係が未整理 → 残タスク BE-16） |

- Windows に logrotate は存在しないため、ローテーションはアプリ側（pino / winston 等）またはタスクスケジューラのスクリプトで明示的に実装する（技術スタック提案.md 4.4）。

### 7.3 ログに出力してはならないもの

- **個人情報・パスワード・トークンをログに出力しない。**
- Prisma のクエリログをそのまま出すとパラメータに個人情報が載るため、**本番のログレベル設定に注意する**。
- 例外のスタックトレースをクライアントに返さない。

### 7.4 監査ログの記録項目

**※未決**（残タスク BE-16）。「誰が・いつ・何を・どのリソースに対して・結果どうなったか」を最低限含める必要があるが、項目定義は未策定。

## 8. データ保持・削除に関わるAPI／バッチ要件

`アプリケーション要求機能.md`「データ保持・削除ポリシー」より。

| ルール | サーバー実装上の要求 |
|---|---|
| 予約データは日付が過ぎた時点で**物理削除**する | 定期バッチ（タスクスケジューラ起動）で削除する。API は削除済みデータを参照しない前提で設計する |
| 退会ユーザーの情報は退会時点で**物理削除**する | 退会APIと、関連レコードの整合（外部キー）を設計と整合させる |
| 拠点の情報は削除時点で**物理削除**する | 拠点配下のコート・予約の扱いを設計と整合させる |
| ただし紛争解決に必要な情報（予約登録者、参加者等）は**12ヶ月保持** | 物理削除の対象外とする退避先が必要（残タスク BE-09、および `要件定義残タスク.md` B-6 と関連） |

> **矛盾あり**：メンバーの操作に「自分が参加した予約の履歴を確認」があり、個人情報保護方針では予約履歴を24ヶ月保持としています。一方で要求機能.md は「予約データは日付が過ぎた時点で物理削除」としており、**履歴参照APIが成立しません**。→ 残タスク BE-09（優先度：高）。

## 9. 実装しないもの（APIを作らない）

以下の機能のAPIは**作りません**（要求機能.md「実装しない機能」）。

- チェックイン機能
- 決済機能
- レビュー機能
- レポート機能
- 利用分析機能
- キャンセル待ち機能
- **記載されていない通知機能**（第5.1章の N-1〜N-7 以外）

また、以下は技術構成上の不採用事項であり、これらを前提としたAPI設計を行いません（技術スタック提案.md 第1章）。

- Vercel / AWS RDS / サーバレスを前提とした設計
- Redis を前提としたセッション・キャッシュ・キュー
- Docker を前提としたデプロイ
- 外部マネージドキューサービスを前提とした非同期処理
- プッシュ通知（`要件定義残タスク.md` B-2 で「実装しない」と整理済み）
