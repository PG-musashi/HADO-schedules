## 0. 本書の位置づけ

本書は、**バックエンド／APIの観点で要件定義工程として不足している事項**を洗い出したものです。`backend-api-reviewer` のレビュー観点（予約の整合性／権限・セキュリティ／エラーハンドリング／性能／監査ログ）を抜け漏れ検出のチェックリストとして使用しています。

各項目には「なぜ必要か」「決まらないと後工程で何が起きるか」「選択肢と推奨案」を記載しています。**推奨案は決定ではありません。** 承認を得てから `バックエンドAPI_要件定義書.md` に反映してください。

全社的な残タスクは `要件定義残タスク.md` にあります。本書は同文書の **A-5（API設計）／A-6（ワークフロー）／A-7（エラーコード設計）** をバックエンド観点で細分化したものです。認証方式（B-1）とメール送信プロバイダ（B-2）の選定そのものは同文書側の管理とし、本書では**それらが未決であることによるAPI設計への影響**のみを扱います。

### 優先度の基準

| 優先度 | 基準 |

## 1. 優先度：高

### BE-01 エンドポイント一覧とリクエスト／レスポンス仕様 【高】

**現状**：`要件定義残タスク.md` A-5 に「主要エンドポイント一覧」とあるのみで未策定。`backend-api-developer.md` にリソース名（`/api/venues`, `/api/courts`, `/api/reservations`, `/api/participations`, `/api/teams`, `/api/users`）の例示があるが、メソッド・パス・パラメータ・レスポンス項目は未定義。

**なぜ必要か**：フロントエンドとバックエンドの契約であり、両者の並行開発の前提。またレスポンス項目を決めることは「どの個人情報を返さないか」を決めることでもある（レビュー観点：レスポンスに不要な個人情報を含めない）。

**決まらないと後工程で何が起きるか**：

- フロントエンドが暫定のI/Fを想定して実装し、結合時に大量の手戻りが出る
- Prisma モデルをそのままレスポンスに流す実装になりやすく、メールアドレスや他ユーザーの内部IDが漏れる
- 「参加者一覧に何を出すか」が場当たりで決まり、拠点スタッフ／他メンバーへの情報開示範囲が統一されない

**選択肢と推奨案**：

| 選択肢 | 内容 | 評価 |
|---|---|---|
| A | 画面ワイヤーが固まってからAPIを定義 | 手戻りは少ないが、着手が遅れる |
| B | リソース単位でCRUDを先に定義し、画面側の要求で調整 | 並行開発しやすい |
| C | 画面単位のBFF的エンドポイント（例：スイムレーン表示専用API） | N+1回避に有利。REST原則からは外れる |

**推奨**：B を基本とし、**スイムレーン表示だけは C**（拠点＋日付を受けてコートと予約をまとめて返す1エンドポイント）とする。スイムレーンはコート×時間帯の一括取得であり、汎用CRUDの組み合わせでは N+1 と応答3秒要件の両方でリスクが高いため。あわせて**レスポンスに含める項目を明示列挙**（`select` で取る前提）する。

### BE-02 共通エラーフォーマットとエラーコード体系 【高】

**現状**：`要件定義残タスク.md` A-7 に「E001=認証エラー、E010=定員超過 等」の例示のみ。実体の一覧は未作成。

**なぜ必要か**：予約登録は「定員超過」「チーム枠超過」「時間帯重複（他者が先に確定）」「営業時間外」「権限なし」「セッション切断」など**失敗理由が多く、それぞれUI上の出し分けが必要**な処理。エラーコードがないとフロントは文言の文字列比較で分岐することになる。

**決まらないと後工程で何が起きるか**：

- ハンドラごとに独自形式のエラーが返り、フロントのエラー処理が個別実装になる
- Prisma の制約違反（`P2002` 等）を捕捉して変換する先がないため、未捕捉の500が返り、ユーザーにも運用にも原因が分からない
- 例外メッセージやスタックトレースをそのままクライアントに返す実装が混入する
- リリース後にコード体系を導入すると、フロント・バック両方の全エラー経路を書き換えることになる

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | HTTPステータスのみで表現 | 予約失敗の理由（定員超過か重複か）を区別できない。不可 |
| B | `{ error: { code, message, details } }` の独自フォーマット＋ `Exxx` コード体系 | 要件（A-7）の例示に沿う |
| C | RFC 9457（Problem Details for HTTP APIs）に準拠 | 標準準拠。`type` / `title` / `detail` に加え独自メンバーでコードを持てる |

**推奨**：**B**（要件で `Exxx` 形式が例示されているため）。ただし以下を必須とする。

- **クライアント向けメッセージと管理者向けログメッセージを分ける**（要件A-7、`backend-api-developer.md`）
- コード一覧をドキュメント化し、**新規コードは一覧に追記してから使う**運用ルールを定める
- 分類の目安：`E0xx`=認証・セッション、`E1xx`=認可・権限、`E2xx`=入力検証、`E3xx`=予約の業務ルール（定員超過・チーム枠超過・時間帯重複・営業時間外）、`E4xx`=競合・状態不整合、`E9xx`=システムエラー
- **最低限、予約登録の失敗理由は個別コードを持つ**こと

### BE-03 「先勝ち」判定に用いる時刻の定義 【高】

**現状**：要件は「同時にアクセスが発生した場合、**リクエスト送信された時刻をマイクロ秒まで比較し先勝ち**。全く同時刻の場合は**利用者の登録番号が大きい**利用者を優先」。しかし「リクエスト送信された時刻」を**誰が採番するか**が未定義。

**なぜ必要か**：クライアントが申告する送信時刻は**改ざん可能**であり、端末の時計ずれも避けられない。この定義が曖昧なまま実装すると、「早く送信したと申告した者が勝つ」＝**先勝ちを詐称できるAPI**になる。またマイクロ秒精度の比較が要求されているのに、比較対象の値の生成箇所が決まっていない。

**決まらないと後工程で何が起きるか**：

- クライアント時刻を信用する実装になれば、任意のユーザーが競合に必ず勝てる（予約の公平性が壊れる）
- 逆に定義がないまま「DBの制約違反が出た方を負け」とだけ実装すると、要件のタイブレーク規則（登録番号が大きい方を優先）が満たされず、受入テストで指摘される
- 「登録番号」が何を指すか（ユーザーの連番ID／会員番号）も未定義のため、比較対象が実装者依存になる

**選択肢と推奨案**：

| 選択肢 | 内容 | 評価 |
|---|---|---|
| A | クライアントが送信時刻をヘッダで申告 | 要件の字面には最も近いが、改ざん可能。**採用不可** |
| B | **サーバーがリクエスト受信時にマイクロ秒精度で1回採番**し、以降その値を使う | 改ざん不可。ネットワーク遅延の差は残るが実運用上妥当 |
| C | DBのトランザクション開始時刻／シーケンス値で決定 | 実装は単純だが、アプリ側の到着順と一致しない場合がある |

**推奨**：**B**。加えて、**判定の実体は DB の排他制約・行ロックによる直列化**とし、時刻比較は「敗者にどのエラーを返すか」および監査ログ上の説明のために記録する、という位置づけを明文化する。マイクロ秒まで同一だった場合のみ登録番号（＝ユーザーの登録連番、要定義）で決着させる。**「登録番号」の定義**もあわせて確定させること。

### BE-04 予約の状態遷移（登録〜確定〜実施〜完了）の定義 【高】

**現状**：`要件定義残タスク.md` A-6 に「予約登録〜確定〜実施〜完了の状態遷移図」とあるのみ。要求機能.md には状態の概念そのものが登場しない。

**なぜ必要か**：状態はAPIの操作可否を決める。「編集できるのはどの状態までか」「キャンセルはどの状態から可能か」「定員カウントに含めるのはどの状態の参加登録か」がすべて状態定義に依存する。

**決まらないと後工程で何が起きるか**：

- 「登録＝確定」なのか「承認待ちがある」のかが実装者判断になり、定員カウントの対象がぶれる（承認待ちを定員に数えるか否かで定員超過の挙動が変わる）
- 実施済み予約が編集できてしまう／できない、が画面ごとにばらつく
- **「実施」「完了」を誰が判定するのかが決められない**。本システムは**チェックイン機能を実装しない**ため、実際の来場を検知する手段がない
- 予約データは日付経過で物理削除されるため、「完了」状態のレコードがほぼ存在しない可能性がある（BE-09と関連）

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | 状態を持たず、日時と削除フラグのみで表現（過去日時＝実施済みとして表示） | 最小。チェックイン機能がない現状と整合的 |
| B | `確定` / `キャンセル済み` の2状態＋日時からの派生表示（`実施予定` / `実施済み`） | 状態遷移が単純で、監査ログとも対応づけやすい |
| C | `仮登録` / `確定` / `実施中` / `完了` / `キャンセル` のフル状態機械 | 承認フローや当日運用がある場合に必要だが、要件に承認や当日操作の記載がない |

**推奨**：**B**。「実施」「完了」は**保存する状態ではなく、現在時刻と予約時間帯から導出する表示上の区分**と定義する。理由：チェックイン機能を実装しないため実施実績を取得できず、C を採ると誰も遷移させられない状態が生まれるため。定員カウントに含めるのは `確定` の参加登録のみと明記する。

### BE-05 参加申請の承認フローとチーム枠への参加単位 【高】

**現状**：要求機能.md では、メンバーは「フリーで募集されている予約への**参加登録**」、チームリーダーは「他のチームが予約した空チーム欄の**参加申請**」と、**語が使い分けられている**が、承認者・承認要否は未定義。

**なぜ必要か**：承認の有無で定員判定のタイミングが変わる。承認制なら「申請中は枠を仮押さえするのか」を決めねばならず、しないと**承認待ちの間に定員が埋まる**問題が発生する。

**決まらないと後工程で何が起きるか**：

- 参加登録APIが「即確定」なのか「申請作成」なのかが決まらず、エンドポイントもレスポンスも定義できない
- 仮押さえの有無が未定のまま実装すると、定員超過または枠の無駄な占有のどちらかが起きる
- **通知要件との矛盾が残る**：要求機能.md の通知一覧に「参加申請があった／承認された」通知は**存在しない**。承認制を採るなら通知が必要になるが、記載のない通知は「実装しない機能」に該当するため、要件追加の判断が必要になる
- チーム枠1枠が消費される単位（1チーム＝1枠か、参加人数分か）が未定義だと、定員とチーム枠の独立判定そのものが実装できない

**選択肢と推奨案**：

| 選択肢 | 内容 | 評価 |
|---|---|---|
| A | **自動承認**（申請＝即確定、先着順） | 通知要件と矛盾しない。実装が単純で競合制御も1トランザクションで完結 |
| B | 予約者（またはチームリーダー）の承認制、仮押さえあり | 主催者が参加者を選べる。承認通知の要件追加が必要。仮押さえの期限設計も必要 |
| C | 承認制だが仮押さえなし | 承認時点で定員超過が起こりうる。実装は簡単だが体験が悪い |

**推奨**：**A（自動承認）**。理由：通知要件に承認関連の通知がなく、A なら要件追加なしで整合するため。あわせて**チーム枠は「1チームの参加＝1枠消費」**と定義する（用語定義「チーム枠2枠、定員9名の場合、チーム枠以外で3名の個人参加者を受け入れる」という例示と整合するかを併せて確認すること。この例示は定員9名＝総枠と読める記述と、定員はチーム枠を除いた人数という記述の間に**解釈の揺れ**があるため、要確認）。

### BE-06 認証・セッションのAPI契約（二重ログイン後勝ちの伝達） 【高】

**現状**：認証方式（NextAuth 採用可否）は `要件定義残タスク.md` B-1 で未決。API側の契約（トークンの種類・受け渡し方法・失効時の応答）も未定義。

**なぜ必要か**：「2重ログイン不可・後勝ち・既存接続は強制切断」は、**切断された側のクライアントが状態を知る手段**をAPIが提供しなければ成立しない。またセッションタイムアウト30分、ログイン失敗3回で30分ロックという要件も、APIの応答としてどう表現するかが決まっていない。

**決まらないと後工程で何が起きるか**：

- 切断された側のクライアントが「なぜ操作できないのか」を判別できず、フロントがログイン画面へ誘導できない（単なる401ではセッション期限切れと区別できない）
- ロックアウト中のログイン試行に対する応答が未定義だと、ユーザーが原因不明のまま繰り返し試行する
- 実装後に認証方式を差し替えると全ハンドラの認証取得箇所に影響する

**選択肢と推奨案**：

- 切断・失効の区別：**401 を返しつつ、エラーコードで「他端末でログインされたため切断」「セッションタイムアウト」「トークン不正」を区別する**ことを推奨（BE-02のコード体系に含める）
- ロックアウト：**423 または 401＋専用コード**とし、**残り時間や失敗回数をレスポンスに含めない**ことを推奨（アカウント存在の推測を助けるため）
- セッション保存先：技術スタック提案.md のとおり **PostgreSQL**（Redis 不採用、サーバーメモリに持たない）
- 認証情報の受け渡し：Secure / HttpOnly Cookie でのセッション参照を基本とし、`API通信は認証トークンによる認証` の要件はこのセッショントークンで満たすものとして整理することを推奨
- **「メールアドレスによるユーザー認証とし、複数アカウント登録は可能とする」の解釈**：同一メールアドレスで複数アカウントを作れるのか（＝メールアドレスは一意でない）、1人が別々のメールアドレスで複数アカウントを持てるのか（＝一意）で、**ログイン処理とDB制約が根本的に変わります**。推奨は後者（メールアドレスは一意）。前者の場合、メールアドレスだけではログインするアカウントを特定できず、別のログイン識別子が必要になるため

### BE-07 通知の非同期処理方式とリトライの実装単位 【高】

**現状**：要件は「メール配信に失敗した場合はシステムログに記録し、3回まで自動リトライ」のみ。実装方式は `要件定義残タスク.md` B-2 で未決。**Redis 不採用・単一VM・外部キューなし**という制約が確定している。

**なぜ必要か**：予約登録は5秒以内という性能要件がある一方、予約削除・編集では**参加者全員へのメール送信**が発生する。同期送信すると人数分のSMTP往復が応答時間に乗り、5秒を超える。またメール送信失敗で予約本体をロールバックしてはならない。

**決まらないと後工程で何が起きるか**：

- 同期送信で実装され、参加者が多い予約の編集・削除が5秒を超える
- 通知処理がトランザクション内に入り、メール送信失敗で予約が消える（レビュー観点の重大度「高」）
- リトライ単位が未定だと、10人中1人だけ失敗した場合に**全員へ再送**され、重複通知になる
- サーバー再起動（週次メンテナンス、Windows Update）でメモリ上のリトライ待ちが消失する

**選択肢と推奨案**：

| 選択肢 | 内容 | 評価 |
|---|---|---|
| A | 同期送信（リクエスト処理内で送る） | 5秒要件を満たせない。**採用不可** |
| B | プロセス内キュー（メモリ上のジョブ配列） | 実装は容易だが再起動で消える。技術スタック提案.md「キューをメモリ上に持たない」に反する |
| C | **PostgreSQL をジョブストアにした非同期送信**（送信待ちテーブル ＋ ワーカー） | 単一VM構成と整合。再起動しても残る。`FOR UPDATE SKIP LOCKED` で取り出す |
| D | タスクスケジューラ起動のバッチで定期送信 | 実装は単純だが即時性が落ちる（数分遅延） |

**推奨**：**C**。あわせて以下を決めること。

- **リトライ単位は「1宛先1通知」**（宛先ごとに独立して3回まで）を推奨。全員一括だと成功者への重複送信が起きる
- リトライ間隔（例：1分 → 5分 → 15分の指数バックオフ）
- 3回失敗後の終端処理（ログ記録のみか、管理者への集約通知か。後者は「記載のない通知」に該当しうるため要確認）
- ワーカーの起動形態（アプリプロセス内の常駐ループか、タスクスケジューラ起動の別プロセスか）
- **アプリ内通知とメール通知の関係**（アプリ内通知はDB書き込みのみで即時、メールのみ非同期、という切り分けを推奨）

### BE-08 API単位の権限マトリクス 【高】

**現状**：`要件定義残タスク.md` A-3 に「機能ごとのCRUD権限マトリクス」とあるが未作成。要求機能.md のロール別記述は箇条書きで、**明示されていない組み合わせの可否が不明**。

**なぜ必要か**：レビュー観点の重大度「高」に「IDOR：拠点スタッフが他拠点のリソースを、メンバーが他人の予約を操作できないか」がある。マトリクスがないと、ハンドラごとに実装者が判断することになり、抜けが生じる。

**決まらないと後工程で何が起きるか**：

- 明示されていない操作（例：拠点スタッフは他者の個人予約を削除できるか／チームリーダーはメンバーの参加登録を取り消せるか／拠点スタッフは自拠点の利用者情報をどこまで閲覧できるか）が実装者依存になる
- 権限テストの網羅基準が作れず、QAが検証できない
- リリース後に権限を厳しくすると既存運用が壊れる

**選択肢と推奨案**：

**推奨**：**エンドポイント×ロールの表を作り、各セルを「可 / 自分のリソースのみ / 自拠点のみ / 不可」の4値で埋める**。特に以下を明示的に決めること。

- 拠点スタッフが「自拠点コートの予約を削除／編集する」権限は、**利用者が登録した個人予約・チーム予約にも及ぶのか**（要求機能.md「コートの予約状況を登録/削除/編集する」は及ぶと読めるが、「予約の編集・削除は予約者のみ、ただしシステム管理者は全予約可」と**衝突している**）
- 拠点スタッフが閲覧できる利用者情報の範囲（個人情報保護方針 6.2 は「自拠点のユーザー情報を確認する場合」を認めている）
- チームリーダーがチーム予約に対して持つ権限が、チーム他メンバーの参加登録に及ぶか

> **この衝突（拠点スタッフの予約操作権限 vs 予約者のみ）は要件の矛盾であり、決着が必要です。**

### BE-09 データ保持ポリシーの矛盾（予約履歴が参照できない） 【高】

**現状**：3つのドキュメントで記述が食い違っています。

| 出典 | 記述 |
|---|---|
| 要求機能.md データ保持・削除ポリシー | 予約データは**日付が過ぎた時点で物理削除**。紛争解決に必要な情報（予約登録者、参加者等）は**12ヶ月保持** |
| 要求機能.md 利用者（メンバー） | 自分が参加した**予約の履歴を確認**できる |
| 個人情報保護方針 第5章 | 予約履歴は**予約日から24ヶ月**保持（紛争解決のため） |

**なぜ必要か**：予約データを日付経過で物理削除すると、**「予約履歴を確認」する機能が成立しません**。また保持期間が12ヶ月と24ヶ月で食い違っており、削除バッチの実装値が決まりません。

**決まらないと後工程で何が起きるか**：

- 履歴参照APIを作っても常に空を返す、あるいは削除バッチを実装したらリリース後に履歴が消え始める
- 削除バッチの条件を実装者が推測で決め、**復旧不可能な物理削除**が誤った基準で走る
- プライバシーポリシーの公開値（24ヶ月）と実挙動が乖離し、法令面のリスクになる

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | 予約は物理削除せず、一定期間（12 or 24ヶ月）保持して履歴参照に使う。期間経過後に物理削除 | 履歴機能と両立。プライバシーポリシーとも整合しやすい |
| B | 予約本体は日付経過で削除し、履歴用の最小限のレコード（日時・拠点・コート・参加者）を別途保持 | 削除ポリシーの字面に忠実。テーブル設計が増える（database-architect と要調整） |
| C | 履歴確認機能を取りやめる | 要求機能の削除にあたるため、承認が必要 |

**推奨**：**A**（保持期間は**24ヶ月**に統一し、要求機能.md の「日付が過ぎた時点で物理削除」を改訂）。理由：Bは実質的に同じデータを二重に持つことになり、削除漏れの経路が増えるため。**保持期間の数値（12／24ヶ月）を1つに統一すること**が最優先。なお具体的な削除方式・テーブル構成は database-architect の領域。

### BE-10 イベント予約の複数コート同時予約とトランザクション境界 【高】

**現状**：用語定義に「イベント予約は**複数コートを同時予約することも可能**」とあるのみ。API上の扱いは未定義。

**なぜ必要か**：複数コートの予約は、一部のコートだけ他者に先取りされる可能性がある。「1コートでも取れなければ全体を失敗にするのか」を決めないと、トランザクション境界が決まらない。

**決まらないと後工程で何が起きるか**：

- 部分成功が残り、イベントが成立しないのに一部コートだけ押さえられた状態になる
- 逆に全件ロールバックとした場合、複数行のロックを取る順序が決まっていないと**デッドロック**が発生する（コートIDの昇順でロックを取る等の規約が必要）
- 長時間のトランザクションが5秒要件とロック競合の両方を悪化させる

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | 全コート成功時のみ確定（オール・オア・ナッシング）、1トランザクション | 整合性が高い。ロック順序の規約が必要 |
| B | 取得できたコートのみ確定し、失敗分をレスポンスで返す | 部分成功の後始末を運用に委ねることになる |

**推奨**：**A**。あわせて「**コートIDの昇順でロックを取得する**」というデッドロック回避規約を明文化すること。1リクエストで指定できるコート数の上限（例：拠点内の全コート）も決めること。

### BE-12 営業日CSVインポートの仕様 【中】

**なぜ必要か**：要求機能.md「営業日の管理はCSVインポートも行う」とあるが、列定義・文字コード・件数上限・エラー時の挙動がすべて未定義。

**決まらないと**：Windows 環境から出力される Shift_JIS / UTF-8 BOM 付きCSVを想定せずに実装し、文字化けで運用開始直後に破綻する。また部分適用の可否が未定だと、100行中1行が不正だったときの挙動が実装者判断になる。

**選択肢と推奨案**：以下を決めること。

- **文字コード**：UTF-8（BOM有無両対応）と Shift_JIS の双方を受け付けることを推奨（拠点スタッフが Excel で編集する想定のため）
- **列定義**：日付／営業・休業区分／営業開始時刻／営業終了時刻（最小構成）
- **エラー時の挙動**：**全行検証してから全件適用（1行でも不正なら全件不適用）**を推奨。行単位スキップは適用結果が分かりにくい
- **既存データとの衝突**：同一日付が既に登録済みの場合の上書き可否
- **既存予約との衝突**：**営業日→休業日に変更する日に既存予約がある場合の扱い**（BE-17 と同じ論点）
- **件数上限**と、上限を超える場合の同期／非同期の切り分け（推奨：1回あたり数百行程度に上限を設け同期処理とする）

### BE-13 APIバージョニング方針 【中】

**なぜ必要か**：本システムのクライアントはWebブラウザのみでサーバーと同時にデプロイされるため、厳密なバージョニングの必要性は低い。ただし**方針を決めておかないと、後から必要になったときにパス設計を変えられない**。

**決まらないと**：`/api/reservations` のような無印パスで実装が広がり、将来的な破壊的変更時にパスの一括変更が必要になる。また週次メンテナンスのデプロイ中に**古いJSを保持したブラウザが新APIを叩く**期間が発生するが、その扱いが未定義になる。

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | バージョンなし（`/api/...`） | 最も単純。Web単独クライアントなら実用上問題は少ない |
| B | パスにバージョン（`/api/v1/...`） | 将来の並行運用が可能。初期コストはほぼゼロ |
| C | ヘッダでバージョン指定 | 柔軟だがキャッシュ・デバッグが煩雑 |

**推奨**：**B**。初期コストがほぼないうえ、後から A → B へ移行するコストの方が大きいため。あわせて、デプロイ直後の古いクライアントに対する扱い（バージョン不一致時に「再読み込みしてください」を返す仕組みの要否）を決めること。

### BE-14 冪等性（重複POST防止）とリクエストIDの方針 【中】

**なぜ必要か**：予約登録ボタンの二度押し、モバイル回線での再送により、同一内容の予約が二重に作られうる。同一コート・同一時間帯なら排他制約で弾かれるが、**参加登録や通知送信は制約で守られない**。

**決まらないと**：二重の参加登録・二重のメール通知が発生する。またリクエストIDがないと、ログ・監査ログ・エラー報告を突き合わせられず、障害調査ができない。

**選択肢と推奨案**：

- **冪等性**：更新系API（特に予約登録・参加登録）で `Idempotency-Key` ヘッダを受け取り、一定時間（例：24時間）同一キーの結果を返す方式を推奨。最小案としては、参加登録に「同一予約・同一ユーザー」の一意制約を置くことで実質的な冪等性を確保する
- **リクエストID**：全リクエストでサーバーがIDを採番し、**ログ・監査ログ・エラーレスポンスに同じIDを載せる**ことを推奨（ユーザーからの問い合わせと内部ログを紐づける唯一の手段になる。IIS 経由のため、IIS 側ログとの突き合わせも考慮）

### BE-15 レート制限のAPI仕様 【中】

**なぜ必要か**：`要件定義残タスク.md` B-4 に「レート制限の実装方式（ログイン / パスワードリセット / 予約登録）」が未決として挙がっているが、**APIとしての応答仕様**（超過時のステータス、エラーコード、制限単位）が未定義。

### BE-16 監査ログの記録項目とAPIからの記録単位 【中】

**なぜ必要か**：要件は「利用者のログイン状態とすべてのデータベース操作に関する状態をログファイルに記録」「拠点スタッフの操作は全てログに記録（誰が操作したかはログイン時刻から推測）」「監査ログは180日保持」。しかし**何を1レコードとして記録するか**が未定義。

**決まらないと**：「すべてのDB操作」を字義通りに解釈するとログ量が膨大になり、単一VMのディスクを圧迫する。逆に絞りすぎると、拠点スタッフの共有アカウント運用で**誰の操作か追跡できない**という要件未達になる。

**選択肢と推奨案**：

- **記録項目**（推奨）：発生日時、リクエストID、セッションID、ユーザーID、ロール、拠点ID（拠点スタッフの場合）、操作種別、対象リソース種別・ID、結果（成功／失敗）、失敗時のエラーコード
- **記録単位**：**SQL1文ごとではなく「APIの業務操作1件ごと」**を推奨。「すべてのDB操作」の要件は、参照系を除く**更新系操作の網羅**と解釈することを提案（要確認）
- **共有アカウントの追跡**：拠点スタッフの操作レコードに**セッションIDとログイン時刻を必ず含める**（要件「ログイン時刻から推測」を成立させるための必須条件）
- **個人情報の非出力**との両立：対象リソースはIDで記録し、氏名・メールアドレスを本文に含めない
- **保持期間の整合**：監査ログ180日（要求機能.md）とアクセスログ90日（個人情報保護方針）の関係を整理すること

### BE-17 拠点スタッフの「利用不可設定」が既存予約に与える影響 【中】

**なぜ必要か**：`要件定義残タスク.md` A-2 にも挙がっている論点。要求機能.md は「コートが利用不可な場合は、拠点スタッフが予約を行う事で利用不可状態を設定する」としているが、**その時間帯に既存の予約がある場合**の扱いが未定義。

**決まらないと**：排他制約により**利用不可設定そのものが失敗**する（既存予約と時間帯が重なるため）。実装者が制約を回避する抜け道を作ると、予約整合性の根幹が壊れる。

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | 既存予約があれば利用不可設定を**失敗**させ、拠点スタッフに既存予約の削除を促す | 整合性が保たれる。運用の手間が増える |
| B | 既存予約を**強制削除**し、予約者と参加者全員に通知 | 運用は楽。強制削除の通知は要件に記載がなく、通知要件の追加が必要 |
| C | 既存予約は残したまま重複を許す | 排他制約と矛盾する。**採用不可** |

**推奨**：**A**。理由：B は「記載のない通知」の追加が必要になり、また拠点スタッフの操作で利用者の予約が消えるという重い副作用を持つため。あわせて、営業日の休業化（BE-12）でも同じ判断を適用すること。

### BE-18 同一ユーザーの重複予約禁止／参加者の追加・削除可能期間 【中】

**なぜ必要か**：`要件定義残タスク.md` A-2 の未決事項。APIから見ると、これは**予約登録・参加登録の検証ルール**そのもの。

**決まらないと**：同一ユーザーが同一時間帯に複数の予約や参加登録を持てるかが実装者判断になる。また「予約開始直前のキャンセル」を許すかが未定だと、参加登録の削除APIに期限チェックを入れるべきか判断できない。要件追加として後から入れる場合、DB制約（部分一意インデックス）の追加が必要になり、既存データの整合性確認が発生する。

**選択肢と推奨案**：以下を決めること。

- 同一ユーザーが同一時間帯に**複数の予約を登録**できるか（推奨：不可。誤登録の防止になる）
- 同一ユーザーが同一時間帯に**複数の予約へ参加登録**できるか（推奨：不可）
- 参加登録の取り消し可能期限（推奨：予約開始時刻まで。キャンセル料の概念がなく、キャンセル待ち機能も実装しないため、複雑な期限を設ける動機が薄い）
- 予約者による予約編集の可能期限（同上）

> 「同一時間帯の重複を禁止する」を選ぶ場合、**部分一意インデックスまたは排他制約が必要**になるため、database-architect と同時に決めること。

### BE-19 日時・境界値のAPI表現と「10:00〜22:00 短縮不可」の解釈 【中】

**なぜ必要か**：要求機能.md の「拠点の営業時間はデフォルトから変更できるが、10:00〜22:00 から短縮することはできない」は、**読み方が複数あります**。

1. 営業時間は必ず 10:00〜22:00 を**含んで**いなければならない（延長のみ可）
2. 営業時間は 10:00 より遅く開始・22:00 より早く終了させられない（＝1と同義）
3. 短縮できないのは**コートの利用可能時間**であり、拠点の営業時間は自由

さらに、この記述は「コート」の節に置かれているのに主語が「拠点の営業時間」であり、**どちらのエンティティへの制約か曖昧**です。

**決まらないと**：営業時間設定APIの検証ロジックが実装者判断になり、拠点が 12:00〜20:00 のような設定を保存できるか否かが不定になる。予約時間の検証（要件定義書 3.3）もこの解釈に依存する。

**選択肢と推奨案**：**解釈1（営業時間は 10:00〜22:00 を必ず含む。延長のみ可）を推奨**し、要求機能.md 側の文言も明確化すること。あわせて以下を決める。

- API上の日時表現形式（推奨：ISO 8601 のオフセット付き文字列 `2026-07-26T10:00:00+09:00`）
- 終了時刻の境界（推奨：**終了時刻は排他的**。22:00 終了は可、22:00 開始は不可）
- 30分刻みへの整合を必須とするか（推奨：必須。スイムレーンが30分刻みのため）
- 日付をまたぐ予約の可否（推奨：不可。営業時間が最大 10:00〜22:00 のため発生しない）

### BE-20 画像アップロードAPIの仕様 【中】

**なぜ必要か**：プロフィール画像、拠点画像、チーム画像の登録が要件にあるが、APIとしての仕様が未定義。技術スタック提案.md では保存先はデータディスク、**保存先を差し替えられる層を挟む**ことが決まっている。

**決まらないと**：サイズ上限がないと単一VMのディスクを圧迫する。形式検証がないと、画像を装った実行可能ファイルの配置経路になる。また保存パスにユーザー入力のファイル名をそのまま使う実装はパストラバーサルの経路になる。

**選択肢と推奨案**：以下を決めること。

- 許可形式（推奨：JPEG / PNG / WebP のみ。**Content-Type 申告ではなくファイル内容のマジックナンバーで判定**）
- 1ファイルのサイズ上限（推奨：5MB 程度）とリクエストボディ上限（Next.js / IIS 双方の設定が必要）
- 保存ファイル名（推奨：**サーバー採番のUUID等**。元のファイル名を保存パスに使わない）
- 配信方法（静的配信か、権限チェックを挟むAPI経由か）
- リサイズ・サムネイル生成の要否（`要件定義残タスク.md` B-7 で優先度低として整理済み）

### BE-21 お気に入り上限の仕様矛盾とフィルタ条件保存API 【中】

**なぜ必要か**：要求機能.md 内に矛盾があります。

| 箇所 | 記述 |
|---|---|
| 利用者（メンバー） | メイン画面から拠点のお気に入りを行う（**上限10件**） |
| 予約検索・フィルター機能 | お気に入り**上限は設けない** |

また「各拠点を選択し、フィルター条件を保存する」の**保存先**（サーバー永続化か、ブラウザのローカル保存か）が未定義です。

**決まらないと**：お気に入り登録APIに上限チェックを入れるか否かが決まらない。フィルタ条件の保存先が未定だと、APIが必要かどうかすら決まらない（不要なら実装しない判断ができる）。

**選択肢と推奨案**：

- お気に入り上限：**どちらか一方に統一**すること。推奨は**上限10件**（初期20拠点・3年後50拠点の規模では10件で足り、無制限にすると初期表示のクエリが重くなる）
- フィルタ条件の保存：**サーバー保存**を推奨（端末を変えても設定が引き継がれる。ただし「保存する」という要件の意図が「その場のフィルタ状態を保持する」程度であればローカル保存で足りるため、意図の確認が必要）

### BE-22 メンテナンス時のAPI挙動 【中】

**なぜ必要か**：週1回 0:00〜5:00 の計画メンテナンスが確定しており、全ユーザーへの事前通知も要件化されている（N-7）。しかし**メンテナンス中にAPIへアクセスされたときの応答**が未定義。

**決まらないと**：メンテナンス中にアプリを停止するとブラウザ側にはネットワークエラーが出るだけで、利用者に理由が伝わらない。またデプロイ手順（ビルド配置 → `prisma migrate deploy` → サービス再起動）の途中で**スキーマとコードが不一致な状態**でリクエストを受ける可能性がある。

**選択肢と推奨案**：

| 選択肢 | 内容 |
|---|---|
| A | 何もしない（アプリ停止によりIISが502を返す） | 実装ゼロ。利用者に理由が伝わらない |
| B | IIS 側でメンテナンスページ／**503 ＋ Retry-After** に切り替える | アプリの実装が不要。推奨 |
| C | アプリにメンテナンスモードのフラグを持たせ、管理者以外へ503を返す | 部分的なメンテに対応できるが、DBマイグレーション中は使えない |

**推奨**：**B**（IIS の App Offline / リライトルールで 503 ＋ Retry-After を返す）。理由：DB マイグレーション中も含めて確実に適用でき、アプリ側の実装が不要なため。フロントは**503 を検知してメンテナンス表示に切り替える**規約を BE-02 と併せて定めること。

## 3. 優先度：低

### BE-23 API仕様書の形式と管理方法 【低】

**なぜ必要か**：BE-01 で定義したエンドポイントを、実装と乖離させずに維持する手段が必要。

**決まらないと**：Markdown の手書き仕様が実装とずれ、フロント・QAが実装を読んで推測することになる。

**選択肢と推奨案**：Markdown 手書き／OpenAPI（YAML）を手書き／コードからの生成（zod 等のスキーマから導出）。**推奨は OpenAPI（YAML）をリポジトリ管理**。将来的にリクエスト検証スキーマと共通化できる余地を残せるため。ただし要件定義段階では BE-01 の一覧が先。

---

### BE-24 キャッシュ・条件付きリクエストの方針 【低】

**なぜ必要か**：スイムレーン表示は頻繁にポーリングされる可能性があり、応答3秒要件と単一VMのリソース制約に影響する。

**決まらないと**：予約状況が古いまま表示され、ユーザーが埋まっている枠に予約を試みる（そして競合で失敗する）体験になる。逆にキャッシュを一切かけないと不要な負荷がかかる。

**選択肢と推奨案**：予約状況は**キャッシュしない**（鮮度が最優先）、マスタ系（拠点・コート・設備）は ETag による条件付きリクエストを許容、を推奨。**Next.js 16 のキャッシュ既定動作は学習データと異なる可能性があるため、`node_modules/next/dist/docs/` を確認してから決めること**（BE-26）。

---

### BE-25 エラーメッセージの言語方針 【低】

**なぜ必要か**：要件は「言語対応はブラウザに依存する」「デフォルトは日本語」。APIが返すエラーメッセージをどちらの責務にするかが未定義。

**決まらないと**：APIが日本語固定のメッセージを返し、将来の多言語対応時にサーバー側の全メッセージを改修することになる。

**選択肢と推奨案**：**APIはエラーコードとパラメータのみを返し、表示文言はフロントエンドが持つ**方式を推奨（BE-02 のコード体系があれば追加コストはほぼない）。ただし**メール本文は日本語固定**でよい。

### BE-26 Next.js 16 Route Handlers 仕様の事前確認 【低】

**現状**：`Source/Next.js/hado-schedules/node_modules` が未取得のため、本書作成時点で `node_modules/next/dist/docs/` を参照できていません。

**なぜ必要か**：Next.js 16.2.6 の Route Handlers / middleware / キャッシュ既定値は学習データと異なる可能性があり、記憶で実装すると動作しない、または意図せずレスポンスがキャッシュされる。

**決まらないと**：実装後に「予約状況が更新されない」「middleware で認証が効かない」といった不具合を、原因不明のまま調査することになる。

**推奨**：実装着手前に `npm install` を実行し、以下を確認すること。

- Route Handlers の既定キャッシュ挙動と動的レンダリングの指定方法
- middleware で認証チェックを行う場合の制約（実行環境・利用可能API）
- リクエストボディサイズの上限設定方法
- エラーレスポンスの返し方（`Response` / `NextResponse` の推奨形）

### BE-27 外部連携API・公開APIの有無 【低】

**なぜ必要か**：要件に外部システム連携の記載はないが、「なし」と明示しておかないと、後から要望が出たときに認証方式（トークン発行）から作り直しになる。

**決まらないと**：Webhook や外部からのAPIアクセスを想定した設計を「念のため」入れてしまい、不要な複雑さとセキュリティ面の攻撃対象を抱える。

**推奨**：**外部連携・公開APIは提供しない**と明記すること。APIはブラウザ（同一オリジン）からのアクセスのみを想定し、CORS は原則すべて拒否する設計とする。
