### 2.1 環境から来る制約

1. **Vercel 固有機能に依存しない。** Edge Runtime 前提の実装、Vercel の外部画像最適化、Vercel KV 等は使用不可。`技術スタック提案.md` §1 に「Vercel / AWS RDS / サーバレスは不採用。これらを前提とした設計・実装を行わないこと」と明記されている。
2. **Redis は不採用。** クライアント側から見える影響として、セッションは PostgreSQL 保持となる。
3. **セッション・キューをサーバーのメモリ上に持たない**（`技術スタック提案.md` §5 の「案2への移行に備えた約束」3）。
4. **画像の保存・取得はローカルパスをコード全体に散らさず、差し替え可能な層を1つ挟む**（同 §5 の約束2）。フロント側は画像の実体パスを直接組み立てず、URL を生成する層を経由する。
5. アプリと DB が単一VM に同居する。フロントからの過剰なリクエストは DB リソースを直接圧迫する。

## 5. 性能要件とフロントエンドへの影響

| 要件 | 出典 | フロントに課される条件 |
|---|---|---|
| 応答時間：画面表示から **3秒以内** | `アプリケーション要求機能.md` パフォーマンス要件 | 不要な Client Component 化を避け、クライアントバンドルを肥大させない。スイムレーンの初期描画コストをこの予算内に収める |
| 予約登録は **5秒以内**に完了 | 同上 | フォーム送信は送信中・失敗・成功の状態を持ち、二重送信を防ぐ。5秒を超え得る処理は送信前に検知して弾く（例：画像サイズ超過） |
| 同時接続 **100人** | 同上 | クライアント起因のポーリング・再取得が 100 人分同時に発生した場合の負荷を見積もる。アプリと DB は同一VM に同居している |
| スループット：予約登録 **5件/分** | 同上 | 予約登録の同時実行は多くない。楽観的更新より確実性を優先してよい ※補完 |

3秒 / 5秒は**外形監視の対象**でもあります（`技術スタック提案.md` §4.3：「外形監視：ログイン、スイムレーン表示、予約API の応答と応答時間（画面表示3秒 / 予約登録5秒）」）。フロントの実装劣化は監視アラートとして顕在化します。

## 6. Server / Client Components の方針

`frontend-developer.md` 実装方針より（確定事項として扱う）。

1. **Server Components を既定**とする。
2. 状態・イベントハンドラ・ブラウザ API が必要な部分**だけ**を Client Component（`"use client"`）に切り出し、**境界を最小化**する。
3. データ取得はサーバ側で行い、**クライアントに渡す前に表示に必要な形へ整形**する。
4. Prisma は Server Component / Route Handler 側でのみ使用する。
5. 型は `any` を使わない。API レスポンス型はバックエンドと共有できる形で定義する。

レビュー時に「高」重大度で指摘される項目（`frontend-code-reviewer.md`）：

- Server Component 内での `useState` / `useEffect` / ブラウザ API の使用
- 不要な `"use client"` による境界の拡大
- `await` 漏れ、Promise の未処理、エラーバウンダリの欠如

## 7. 日時の取り扱い（JST 固定）

- **タイムゾーンは日本（JST）に固定**（`アプリケーション要求機能.md` ユーザーインターフェース）。
- `new Date()` のローカルタイムゾーン依存で組まない（`frontend-developer.md` 5）。
- **日時の変換ロジックは1箇所に集約する**（同）。重複した日時変換が複数箇所にコピーされていないかはレビュー観点でもある。
- ローカルタイムゾーン依存の `new Date()` / `toLocaleString` の使用はレビューで「高」相当の指摘対象（`frontend-code-reviewer.md`）。
- DB 側は日時カラムを `@db.Timestamptz` で保持する（`技術スタック提案.md` §3）。サーバから受け取る日時はタイムゾーン付きである前提で、表示時に JST へ変換する。

※補完：ブラウザ端末のタイムゾーン設定が JST 以外であっても、画面表示は常に JST とする（「JST に固定」の文言から）。ただし実装方式は未決のため残タスクに記載。

## 8. 個人情報をクライアントに渡さない方針

`frontend-developer.md` 3 および `frontend-code-reviewer.md` セキュリティ観点より（確定事項）。

1. **Prisma のモデルオブジェクトを Server Component から Client Component へそのまま渡さない。** `select` で必要な項目だけを取得し、**表示用の型に詰め替える**。
   - 理由：`select` で絞らずに取得した結果を渡すと、画面に出していないカラムまで HTML（RSC ペイロード）に埋め込まれ、閲覧できてしまう。**最も見落とされる漏洩経路**として明示されている。
2. クライアントに渡す props に**他ユーザーのメールアドレス・内部ID・権限情報を含めない**。
3. **権限判定をクライアント側だけで行わない。** UI で隠すのは表示制御にすぎず、サーバ側で必ず判定する。
4. `dangerouslySetInnerHTML` を使わない（使う場合は入力元を明示して審査する）。
5. **`NEXT_PUBLIC_` の誤用をしない。** API トークン・秘密情報をクライアントバンドルに入れない。

### 8.1 保護対象（`個人情報保護方針.md` §2 より）

- 基本情報：プレイヤーネーム、メールアドレス、パスワード
- プロフィール情報：プロフィール画像、自己紹介文、プレースタイル
- 予約関連情報：予約日時、拠点・コート選択、チーム情報、キャンセルポリシー記載内容
- 自動収集：IPアドレス、ユーザーエージェント、アクセス日時・ログ、Cookie

**メールアドレスは画面に出さない**のが既定です ※補完（要求機能・画面ワイヤーのいずれにも、他ユーザーのメールアドレスを表示する画面は定義されていない。マイページの「アカウント設定（メール変更）」は自分自身の情報であり例外）。

### 8.2 参加者リストの表示範囲

予約詳細モーダルには「参加者リスト」が含まれます（`画面ワイヤー下書き.md` 3）。表示してよい項目はプレイヤーネームとプロフィール画像・プレースタイルまでと解釈します ※補完。**表示項目の確定は残タスク**（誰にどこまで見せるかは `個人情報保護方針.md` §6.2 の「スキーム参加者間での必要情報」の範囲と突き合わせが必要）。

### 8.3 Cookie

| Cookie種類 | 目的 | 保持期間 |
|---|---|---|
| セッションCookie | ユーザー認証・セッション管理 | ブラウザを閉じるまで |
| 設定Cookie | ユーザーの画面設定・言語設定 | 12ヶ月 |

「設定Cookie（画面設定・言語設定、12ヶ月）」はフロント側で扱う対象です。何を保存するかは未確定（残タスク）。

## 10. アクセシビリティ

**WCAG 2.1 AA に準拠する**（`アプリケーション要求機能.md` ユーザーインターフェース）。

実装上守ること（`frontend-developer.md`「UI 実装で守ること」）：

- セマンティック HTML を優先する
- **`div` にクリックハンドラを付けない**（ボタンは `button`、リンクは `a`）
- **フォーカスリングを消さない**
- **色だけで状態を示さない**（予約ブロックの種別・満席状態など、スイムレーンで特に影響する）
- フォーム入力に `label` を紐付ける

スイムレーンとモーダルは AA 準拠の難所です ※補完：グリッド状 UI のスクリーンリーダー読み上げ、モーダルのフォーカストラップと Esc 閉じ、横スクロール領域のキーボード操作が該当します。検証手段と受入基準は未確定（残タスク）。

## 12. 認証・セッションがフロントに与える制約

いずれも `アプリケーション要求機能.md`（ユーザー認証・登録機能 / セキュリティ）および `技術スタック提案.md` §6 より。

| 要件 | フロントへの影響 |
|---|---|
| アプリケーションにアクセスする際はログイン認証をする | 未ログイン時のリダイレクト先とガード方式が全画面に関わる |
| **2重ログイン不可・後勝ち**（既存接続は強制切断される） | 使用中の画面が突然無効セッションになる。この時のクライアント挙動を定義する必要がある（残タスク） |
| **セッションタイムアウトは30分間の無操作で自動ログアウト** | 画面を開いたまま放置された後の操作をどう扱うかを定義する必要がある（残タスク） |
| ログイン失敗3回で30分アカウントロック | ログイン画面のエラー表示に「ロックされた」状態が必要 |
| パスワード要件：最小8文字、大文字・小文字・数字を含む | クライアント側バリデーションの要件（サーバ側検証と二重管理になる。残タスク） |
| API 通信は認証トークンによる認証を行う | トークンをクライアントに露出させない方式であること（`NEXT_PUBLIC_` 禁止と整合） |
| 認証方式（NextAuth 採用可否）は**未決**。DBセッション方式が必須 | 認証方式の確定までフロントのセッション取得 API を固定できない |

## 13. 実装しない機能（提案・実装ともに禁止）

`アプリケーション要求機能.md`「実装しない機能」より。

- チェックイン機能
- 決済機能
- レビュー機能
- レポート機能
- 利用分析機能
- キャンセル待ち機能
- 記載されていない通知機能

これらの UI（ボタン、導線、プレースホルダを含む）を作らない。

## 14. 品質ゲート（完了条件）

`frontend-developer.md`「完了条件」より。

- `npm run lint` が通る
- TypeScript の型エラーがない（`npx tsc --noEmit`）
- 実装した画面の**状態（空 / 読込中 / エラー / 権限なし）が揃っている**
- 変更ファイルと動作確認方法を報告する

CI は `技術スタック提案.md` §7 の次アクションで「lint / 型チェック / build」を最小構成として構築予定です。
