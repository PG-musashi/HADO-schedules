# フロントエンド 要件定義残タスク

作成日：2026-07-26
対象領域：フロントエンド（`Source/Next.js/hado-schedules/`）
前提ドキュメント：`フロントエンド_要件定義書.md`（確定事項の整理）

## このドキュメントの読み方

要件定義工程として**フロントエンド領域で決まっていない項目**を洗い出したものです。各項目は次の形式です。

- **なぜ必要か** — 決めないと何が判断できないか
- **決まらないと後工程で起きること** — 具体的な手戻り・不具合
- **選択肢と推奨案** — 推奨は「この方向で確定させたい」という提案であり、決定ではありません

優先度の基準：

| 優先度 | 意味 |
|---|---|
| **高** | 基本設計に入る前に決めないと、実装後の作り直しになる |
| **中** | 実装着手までに決めればよいが、放置すると各画面でバラバラの実装が生まれる |
| **低** | 実装しながら決めても手戻りが小さい |

全体の残タスク（`要件定義残タスク.md`）と重複する項目は、フロント固有の観点に絞って記載しています。

### 先に解消が必要な、原文の矛盾

要件定義ドキュメント自体の記述矛盾で、フロントの実装量に直結するものです。**FE-01 の見積もり前に解消が必要**です。

| 箇所 | 矛盾 |
|---|---|
| `アプリケーション要求機能.md` 利用者/メンバー：「メイン画面から拠点のお気に入りを行う（**上限10件**）」 vs 予約検索・フィルター機能：「**お気に入り上限は設けない**」 | お気に入り件数の上限。メイン画面の初期表示はお気に入り拠点に紐づくコートを表示するため、上限の有無がそのまま初期描画の DOM 数上限になる |

## FE-01. スイムレーンの描画方式と DOM 数の上限（優先度：高）

**なぜ必要か**

スイムレーンは本システムの中核画面であり、「画面表示3秒以内」の要件を最も脅かす箇所です。`frontend-developer.md` は「ヘッダ固定・横スクロールを CSS で実現し、**必要になるまで仮想化ライブラリを足さない**」と方針を定めていますが、「必要になる」閾値＝**最大何行×何列を描画し得るのか**が決まっていません。

概算：10:00〜22:00 の 30分刻み＝**24スロット/行**。

| 初期表示の対象 | 行数（コート数） | セル数の目安 |
|---|---|---|
| 1拠点・4コート | 4 | 約 100 |
| お気に入り10拠点 × 平均4コート | 40 | **約 1,000** |
| お気に入り上限なし × 20拠点 × 4コート | 80 | **約 2,000** |

**決まらないと後工程で起きること**

- 「CSS で素直に組む」判断が上限次第で破綻し、実装後に仮想化ライブラリの追加＝コンポーネント全面書き直しになる。仮想化ライブラリは依存追加のためユーザー承認も必要（`frontend-developer.md`「やらないこと」）。
- 外形監視（`技術スタック提案.md` §4.3）で「スイムレーン表示」の応答時間が監視対象になっており、リリース後にアラートで顕在化する。
- 上限が無いままだと性能テストの条件（`要件定義残タスク.md` A-9）も作れない。

**選択肢と推奨案**

| 案 | 内容 | 評価 |
|---|---|---|
| A | メイン画面は**常に1拠点分のみ**表示する（拠点は左ペインで選択、お気に入りは並び順にのみ影響） | 描画量が有界（最大 1拠点のコート数×24）。要求機能「拠点を選択するとコートごとにスイムレーンが表示される」の原文に最も近い |
| B | お気に入り拠点を全て縦に連結表示する | 直感的だが DOM 数が青天井。仮想化がほぼ必須になる |
| C | 全拠点表示だが拠点単位で折りたたみ（既定は先頭のみ展開） | 折衷。実装コストは中 |

**推奨：案A。** 併せて次を数値で確定させる。

- 1拠点あたりのコート数の**想定最大値**（例：8）。`アプリケーション要求機能.md` には拠点数（3年後50）はあるがコート数の想定がない
- 同時に描画する行数の上限（例：最大16行＝約400セル）
- この上限を超える場合の扱い（ページング / 折りたたみ / スクロール読み込み）

## FE-02. スイムレーンの表示ルール（営業時間外・利用不可・22:00 境界・重複）（優先度：高）

**なぜ必要か**

表示レンジは 10:00〜22:00 固定と決まっていますが、**その中に何をどう描くか**が未定義です。

1. 拠点の営業日／営業時間はスタッフが設定できる（10:00〜22:00 より短縮は不可だが、営業日でない日がある）。**休業日・営業時間外のセルの見え方**が未定義。
2. コートごとに「利用可能時間」を設定できる。営業時間内でも利用不可な帯がある。
3. 「コートが利用不可な場合は、拠点スタッフが予約を行う事で利用不可状態を設定する」＝**利用不可は予約ブロックとして現れる**。他の予約種別と見分けがつく必要がある。
4. **22:00 の境界**：24番目のスロットが 21:30〜22:00 なのか、22:00 開始のスロットが存在するのか。`frontend-code-reviewer.md` が明示的にレビュー観点に挙げている。
5. 予約種別は4種（個人/チーム/イベント/店舗）。イベント予約は**複数コート同時予約**が可能で、複数行にまたがるブロックになり得る。
6. 「色だけで状態を示さない」（WCAG AA）ため、種別・満席・利用不可は**色以外の手がかり**が必要。

**決まらないと後工程で起きること**

- スイムレーンコンポーネントを作った後で表示ルールが追加され、セルとブロックのレンダリング構造を作り直すことになる（優先実装順1位のコンポーネントであり、影響が全画面に波及する）。
- 22:00 の解釈がフロントとバックエンドでずれると、22:00 開始の予約が作れる／作れないの不整合や、境界での重複判定漏れが起きる。DB 側の排他制約（`EXCLUDE USING gist`）と食い違えば、フォーム上は通るがサーバで弾かれる。
- 色だけの区別で作ってしまい、アクセシビリティ受入で全面手直しになる。

**選択肢と推奨案**

**推奨：ui-ux-designer と共同で「スイムレーンのセル状態一覧」を表として確定させる。** 最低限、以下の状態それぞれについて「表示」「操作（クリック時の挙動）」を定義する。

| 状態 | 例 |
|---|---|
| 予約可能（空き） | クリックで予約作成へ |
| 予約あり・空きあり（定員未満） | クリックで詳細 → 参加登録可 |
| 予約あり・満席 | クリックで詳細（参加不可） |
| 利用不可（スタッフ設定） | 詳細を出すか、非活性か |
| 営業時間外／休業日 | 非活性・斜線等 |
| 過去日時 | 非活性 |

境界については **「10:00〜22:00 は 21:30-22:00 を最終スロットとする24スロット。22:00 開始の予約は作成できない」** を推奨（営業時間の終端という自然な解釈で、バックエンドの区間表現 `[start, end)` とも整合する）。ただし**バックエンド・DB と合わせて1つの定義にすること**。

## FE-03. モバイル代替表示（日別縦表示）の具体仕様（優先度：高）

**なぜ必要か**

`画面ワイヤー下書き.md` は「モバイル（<=640px）ではスイムレーンは日別縦表示へ」とだけ書いており、**具体的な形が未定義**です。`frontend-developer.md` も「モバイル用の代替表示を実装する」とのみ定めています。

未定義の点：

- 縦軸が時間で横軸がコートになるのか、コートを1つ選んで時間リストを出すのか
- 複数コートをどう切り替えるか（タブ／セレクト／スワイプ）
- タブレット（641〜1024px）はデスクトップ版とモバイル版のどちらを使うか（ワイヤーに指針がない）
- 時間ズーム（30分/1時間）はモバイルでも提供するか

**決まらないと後工程で起きること**

- デスクトップ版だけ作って後からモバイル版を足すと、実質2つ目のコンポーネントを新規実装することになる。**要件定義段階で決めれば1つのデータ構造から2つのビューを出す設計にできる**。
- タブレットの扱いが未定だと、641〜1024px でレイアウトが崩れたまま気付かれない。

**選択肢と推奨案**

| 案 | 内容 |
|---|---|
| A | コート選択（セレクト or タブ） + 選択コートの時間帯リスト（縦） |
| B | 時間を縦軸、コートを横軸にした転置グリッド（横スクロール） |
| C | 予約カードのリスト表示（グリッドを捨てる） |

**推奨：案A。** 幅 640px 以下で 24 スロット × 複数コートのグリッドは可読性・タップ精度とも成立しにくく、案Aが最も破綻しにくい。タブレットは**デスクトップ版（左右ペイン）を適用**し、左ペインを折りたたみ可能にすることを推奨。

## FE-04. フォームバリデーション方式とサーバ側検証の二重管理（優先度：高）

**なぜ必要か**

予約作成フォームは項目が多く（拠点・コート・日付・開始/終了時刻・種別・定員・チーム枠・キャンセルポリシー・備考・添付）、しかも**業務ルールの検証**を含みます。

- 「参加者上限の動的バリデーション（定員とチーム枠の整合性）」（`画面ワイヤー下書き.md` 2）
- 「定員とチーム枠を同時に設定する場合、定員はチーム枠を除いた人数」（`アプリケーション要求機能.md` 予約）
- 既存予約との**時間帯重複チェック**（DB 側で `EXCLUDE USING gist` の排他制約として実装される）
- パスワード要件（最小8文字・大文字・小文字・数字）

これらは**クライアントとサーバの両方に必要**で、放置すると同じルールが2箇所に別実装されます。

**決まらないと後工程で起きること**

- ルール変更のたびに2箇所を直す必要が生まれ、片方だけ直した結果「画面は通るがサーバが弾く」「画面で弾かれるがサーバは受け付ける」という不整合が出る。
- 重複予約は DB の排他制約で最終的に弾かれるが、**エラーがフロントに 500 相当で返ると原因が利用者に伝わらない**。制約違反を業務エラーとして表現する取り決めが要る（FE-05 と連動）。
- バリデーションライブラリの導入は依存追加であり、ユーザー承認が必要（`frontend-developer.md`）。実装直前に判明すると止まる。

**選択肢と推奨案**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 手書きの検証関数を `lib/` に置き、Server / Client の両方から import して**同一実装を共有** | 依存追加ゼロ。型との整合は手動 |
| B | スキーマバリデーションライブラリ（Zod 等）でスキーマを1つ定義し、型・クライアント検証・サーバ検証を共有 | 二重管理が構造的に解消。依存1件の追加とユーザー承認が必要 |
| C | クライアント検証は最小限（必須・形式のみ）にし、業務ルールは**サーバ側のみ**で判定して結果を表示 | 実装が薄い。ただし「予約登録5秒以内」の中で往復が増え、入力体験は落ちる |

**推奨：案B（Zod 等のスキーマ共有）＋ 重複チェックのみ案C（サーバ判定）。** 時間帯の重複は他ユーザーの操作で刻々と変わるためクライアントで確定判定はできず、**サーバ判定が唯一の正**とすべきです。方針として次を明文化することを推奨します。

- **クライアント検証は UX のための先行チェックであり、サーバ検証を省略する理由にはならない**
- 単一データ（自フォーム内で完結する整合性）＝クライアント＋サーバ両方
- 他者の状態に依存するもの（重複・定員超過・権限）＝**サーバのみが判定**

## FE-05. エラー表示の共通化とエラーコード → メッセージのマッピング（優先度：高）

**なぜ必要か**

`要件定義残タスク.md` A-7 に「共通エラーコード一覧（E001=認証エラー、E010=定員超過 等）」「クライアント向け/管理者向けのメッセージ方針」が未決として挙がっています。フロント側は**受け取ったエラーをどこにどう出すか**が完全に未定義です。

想定されるエラー種別：

- 業務エラー（定員超過、時間帯重複、権限なし、営業時間外）
- 認証・セッションエラー（未ログイン、セッション失効、強制ログアウト、アカウントロック）
- 通信・サーバエラー（タイムアウト、5xx）
- 入力エラー（フィールド単位）

**決まらないと後工程で起きること**

- 画面ごとに `alert` / トースト / インライン表示がバラバラに実装され、後から統一するとほぼ全画面の修正になる。
- サーバのエラーレスポンス形式が決まっていないため、フロントは `catch` して「エラーが発生しました」と出すだけの実装になりがちで、**利用者が原因も次の行動も分からない**（特に予約重複と定員超過は頻発する）。
- 「実装した画面の状態（空 / 読込中 / エラー / 権限なし）が揃っている」が完了条件（`frontend-developer.md`）なのに、**「エラー」「権限なし」の見た目の基準が無いため完了判定ができない**。

**選択肢と推奨案**

**推奨：バックエンドと共通エラーレスポンス形式を先に合意し、フロントは以下3層に整理する。**

| 層 | 用途 | 例 |
|---|---|---|
| フィールドインライン | 入力値の誤り | 「定員はチーム枠を除いた人数を入力してください」 |
| フォーム上部／トースト | 送信時の業務エラー | 「この時間帯は既に予約されています」 |
| 画面全体（`error.tsx` 等） | 取得失敗・想定外エラー | 再試行導線を置く |

併せて確定が必要なもの：

- 共通エラーレスポンスの形（エラーコード・利用者向けメッセージ・フィールド名を含むか）
- **メッセージ文言をサーバが返すか、フロントがコードから引くか**（推奨：フロントがコード → 文言の辞書を持つ。多言語化・文言修正の一元管理がしやすく、サーバがエラー文言に個人情報や内部情報を含める事故も防げる）
- ログイン試行3回失敗による30分ロックの通知文言（アカウント存在の有無を推測させない配慮が必要）
- 「権限なし」を 403 画面にするか、そもそも導線を出さないか

## FE-06. セッション失効・二重ログイン後勝ち時のクライアント挙動（優先度：高）

**なぜ必要か**

要件として次の2つが確定しています。

- 「各アカウントは2重ログイン不可とし、すでにログインされている場合は**後勝ち**（既存接続は**強制切断**される）」
- 「セッションタイムアウトは**30分間のアクティビティがない場合に自動ログアウト**する」

つまり**利用者が操作していない間にセッションが無効化される**ケースが仕様上必ず発生します。フロントがこれをどう検知し、どう見せるかが未定義です。

**決まらないと後工程で起きること**

- 予約フォームに入力中にセッションが切れ、送信時に 401 が返る。何も設計していないと**入力内容が消えて原因も分からない**という最悪の体験になる。これは 30分無操作の要件がある以上、確実に起きる。
- 各画面が個別に 401 をハンドリングし、リダイレクト先も挙動もバラバラになる。
- Server Component で描画済みの画面は、セッション失効を自力では検知できない。**検知点の設計が要件定義段階で必要**。

**選択肢と推奨案**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 検知は**操作時のみ**（API が 401 を返したらログイン画面へ遷移し、理由を表示） | 実装が最も軽い。追加のポーリング負荷ゼロ |
| B | 定期ポーリングでセッション有効性を確認し、切れたら即座に通知 | 即時性は高いが、同時接続100人 × 定期リクエストが単一VM の DB に直接効く |
| C | A + 30分に近づいたら画面上で警告（延長ボタン） | 体験は最良。実装コストは中 |

**推奨：案A を基本とし、予約作成など入力量の多いフォームでは「送信失敗時に入力内容を保持したままログインを促す」ことを要件に含める。** 併せて次を確定させる。

- 強制切断（後勝ち）とタイムアウトを**区別して表示するか**（「別の端末でログインされました」と「一定時間操作がなかったため…」）
- ログイン後に元の画面へ戻すか
- 401 を一元的に扱う場所（`frontend-developer.md` の「重複ロジックを複数箇所にコピーしない」に従い1箇所に集約）

## FE-07. 権限による UI 出し分けに必要な情報の受け渡し方（優先度：高）

**なぜ必要か**

権限は4種（メンバー／チームリーダー／拠点スタッフ／システム管理者）あり、画面の出し分けが広範囲に及びます（予約の編集・削除は予約者のみ、ただしシステム管理者は全予約可能／拠点スタッフは自拠点のみ／チームリーダーは承認操作あり）。

一方でレビュー観点として次が「高」重大度に置かれています。

- クライアントに渡す props に**権限情報**を含めない
- **権限判定をクライアント側だけで行わない**（UI で隠すのは表示制御にすぎない）

**「権限で UI を出し分ける」と「権限情報をクライアントに渡さない」をどう両立させるか**の方針が決まっていません。

**決まらないと後工程で起きること**

- 安易に `user.role` を Client Component に渡す実装が各所に生まれ、レビューで一律差し戻しになる。
- 逆に厳格に解釈しすぎて、ボタンの表示可否まで毎回サーバ問い合わせする実装になり、応答時間を圧迫する。
- `要件定義残タスク.md` A-3（権限マトリクス）が未確定なままだと、そもそも何を出し分けるかの一覧が無い。

**選択肢と推奨案**

**推奨：ロールそのものではなく「この画面・この対象に対して可能な操作」を boolean のフラグに落としてサーバ側で算出し、それだけをクライアントへ渡す。**

例：予約詳細に渡すのは `role: "SYSTEM_ADMIN"` ではなく `{ canEdit: true, canDelete: true, canJoin: false }`。

- ロール名・内部ID・所属拠点IDといった情報がクライアントに出ない
- 判定ロジックがサーバ側の1箇所に集約される（重複実装の防止）
- Client Component は表示制御に徹する

前提として **A-3 の権限マトリクス確定が必要**です。フロントとしては「画面 × 操作 × ロール」の表を要求してください。

## FE-08. 画面遷移図・ルーティング設計（モーダル vs ページ）（優先度：高）

**なぜ必要か**

`要件定義残タスク.md` A-1 に「画面遷移図（ログイン/未ログイン時の遷移含む）」が未決とあります。加えてフロント固有の論点として、ワイヤーが**モーダルとページを併記**しています（「予約作成**モーダル / 画面**」「予約詳細**モーダル**」）。

**決まらないと後工程で起きること**

- モーダルとして作った後に「URL で共有したい」「ブラウザの戻るで閉じたい」という要求が出ると、ルーティング構造ごと作り直しになる。App Router ではモーダルをルートとして扱う実装方式が用意されており、**後付けよりも最初に決める方が圧倒的に安い**（具体的な規約名・ディレクトリ規約は `node_modules/next/dist/docs/` で確認のこと。本書では断定しない）。
- 未ログイン時のリダイレクト方式（どこでガードするか）が決まらないと、全ルートに個別実装が散らばる。
- 予約作成は「送信ボタン（確認画面へ）」とあり、**確認ステップが別画面なのかモーダル内のステップなのか**でフォーム状態の保持方法が変わる。

**選択肢と推奨案**

**推奨：**

- **予約詳細はルート付きモーダル**（URL で共有可能・戻るで閉じる・直リンクでは単独ページとして描画）。予約の共有は業務上ありうる
- **予約作成はモーダル内2ステップ（入力 → 確認）**。ページ遷移すると入力内容の保持が別問題になる
- 未ログインガードは**ルートグループ単位で一元化**し、各ページで個別実装しない

併せて画面遷移図に含めるべきもの：ログイン／未ログイン、パスワードリセット（初回・再設定のランダム文字列メール経由）、権限別のトップ画面、強制ログアウト後の戻り先。

## FE-09. 予約データの鮮度とキャッシュ／再取得方針（優先度：高）

**なぜ必要か**

スイムレーンは**他人が同時に更新する共有リソース**です。要件には次があります。

- 同時接続ユーザーの想定は100人
- 「同時にアクセスが発生した場合、リクエスト送信された時刻をマイクロ秒まで比較し先勝ち」（＝競合が起きる前提の仕様）

一方、フロントの表示が古いままだと**空きに見えるセルをクリックして予約作成に進み、送信時に弾かれる**という失敗が日常的に起きます。何秒古いデータまで許容するかが未定義です。

**決まらないと後工程で起きること**

- Next.js のデータキャッシュ既定挙動に無自覚なまま実装し、**予約したのに画面に反映されない**という不具合が出る（App Router で最も頻出するクラスの不具合）。
- 逆に全てを都度取得にすると、同時接続100人 × スイムレーン再取得が単一VM の PostgreSQL を直撃する。
- 「画面表示3秒以内」の判定基準が、キャッシュ有無で大きく変わる。

**選択肢と推奨案**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 常に最新取得（キャッシュしない）。予約後は再検証して再描画 | 実装が単純で鮮度は最良。DB 負荷は最大 |
| B | 短時間キャッシュ（数十秒）＋ 予約操作後に明示的再検証 | 負荷と鮮度のバランスが良い |
| C | B + 一定間隔の自動再取得（画面を開いたままでも更新される） | 体験は良いが定期リクエストが 100人分乗る |
| D | リアルタイム更新（WebSocket / SSE） | **非推奨**。要求機能に記載がなく、単一VM・IIS リバースプロキシ経由の常時接続は運用負荷が大きい |

**推奨：案B。** 加えて次を明文化する。

- 予約の作成・編集・削除・参加登録の直後は、**必ずスイムレーンを再検証してから完了表示する**
- 「送信時に他者に先を越された」場合のエラー表示を FE-05 の業務エラーとして定義する（先勝ちルールの結果を利用者に説明する文言）
- 画面を開いたまま放置した場合の自動更新は**行わない**（30分でセッションも切れるため整合的）。ただし手動リロード導線は置く

キャッシュ・再検証の具体的な API 名と既定挙動は **`node_modules/next/dist/docs/` を確認してから**基本設計に書くこと。

## FE-10. 画像アップロードのクライアント側仕様（優先度：高）

**なぜ必要か**

画像アップロードは複数箇所にあります。

- プロフィール画像（メンバー）
- チーム画像（チームリーダー）
- 拠点画像（拠点スタッフ）
- 予約作成フォームの「画像/ファイル添付（任意）」（`画面ワイヤー下書き.md` 2）

しかし**サイズ上限・許容形式・枚数・寸法・処理方式のいずれも未定義**です。保存先は「データディスク上のディレクトリ」とだけ決まっています（`技術スタック提案.md` §2.3）。

**決まらないと後工程で起きること**

- 上限が無いと数十MBの画像が投稿され、**「予約登録は5秒以内」を確実に破る**。単一VM のデータディスク（100GB）も想定外に消費される。
- 形式が無制限だと、SVG（スクリプト実行の恐れ）や実行可能ファイルの受け入れというセキュリティ問題になる。
- 「画像/ファイル添付」の「ファイル」が何を指すのか不明なまま実装すると、任意ファイルのアップロード機能を作ってしまう。
- クライアント側で事前に弾かないと、アップロードしてから拒否される（帯域と待ち時間の無駄）。

**選択肢と推奨案**

**推奨：以下を要件として確定させる（数値は推奨案であり要合意）。**

| 項目 | 推奨 | 理由 |
|---|---|---|
| 許容形式 | JPEG / PNG / WebP のみ。**SVG は不可** | SVG はスクリプトを埋め込める |
| 1ファイル上限 | 5 MB | 5秒要件に対して余裕を持てる |
| 枚数 | プロフィール・チーム・拠点は各1枚。予約添付は上限を定める（例：3枚） | 無制限を避ける |
| クライアント側の事前検証 | 形式・サイズを送信前にチェックし、超過時はその場でエラー表示 | 無駄な送信を防ぐ |
| クライアント側リサイズ | 行うか要判断（推奨：長辺 1600px 程度に縮小して送信） | 帯域・保存容量・5秒要件のすべてに効く |
| サーバ側検証 | **必須**（クライアント検証は回避可能なため） | FE-04 と同じ原則 |
| 表示側 | 保存先を差し替え可能な層を経由して URL を得る（`技術スタック提案.md` §5 の約束2） | 案2移行時のコストをゼロにする |
| アップロード中の表示 | 進捗またはスピナー、キャンセル可否 | 未定義だと画面ごとにバラバラになる |

「予約作成フォームの**ファイル**添付」については、**画像のみに限定する**ことを推奨します（任意ファイルの受け入れはウイルススキャン等の運用要件を新たに発生させ、要求機能にその記載がないため）。

## FE-11. 状態管理方針（優先度：中）

**なぜ必要か**

「Server Components を既定とし、境界を最小化する」方針は決まっていますが、**Client 側に残る状態を何で管理するか**が未定義です。実際に状態が必要になる箇所：

- 選択中の拠点・日付・時間ズーム（30分/1時間）
- 「各拠点を選択し、**フィルター条件を保存する**」（`アプリケーション要求機能.md` 予約検索・フィルター機能）— **保存先が未定義**
- 予約作成フォームの入力値と送信中フラグ
- モーダルの開閉
- 未読通知の件数

**決まらないと後工程で起きること**

- 画面ごとに `useState` / Context / URL クエリ / localStorage がバラバラに選ばれ、同じ情報が複数の場所で持たれて不整合を起こす。
- 状態管理ライブラリの追加は依存追加であり、実装途中に判明すると承認待ちで止まる。
- 「フィルター条件を保存する」の保存先（URL / Cookie / DB）が決まらないと、そもそも実装できない。`個人情報保護方針.md` §8.1 には「設定Cookie：ユーザーの画面設定・言語設定、12ヶ月」があるため、Cookie 保存が想定されている可能性がある。

**選択肢と推奨案**

**推奨：状態管理ライブラリは導入せず、次の優先順で置き場所を決める方針を明文化する。**

1. **URL のクエリパラメータ** — 拠点・日付・ズーム。共有・リロード・戻る操作に強く、Server Component 側でそのまま読める（最優先）
2. **サーバ（DB）** — お気に入り、ユーザー設定。ログイン単位で永続すべきもの
3. **Cookie** — 「フィルター条件の保存」（`個人情報保護方針.md` の設定Cookie と整合する）
4. **`useState` / Context** — モーダル開閉、フォーム入力など画面ローカルかつ一時的なもののみ

そのうえで「フィルター条件の保存」が**端末ごと（Cookie）か、アカウントごと（DB）か**を確定させてください。

## FE-12. ローディング UI の方針（優先度：中）

**なぜ必要か**

「実装した画面の状態（空 / 読込中 / エラー / 権限なし）が揃っている」が完了条件（`frontend-developer.md`）ですが、**読込中の見せ方の基準がありません**。

**決まらないと後工程で起きること**

- 画面ごとにスピナー／スケルトン／何も出さない、が混在する。
- 「画面表示3秒以内」の要件に対し、**何をもって「表示された」とみなすか**の共通理解が無い。スケルトンが出た時点なのか、実データが出た時点なのかで測定結果が変わり、外形監視（`技術スタック提案.md` §4.3）の閾値設計にも影響する。

**選択肢と推奨案**

**推奨：**

- スイムレーンのような**レイアウトが確定している領域はスケルトン**（レイアウトシフトを防ぐ）
- モーダル・小領域はスピナー
- ボタン送信中はボタン自体を無効化＋ラベル変更（二重送信防止と兼ねる。`frontend-developer.md` 6）
- **「表示3秒以内」の判定は実データが描画された時点**とする（監視側と定義を揃える）

App Router のストリーミング／`loading.tsx` の規約は `node_modules/next/dist/docs/` を確認して基本設計に反映すること。

## FE-13. i18n の実装方式（優先度：中）

**なぜ必要か**

要件は次の2文だけです。

- 「言語対応はブラウザに依存する」
- 「言語はブラウザ設定に依存し、デフォルトは日本語とする」

**この「ブラウザに依存する」が何を指すか判別できません。**

| 解釈 | 実装 |
|---|---|
| ① ブラウザの翻訳機能に任せる（アプリは日本語のみ） | i18n 実装は**不要**。`lang="ja"` を正しく付け、翻訳を妨げるマークアップを避けるだけ |
| ② `Accept-Language` を見てアプリが表示言語を切り替える | i18n の仕組み・翻訳リソース・対応言語リスト・ルーティング設計がすべて必要 |

**決まらないと後工程で起きること**

- ②だった場合、後から入れると**全画面の文言を外部化する作業**が発生する。文言がコンポーネントに直書きされた後では極めて高コスト。
- ①なのに②の前提で作ると、翻訳リソース管理という不要な運用コストが生まれる。
- `個人情報保護方針.md` §8.1 に「設定Cookie：ユーザーの画面設定・**言語設定**、12ヶ月」とあり、②を示唆しているようにも読める。**この矛盾の解消が必要**。

**選択肢と推奨案**

**推奨：①（日本語のみ。ブラウザの翻訳機能に委ねる）で確定させる。** 根拠：

- 要求機能に対応言語のリストが無い
- `個人情報保護方針.md` が「日本語版が正式版」と明記している
- 対象利用者は国内拠点のコート予約者である

そのうえで、①を選んだ場合でも**画面文言をコンポーネントに直書きせず、1箇所にまとめておく**ことを推奨します（将来②へ移行する際のコストが大幅に下がり、FE-05 のエラー文言辞書とも同じ置き場所を使えます）。①で確定するなら `個人情報保護方針.md` の設定Cookie の「言語設定」記述も併せて見直してください。

## FE-14. 日時ユーティリティの方式・ライブラリ選定（優先度：中）

**なぜ必要か**

「JST 固定」「日時変換ロジックは1箇所に集約」は方針として決まっていますが、**何で実装するか**が未定義です。日時は本システムのほぼ全画面に出ます（スイムレーン、日付ピッカー、予約フォーム、履歴、営業日カレンダー）。

**決まらないと後工程で起きること**

- 各所で `new Date()` と `toLocaleString` が使われ、**サーバ（Windows Server のロケール設定）とブラウザで表示がずれる**。レビューで「高」重大度の指摘対象。
- 30分刻みのスロット計算、夏時間なし前提の日付跨ぎ、月末・営業日カレンダーの計算がバラバラの実装になる。
- ライブラリ導入なら依存追加の承認が必要。

**選択肢と推奨案**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 標準の `Intl` API（`timeZone: "Asia/Tokyo"` を明示）でユーティリティを自作 | 依存ゼロ。JST 固定なら十分に書ける |
| B | 日時ライブラリを導入（date-fns / Day.js + timezone プラグイン 等） | 記述は楽。バンドルサイズと依存追加の承認が必要 |
| C | Temporal API | 対応ブラウザが「最新版のみ」なら候補になり得るが、**対応状況を実測で確認してから**判断すること（記憶で断定しない） |

**推奨：案A。** JST 固定であればタイムゾーン変換の複雑さは無く、`Intl.DateTimeFormat` に `timeZone: "Asia/Tokyo"` を明示するだけで要件を満たせます。クライアントバンドルを増やさない点も「表示3秒以内」に有利です。

そのうえで**次を1つのモジュールに集約する**ことを要件とする：JST でのフォーマット、日付文字列 ⇄ 内部表現の変換、30分スロットの生成・境界判定、営業時間内判定。

## FE-15. UI コンポーネントの調達方針とデザイントークン（優先度：中）

**なぜ必要か**

「勝手に UI ライブラリを導入しない」（`frontend-developer.md`「やらないこと」）と定められている一方、**何を使うのか（あるいは全部自作するのか）が決まっていません**。必要になるのは、モーダル、日付ピッカー、セレクト、タブ、トースト、カレンダー（営業日設定）です。

WCAG 2.1 AA 準拠が要件であり、**モーダルのフォーカストラップや日付ピッカーのキーボード操作を自作で AA 水準にするのは相応の工数**です。

**決まらないと後工程で起きること**

- 実装開始後に「モーダルを作るのにライブラリが要る」と判明し、承認待ちで止まる。
- 自作を選んだ場合、アクセシビリティ要件を満たすコストが見積もりに入っていない。
- 現状の `app/globals.css` は `create-next-app` のテンプレート（`--background` / `--foreground` のみ）で、色・間隔・タイポグラフィのトークンが定義されていない。各画面が個別に色指定を書くと統一が崩れる。

**選択肢と推奨案**

| 案 | 内容 |
|---|---|
| A | 全て自作（依存追加ゼロ） |
| B | ヘッドレスな UI プリミティブを1つ導入（アクセシビリティ対応済みの挙動のみを得て、見た目は Tailwind で作る） |
| C | 完成された UI キットを導入 |

**推奨：案B を1件だけ導入する方向でユーザー承認を取る。** 理由：AA 準拠が契約上の要件であり、モーダル・日付ピッカー・セレクトのキーボード／スクリーンリーダー対応を自作で担保するリスクが高いため。案C は見た目の制約とバンドルサイズが大きく、「表示3秒以内」に不利。

併せて **`app/globals.css` の `@theme` にデザイントークン（色・間隔・タイポグラフィ・予約種別の識別色）を定義する**ことを要件化してください。Tailwind v4 は設定方式が v3 と異なるため、書き方は既存の `postcss.config.mjs` / `globals.css` と `node_modules/tailwindcss` を確認してから確定すること。

## FE-16. アプリ内通知 UI の仕様（優先度：中）

**なぜ必要か**

要求機能では複数の通知が「メール**および**アプリ上で通知」と定められています（予約情報の編集、チーム登録申請・承認/却下、システムメンテナンス）。ワイヤーのヘッダにも「ユーザーメニュー(通知/マイページ)」があります。

しかし**アプリ内通知の画面仕様が一切ありません**（一覧画面の有無、既読/未読、保持件数、削除可否、未読件数の取得方法）。

**決まらないと後工程で起きること**

- ヘッダの通知アイコンだけ作って中身が無い、という状態で止まる。
- 未読件数を**全画面のヘッダで表示する**ため、取得方式を誤ると同時接続100人分の定期リクエストが単一VM に乗る。ポーリング間隔は性能に直結する。
- 「記載されていない通知機能は実装しない」という制約があるため、**通知の種類を仕様として確定させないと実装可否の線引きができない**。

**選択肢と推奨案**

**推奨：**

- 通知は**一覧画面（またはドロップダウン）＋既読管理**を持つ。対象は要求機能に列挙された通知に限定する
- 未読件数は**ページ遷移時にサーバ側で取得**する（Server Component で描画）。定期ポーリングは行わない
- 定期ポーリングを入れる場合は間隔を要件として明記する（推奨：入れない。入れるなら60秒以上）

## FE-17. アクセシビリティの検証手段と受入基準（優先度：中）

**なぜ必要か**

「WCAG 2.1 AA に準拠する」は契約上の要件ですが、**準拠していることを何で確認するかが未定義**です。`要件定義残タスク.md` A-9（テスト計画）にもアクセシビリティの記載はありません。

**決まらないと後工程で起きること**

- 「準拠している」と主張する根拠が無く、UAT や受入で争点になる。
- 実装完了後に自動チェックを回して大量の違反が出ると、スイムレーンやモーダルの構造レベルの手直しになる。
- どのスクリーンリーダー・どのブラウザ組み合わせを対象とするかが不明なまま検証すると、検証範囲が発散する。

**選択肢と推奨案**

**推奨：**

- CI に**自動チェック**（axe 系）を組み込み、検出可能な違反ゼロを最低ラインとする
- 自動では検出できない項目（キーボードのみでの操作完遂、フォーカス順序、色以外の状態表現、スクリーンリーダーでのスイムレーン読み上げ）について、**主要画面ごとのチェックリストを作り手動確認する**
- 対象とするスクリーンリーダーと OS / ブラウザの組み合わせを1つ以上明記する
- 検証対象画面の優先度（メイン画面・予約作成・予約詳細・ログインを必須とする）

自動チェックツールの導入は依存追加のため、テストフレームワーク（`要件定義残タスク.md` B-5、いずれも未導入）の決定と合わせて判断してください。

## FE-18. フォント配信方式（オンプレ・ビルド時外部通信）（優先度：中）

**なぜ必要か**

現状の `app/layout.tsx` は `next/font/google` から Geist / Geist_Mono を読み込んでいます（テンプレートのまま）。本番は **Windows Server 上のセルフホスト**で、CI は GitHub Actions の **Windows セルフホストランナー（本番VM上）** です。

論点：

- `next/font/google` はビルド時に外部からフォントを取得する方式であるため、**ビルド環境が外部へ出られない場合にビルドが失敗し得る**（正確な挙動は `node_modules/next/dist/docs/` の font ガイドで確認すること。本書では断定しない）
- Geist はラテン文字のフォントであり、`subsets: ["latin"]` の指定のままでは**日本語には効かない**。本サービスの主要言語は日本語

**決まらないと後工程で起きること**

- 閉域ネットワークでビルドが通らず、デプロイ直前に判明する。
- 日本語フォントを Web フォントとして配信すると容量が大きく、「画面表示3秒以内」を圧迫する。

**選択肢と推奨案**

**推奨：日本語はシステムフォント（OS 標準の日本語フォントを CSS の font stack で指定）とし、Web フォントの読み込みを行わない。** 容量ゼロで 3秒要件に最も有利で、ビルド時の外部通信も不要になります。

ラテン文字用に Web フォントを使いたい場合は、**フォントファイルをリポジトリに同梱してローカル読み込みする方式**（外部取得を伴わない方式）を推奨します。いずれにせよ**テンプレートの Geist 設定はそのまま残さない**でください。

## FE-19. 画像配信・`next/image` の最適化方針（優先度：中）

**なぜ必要か**

拠点画像・チーム画像・プロフィール画像が各画面に並びます（メイン画面の拠点リストは画像 + 名称）。画像はデータディスク上のディレクトリに保存されます。

しかし**配信方法が未定義**です。

- 画像を返すのは Next.js か、IIS で静的配信するか
- `next/image` の最適化を使うか（セルフホストでの最適化はサーバ CPU を消費する。単一VM でアプリ・DB と同居している）
- Vercel の外部最適化は**使用不可**（`技術スタック提案.md` §1）

**決まらないと後工程で起きること**

- 未最適化の原寸画像が拠点リストに10件並び、「画面表示3秒以内」を破る。
- 画像最適化をサーバで行う設計にすると、DB と CPU を奪い合う（単一VM のため）。
- 保存先パスを画面側で直接組み立てると、`技術スタック提案.md` §5 の「保存先を差し替えられる層を挟む」約束に反し、案2移行時のコストが発生する。

**選択肢と推奨案**

**推奨：アップロード時にサーバ側でリサイズして保存し、表示は最適化を掛けない静的配信とする。** 表示のたびに最適化するのではなく、投入時に1回だけ処理する方式が単一VM 構成に適合します。併せて次を確定させる。

- 保存する画像のバリエーション（例：一覧用サムネイル / 詳細用の2種）と各寸法
- 配信経路（IIS 静的配信を推奨。Node プロセスを画像配信で占有させない）
- URL の組み立てを担う層の置き場所（1箇所に集約）
- `next/image` を使うか否か（使う場合はセルフホスト時の設定を `node_modules/next/dist/docs/` で確認すること）

## FE-20. フロントエンドのテスト方針（優先度：中）

**なぜ必要か**

`要件定義残タスク.md` B-5 で Jest + React Testing Library / Playwright とも「**未導入**」、採用可否が未決です。一方、品質要件として「**コードカバレッジ80%以上**」が定められています。

**決まらないと後工程で起きること**

- カバレッジ80%が要件なのに測定手段が無い。
- テストしにくい構造で実装が進み、後からテストを足す段階でコンポーネント分割をやり直すことになる。
- 「予約登録5秒以内」「画面表示3秒以内」を**どう検証するか**の手段が無い（外形監視は本番の話であり、リリース前の確認手段が別に要る）。

**選択肢と推奨案**

**推奨：**

- 単体・コンポーネントテストは Jest + React Testing Library を採用し、CI（lint / 型チェック / build）に追加する
- E2E は Playwright を採用し、対象を絞る（ログイン、スイムレーン表示、予約登録の3シナリオを最低ラインとする。これは外形監視の項目とも一致し、監視用スクリプトの下敷きにできる）
- カバレッジ80%の**対象範囲を明記する**（UI コンポーネントを含む全体なのか、ロジック層に限るのか）。この定義が無いと達成判定ができない
- 日時変換ユーティリティ（FE-14）とバリデーション（FE-04）は**純粋関数として切り出し、単体テストを必須とする**

## FE-21. 「対応ブラウザ最新版」の定義とビルドターゲット（優先度：低）

**なぜ必要か**

「対応ブラウザは Chrome/Firefox/Safari/Edge の**最新版**」とありますが、「最新版」の定義（最新1バージョンのみか、直近N世代か）が不明です。また `tsconfig.json` の `target` は `ES2017` のままです。

**決まらないと後工程で起きること**

- iOS Safari は OS バージョンに依存して古いまま残ることがあり、「最新版のみ」の解釈次第で対応工数が変わる。
- 動作保証範囲が曖昧なため、不具合報告時に「対応外」の判断ができない。
- ビルドターゲットが不必要に古いと、出力コードが冗長になりバンドルが膨らむ（3秒要件に不利）。

**選択肢と推奨案**

**推奨：「各ブラウザの最新2バージョン、iOS Safari は最新2 OS メジャーバージョン」として明文化する。** そのうえで `tsconfig.json` の `target` とブラウザターゲット設定を見直してください（Next.js 16 のビルドターゲット既定値は `node_modules/next/dist/docs/` で確認のこと）。

## FE-22. ダークモード対応の要否（優先度：低）

**なぜ必要か**

現状の `app/globals.css` は `create-next-app` テンプレートのまま `prefers-color-scheme: dark` によるダークモードが有効になっており、`app/page.tsx` にも `dark:` クラスが多数あります。**しかし要件にダークモードの記載は一切ありません。**

**決まらないと後工程で起きること**

- 意図せずダークモードが有効な状態で各画面が実装され、**片方の配色でしかコントラスト比を検証しないまま WCAG AA 違反が残る**（AA はコントラスト比の基準を含み、対応するなら両方の検証が必要）。
- スイムレーンの予約種別の色分けを2セット設計・検証する工数が、見積もりに入っていない。

**選択肢と推奨案**

**推奨：ダークモードは対応しない（ライトのみ）と明示的に決め、テンプレート由来の `prefers-color-scheme` 設定と `dark:` クラスを除去する。** 対応する場合は、**全画面でコントラスト比検証を2回行う**ことを工数に含めてください。

## FE-23. 検索ボックスの検索対象（優先度：低）

**なぜ必要か**

`画面ワイヤー下書き.md` のヘッダに「検索ボックス」がありますが、**何を検索するのかが要求機能に定義されていません。** 要求機能の「予約検索・フィルター機能」は拠点選択・日付指定・お気に入りについての記述で、フリーワード検索には触れていません。

**決まらないと後工程で起きること**

- 検索対象（拠点名 / チーム名 / ユーザー / 予約）が不明なまま UI だけ置かれ、機能しない要素が残る。
- ユーザー検索を含めると、**他ユーザーの情報がどこまで見えてよいか**という個人情報の論点が新たに発生する（`個人情報保護方針.md` との突き合わせが必要）。

**選択肢と推奨案**

**推奨：初期リリースでは検索対象を「拠点名」のみに限定する**（要求機能に定義がある範囲＝拠点の絞り込みに対応するため）。ユーザー検索・チーム検索を含めるなら、要求機能側に機能として追記し、表示可能な項目を個人情報保護方針と整合させてください。対象を定めないなら、ヘッダの検索ボックスは初期リリースでは置かないことを推奨します。
