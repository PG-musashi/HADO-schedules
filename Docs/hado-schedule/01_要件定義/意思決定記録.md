# 意思決定記録

要件定義工程で確定した業務判断を記録します。決定者：プロジェクトオーナー。

反映先の一次情報は `アプリケーション要求機能.md`。本書は決定の背景と波及範囲を残すためのものです。

---

## 2026-07-27 決定（7件）

### D-01. 過去の予約履歴は利用者に表示しない

**決定**：過去の予約は利用者に見せない。ただし将来的に見せる可能性があるため、**記録の保持期間を設定値として可変**にする。

| 項目 | 内容 |
|---|---|
| 解消した矛盾 | 「予約データは日付経過で物理削除」と「自分が参加した予約の履歴を確認」の両立不能 |
| 廃止した機能 | メンバーの操作「自分が参加した予約の履歴を確認」 |
| 実装への影響 | 保持期間をハードコードせず設定値化。予約データは保持期間中システム管理者のみ参照可 |
| 残る未決 | **保持期間の初期値**（`個人情報保護方針.md` は24ヶ月、要求機能は12ヶ月と記載。要統一） |

---

### D-02. 拠点スタッフは自拠点の全予約を編集・削除できる

**決定**：拠点スタッフは、利用者が登録した個人予約を含め、自拠点の全予約を編集・削除できる。

| 項目 | 内容 |
|---|---|
| 解消した矛盾 | 「編集・削除は予約者のみ」と「拠点スタッフはコートの予約状況を登録/削除/編集する」の衝突 |
| 派生して必要になったもの | **他者の予約を編集・削除した際の通知**（予約者本人＋参加登録者全員）。従来は「予約者が削除した場合」しか規定がなかった |
| 実装への影響 | 権限判定は「予約者 or システム管理者 or 自拠点の拠点スタッフ」。拠点スタッフは**自拠点のみ**（他拠点への越境は不可） |
| リスク | 他人の予約を消せる権限のため、監査ログの重要度が上がる |

---

### D-03. 拠点スタッフの同時操作者は常に1人

**決定**：1拠点1アカウントの共有は維持し、**同時に操作するのは常に1人**とする。

| 項目 | 内容 |
|---|---|
| 解消した問題 | 共有アカウント × 二重ログイン後勝ちにより、2人目のログインで1人目が強制ログアウトされる問題 |
| 結論 | 同時操作が1人であれば実害は発生しない。要件の変更は不要 |
| 運用上の注意 | スタッフ交代時、後からログインした者が操作権を得る。前任者の画面は強制切断される |
| 実装への影響 | 認証方式は引き続き**サーバー側セッション必須**（ステートレスJWT単独では後勝ちを実現できない） |

---

### D-04. 欠員発生時は空き枠として再募集する

**決定**：参加登録後に欠員が発生した場合、その枠は空きとして再度募集対象になる。**欠員が発生しても予約自体は成立したまま**とし、キャンセル扱いにしない。

| 項目 | 内容 |
|---|---|
| 実装への影響 | 定員・チーム枠の充足判定は**静的なカウンタではなく、その時点の参加人数・チーム数で都度判定**する |
| 実装への影響 | 「定員に達したら予約不可」は動的判定。満席→欠員→再度空きという状態遷移が発生する |
| テストへの影響 | 満席状態からの離脱→再参加のケースが必須。境界値テストが増える |
| 残る未決 | **チーム内で1人抜けた場合、その1名分の枠を誰が埋められるか**（同一チームのメンバー限定か、誰でも可か）→ D-08 として要決定 |

---

### D-05. チーム枠への参加申請はリーダー承認制

**決定**：他チームが予約したチーム枠への参加申請は、**予約を作成したチームのリーダーが承認**する。

| 項目 | 内容 |
|---|---|
| 派生して必要になったもの | **通知2件の追加**（申請発生時にリーダーへ／承認・却下時に申請者へ）。要求機能の通知一覧に無かったため追記済み |
| 実装への影響 | 参加申請に「申請中／承認済／却下」の状態が必要。申請中は枠を仮押さえするか否かの判断が要る |
| 残る未決 | **個人参加（フリー募集への参加登録）も承認制にするか**。現状の記載は「参加登録」で承認の記述なし → D-09 として要決定 |
| 残る未決 | 申請中の枠を仮押さえするか。しない場合、承認前に他者が埋める競合が起きる |

---

### D-06. 運用体制は1名・週1回対応

**決定**：運用者は1名。対応可能なのは週1回のみ。深夜・週末の即時対応は行わない。

| 項目 | 内容 |
|---|---|
| **重大な影響** | **SLA 99.9%（非計画停止 月約42分）は達成不可能**。障害が金曜夜に起きれば復旧は次回対応日まで待つことになる |
| **重大な影響** | インシデント対応SLA（重大度1＝3日以内初期対応・5日以内復旧）も、週1回対応では保証できない |
| 必要な対応 | **可用性要件とインシデントSLAの改訂**（要決定）。現状の数値のままではリリース初日から未達 |
| 設計方針への影響 | 「人が来るまで自動で耐える」設計に寄せる。サービス自動再起動、ディスク枯渇の予防、アラートの絞り込み（人が見ない通知を作らない） |
| 整合している点 | メンテナンス枠が週1回（0:00〜5:00）であることとは矛盾しない |

### D-07. UAT はオーナー1名が実施・判定、全テストケース合格をリリース条件とする

**決定**：UAT の実施者および合否判定者はプロジェクトオーナー1名。テスト計画で定義した全テストケースに合格したらリリースとする。

| 項目 | 内容 |
|---|---|
| 解消した問題 | UAT の実施主体・受入基準・合格判定基準が未定義だった（＝プロジェクトの完了条件が存在しなかった） |
| 前提となる作業 | **テスト計画とテストケースが未作成**。これが無いとリリース判定基準が機能しない |
| 実務上の負荷 | 4ロールすべてを1名で検証する。ロール横断の検証（例：拠点スタッフが消した予約の通知をメンバーが受け取る）には複数アカウントの併用が必要 |
| 残る未決 | 「全ケース合格」は不具合ゼロを意味するか、軽微な不具合の残存を許容するか → D-10 として要決定 |

---

### D-08. チーム枠はチーム単位で管理し、空きがある限り常に募集する

**決定**（2026-07-27 確定）：チーム予約はチームリーダーが行うため、チーム内の参加人数が満たない場合は考慮しない。募集の規模は募集作成者が設定し、**その枠に空きがある限り常に募集対象**とする。

| 項目 | 内容 |
|---|---|
| 募集規模の決定者 | **募集作成者**。予約登録時にチーム枠数・個人定員を設定する |
| チーム枠の扱い | **1チーム = 1枠**。チーム内の実参加人数は管理しない。人数不足による再募集は行わない |
| 募集の継続条件 | **空きが1つでもあれば募集を継続**。参加者の離脱で空きが生じた場合も同様に再募集 |
| 実装への影響 | チーム枠は「チーム数」で、個人枠は「人数」でカウントする**別種のカウンタ**になる。同一の数値で扱わない |
| 実装への影響 | チームメンバーの個人単位の参加状態を追跡する必要がない。データモデルが単純化される |
| 実装への影響 | 充足判定は単純な「設定枠数 vs 現在の充足数」の比較。特別な閾値（3名等）は設けない |

**経緯**：当初「個人参加が3名未満になった場合に再募集」と記録したが、これは「3名以上いる間は空きがあっても募集しない」という誤った解釈だった。正しくは、募集作成者の設定した枠に対して空きがあれば常に募集する。上表が確定内容。

### D-09. 予約への参加はすべて承認制とする

**決定**：個人参加の場合も、予約を作成したチームのリーダーの承認を必要とする。

| 項目 | 内容 |
|---|---|
| 解消した非対称 | チーム参加のみ承認制で個人参加が自動承認、という不整合を解消 |
| 実装への影響 | 「参加登録」ではなく「参加申請 → 承認/却下」の状態遷移を全参加経路に適用する |
| 通知への影響 | 追加した通知2件（申請時／承認・却下時）を、チーム単位・個人単位の両方に適用 |
| 残る未決 | **チーム予約以外（個人予約・イベント予約・店舗予約）の承認者が未定**。個人予約は予約者本人、イベント/店舗予約は拠点スタッフが自然だが未確定 → D-14 |
| 残る未決 | 申請中の枠を仮押さえするか（D-13 として継続） |

### D-12. SLA 99.9% を撤廃し、障害対応を週1回とする

**決定**：可用性の保証値（SLA 99.9%）は設定しない。障害対応は週1回の定期対応日に行う。

| 項目 | 内容 |
|---|---|
| 撤廃したもの | SLA 99.9%、および「非計画停止は月約42分まで」という制約 |
| 撤廃したもの | インシデント対応の時間SLA（重大度1：3日以内初期対応・5日以内復旧 等） |
| 新しい基準 | 重大度によらず**週1回の定期対応日に対応**。重大度の区分は優先順位付けのために維持 |
| 設計方針への影響 | **人手の介在なしに自動復旧できること**が設計前提になる（サービス自動再起動、ディスク枯渇の予防） |
| 監視方針への影響 | 即時通知は「自動復旧が効かずサービス停止」に限定。他は対応日のダイジェスト。**人が見ない通知を作らない** |
| 副次的な効果 | 非計画停止の枠がなくなり、Windows Update の適用計画に余裕ができた |
| 残るリスク | 障害発生から復旧まで最長1週間。**利用者が認識できる形で示す必要がある**（方法は未定） |
| 推奨 | メンテナンス実施曜日と障害対応日を同一日に統合する |
