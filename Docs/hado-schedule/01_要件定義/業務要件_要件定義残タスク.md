## 0. 本書の範囲

- 本書は**業務要件として不足している事項のみ**を列挙する。DB設計・API設計・インフラ・非機能要件の数値は対象外（それらは `要件定義残タスク.md` および `技術スタック提案.md` が扱う）。
- `アプリケーション要求機能.md` および `技術スタック提案.md` で**すでに決定済みの事項は記載しない**。以下は決定済みとして本書では扱わない。

| 決定済み事項 | 出典 |
|---|---|
| SLA 99.9%／応答時間3秒・予約登録5秒／同時接続100人／スループット5件/分 | 要求機能「システム要件」 |
| 定期メンテナンス週1回 0:00〜5:00、全ユーザー事前通知 | 要求機能「可用性・信頼性要件」 |
| 二重ログイン後勝ち／パスワード要件／ロックアウト3回30分／セッションタイムアウト30分 | 要求機能「ユーザー認証・登録機能」「セキュリティ」 |

| 監査ログ180日／バックアップ30日／予約データは日付経過で物理削除 | 要求機能「データベース要件」「データ保持・削除ポリシー」 |

判定基準：

## 2. 一次情報の矛盾（最優先で解消）

### R-01 予約の編集・削除における拠点スタッフの権限が矛盾している

**優先度：高**

| 項目 | 内容 |
|---|---|
| 矛盾箇所 | 要求機能「予約」：**「予約の編集・削除は予約者のみが可能とする。ただしシステム管理者は全予約の編集・削除が可能」**<br>要求機能「拠点スタッフ」：**「コートの予約状況を登録/削除/編集する」** |
| なぜ必要か | 拠点スタッフが他人の予約を触れるかどうかは、権限モデル・監査ログ・通知仕様の三つを同時に規定する。曖昧なまま実装できない |
| 決まらないと後工程で何が起きるか | 権限判定ロジックが実装者の解釈に委ねられ、拠点スタッフが利用者の予約を削除できる／できないがビルドごとに変わる。受入テストで「仕様が読み取れないため判定不能」となる。個人情報保護方針 4.3「職務上必要な者に限定」との整合も検証できない |

**選択肢**

| 案 | 内容 | 影響 |
|---|---|---|
| 案A | 拠点スタッフが編集・削除できるのは**自拠点のイベント予約・店舗予約・利用不可設定のみ**。利用者の個人予約／チーム予約は参照のみ | 権限が明快。ただし「利用者が来ない予約を消したい」等の運用要望に応えられない |
| 案B | 拠点スタッフは**自拠点のすべての予約**を編集・削除できる | 運用は柔軟。ただし共有アカウント（R-06）と組み合わさると、誰が削除したか特定できない |
| 案C | 削除は不可、時間帯変更等の編集のみ可 | 中間案だが権限の説明が複雑になる |

**推奨：案A**。理由は、(1) 一次情報の「予約者のみ」がより具体的な限定表現であること、(2) 共有アカウント運用（BR-USR-006）では操作者を個人まで特定できないため、他人のデータの削除権を与えるべきでないこと。案Bを採る場合は R-06 の解決（個人識別）を前提条件とする。

### R-02 チーム／リーグ戦チーム所属申請の承認者が確定していない

**優先度：高**

| 項目 | 内容 |
|---|---|
| 矛盾・欠落箇所 | 用語定義「リーグ戦チーム」：**「システム管理者による承認が必要とする」**<br>チームリーダー操作：**「チーム所属申請の承認」「リーグ戦所属チームの承認」**（＝リーダーも承認できる）<br>システム管理者操作：**「メンバーからのチーム/リーグ戦チームの登録申請を承認する」**<br>通知要件：申請時にチームリーダー**と**システム管理者の**両方**に通知（BR-NTF-003/004） |
| なぜ必要か | 「二段階承認（リーダー承認 → 管理者承認）」なのか「いずれか一方が承認すれば成立」なのかで、申請エンティティの状態数・画面・通知回数がすべて変わる |
| 決まらないと後工程で何が起きるか | 申請ステータスの設計ができない（`申請中` のみか、`リーダー承認済/管理者承認待ち` を持つか）。承認通知（BR-NTF-005/006）が二重に飛ぶ／飛ばない不具合が受入時に発覚する |

**選択肢**

| 案 | 内容 |
|---|---|
| 案A | **チームはリーダー単独承認、リーグ戦チームは管理者承認必須**（リーダー承認 → 管理者承認の二段階）。管理者への申請通知は「リーグ戦チームのみ」に限定せず、可視性のため両方送る |
| 案B | 両方とも二段階承認（リーダー → 管理者） |
| 案C | 両方ともリーダー単独承認とし、管理者は事後の是正のみ |

**推奨：案A**。用語定義がリーグ戦チームにのみ「システム管理者による承認が必要」と限定して書かれているため、通常のチームは管理者承認不要と読むのが自然。管理者への申請通知（BR-NTF-004）は「監視目的の通知であり承認アクションを伴わない」と定義すれば矛盾なく成立する。

### R-14 お気に入り拠点の上限が矛盾している

**優先度：中**

| 項目 | 内容 |
|---|---|
| 矛盾箇所 | 要求機能「メンバー」：**「メイン画面から拠点のお気に入りを行う（上限10件）」**<br>要求機能「予約検索・フィルター機能」：**「お気に入り上限は設けない」** |
| なぜ必要か | メイン画面の初期表示対象を決めるフラグであり、上限は画面レイアウト（左ペインの拠点リスト）と初期表示のコート数に直結する |
| 決まらないと後工程で何が起きるか | 上限なしの場合、拠点数が3年後想定の50に達したときにメイン画面が全50拠点のコートを初期表示しうる。応答時間3秒（要求機能「パフォーマンス要件」）を満たせなくなる |

**選択肢**：(A) 上限10件、(B) 上限なし、(C) 上限なしだがメイン画面の初期表示は上位N拠点のみ。

**推奨：案A（上限10件）**。パフォーマンス要件と整合し、記述としてもより具体的。「上限は設けない」の記述を削除する形で一次情報を修正することを提案する。

## 3. 境界条件・例外の欠落

### R-10 定員／チーム枠の充足判定が数式レベルで定義されていない

**優先度：高**

| 項目 | 内容 |
|---|---|
| 既存記述 | 「チーム枠2枠、定員9名の場合、チーム枠以外で3名の個人参加者を受け入れることができる」（用語定義）、「定員はチーム枠を除いた人数を設定する」（予約）、「2〜3チーム（3人以上で1チームを構成）もしくは6〜12人」（補足） |
| 欠落している点 | ① チーム枠1枠が消費する人数（チームの実人数か、固定人数か）<br>② 例示「チーム枠2枠・定員9名 → 個人3名」が成立する計算根拠（9 − 2×3 = 3 なら1枠=3人だが、1チームは最大10名）<br>③ **チーム参加後にそのチームの人数が変動した場合の扱い**（枠内で増減してよいか、超過時どうするか）<br>④ 定員に達した後、参加者が抜けて欠員が出た場合に再度受け付けるか<br>⑤ チーム枠が埋まらないまま予約日を迎えた場合の扱い |
| なぜ必要か | 予約成立の中核ロジック。「予約不可」の判定条件そのものである |
| 決まらないと後工程で何が起きるか | 参加登録APIの受入判定が書けない。実装者ごとに「チーム枠＝人数」「チーム枠＝チーム数」の解釈が割れ、定員超過または過少受付の不具合が本番で発生する。受入テストのテストケースも作成できない |

**選択肢**

| 案 | 内容 |
|---|---|
| 案A | **チーム枠はチーム数の上限**とし、1チームが消費する人数は「そのチームが当該予約に登録した参加人数」。定員は個人参加者のみを数える別カウンタとする。チーム参加人数の上限は予約単位で別途「1チームあたり最大人数」を設定する |
| 案B | チーム枠1枠＝固定人数（例：3名）とし、定員 ＝ 総人数 − チーム枠×固定人数 |
| 案C | チーム枠と定員を完全に独立した2カウンタとし、チーム参加者は定員を一切消費しない |

**推奨：案C を基本とし、案A の「1チームあたり最大人数」を予約項目として追加**。理由は一次情報が「定員はチーム枠を除いた人数」と明記しており、二カウンタ方式が最も忠実であるため。あわせて③④について次を定義することを推奨する。

- ③ チーム人数の変動：チーム枠は**予約時点のチーム登録人数を固定**し、以後の増減を予約に反映しない（反映すると定員判定が予約成立後に覆る）
- ④ 欠員：欠員が出た場合は再度受付可能とする（キャンセル待ち機能は実装しないため、先着順で自然に埋まる）
- ⑤ 未充足：未充足のまま予約日を迎えても予約は有効。自動キャンセルは行わない

### R-17 同一ユーザーの同一時間帯における重複予約の可否

**優先度：高**

| 項目 | 内容 |
|---|---|
| 欠落している点 | 同一ユーザーが同一時間帯に、①別コートの予約を2件登録できるか ②予約者かつ他予約の参加登録者になれるか ③複数予約への参加登録ができるか |
| なぜ必要か | 物理的に同時刻に2つのコートに居ることはできない。放置すると空予約でコートが押さえられ、実利用率が下がる |
| 決まらないと後工程で何が起きるか | 予約テーブルの一意制約／排他制約の設計に反映できない。技術スタック提案 3章の `EXCLUDE USING gist` はコート単位の重複防止を想定しており、ユーザー単位の重複防止制約を初回マイグレーションに含めるかがここで決まる（後から追加すると既存データのクレンジングが必要） |

**選択肢**：(A) ユーザー単位でも時間帯重複を全面禁止、(B) 制限なし、(C) 警告表示のみで登録は許可。

**推奨：案A（全面禁止）**。予約者・参加登録者のいずれの立場でも、同一ユーザーが時間帯の重なる予約に2件紐づくことを禁止する。ただし拠点スタッフのイベント予約・店舗予約は複数コート同時予約（BR-RSV-009）が要件のため、**この制約の対象外**とする。

### R-05 「利用不可設定」が既存予約に与える副作用

**優先度：高**

| 項目 | 内容 |
|---|---|
| 既存記述 | 「コートが利用不可な場合は、拠点スタッフが予約を行う事で利用不可状態を設定する」（要求機能「コート」） |
| 欠落している点 | ① 既に他者の予約が入っている時間帯に利用不可を設定できるか<br>② 設定できる場合、既存予約はどうなるか（自動削除／拠点スタッフが手動削除／併存）<br>③ その際の予約者・参加登録者への通知有無と手段 |
| なぜ必要か | 設備故障・災害等で不可避に発生する運用。最も苦情につながりやすい経路 |
| 決まらないと後工程で何が起きるか | 既存予約と重複する登録は BR-RSV-006（時間帯重複禁止）により**そもそも登録できない**ため、拠点スタッフが利用不可を設定できないまま運用に入る。逆に例外を認めた場合、通知が飛ばず参加者が当日現地で締め出される |

**選択肢**

| 案 | 内容 |
|---|---|
| 案A | 既存予約がある時間帯には利用不可を設定できない。拠点スタッフが先に既存予約を削除する（削除権は R-01 に依存） |
| 案B | 利用不可設定を優先し、既存予約を自動キャンセルして予約者・参加登録者に通知する |
| 案C | 拠点スタッフに強制設定を認め、既存予約は「無効化」状態にして残す |

**推奨：案B**。ただし発生する通知は BR-NTF-002（予約削除通知）を再利用し、**新しい通知種別を追加しない**（記載のない通知機能に該当するため）。案Bを採る場合、通知本文に「拠点都合による中止」である旨を含める必要があるかを R-11 とあわせて判断する。案Aは運用上「削除→設定」の2操作となり、その間に第三者が予約を入れうる隙間が生じる。

### R-04 参加登録の取消・参加者の追加／削除の可能期間

**優先度：高**

| 項目 | 内容 |
|---|---|
| 既存記述 | メンバー操作に「フリーで募集されている予約への参加登録」はあるが、**参加取消の記述がない**。画面ワイヤー 3 には「参加/参加取り消しボタン」がある |
| 欠落している点 | ① 参加登録者が自ら参加を取り消せるか<br>② 取り消せる期限（予約開始の何時間前まで等）<br>③ 予約者が参加者を削除（強制退出）できるか<br>④ 取消／削除時の通知（誰に、どの手段で） |
| なぜ必要か | 参加取消は最も高頻度で発生する操作。画面ワイヤーには存在するが要求機能に無く、要件と画面が乖離している |
| 決まらないと後工程で何が起きるか | 画面ワイヤーに従って実装すると要求機能に無い機能を作ることになる（逆も同様）。取消時に定員カウンタを戻すかどうかも未定のため、定員判定（R-10）が完成しない |

**選択肢**：(A) 参加取消は予約開始時刻まで自由、予約者が参加者を削除する機能は設けない、(B) 参加取消に期限（例：開始24時間前）を設ける、(C) 予約者による参加者削除も認める。

**推奨：案A**。キャンセルポリシーは予約者が自由記述するもの（BR-RSV-011）でシステム的な強制力を持たない設計であり、期限を設けるとポリシー記述と二重管理になる。通知は BR-NTF-001（予約情報の編集通知）に含めるか、通知しないかを R-11 で確定する。

### R-21 予約のキャンセル可能期限とキャンセル料の扱い

**優先度：低**

| 項目 | 内容 |
|---|---|
| 既存記述 | 「各予約には予約登録を行った利用者がキャンセルポリシーを記載することができる」（自由記述テキスト） |
| 欠落している点 | 予約者自身による予約削除に時間的制限を設けるか。キャンセル料の扱い |
| なぜ必要か | 既存の残タスク A-2 に挙がっているため、明示的に決着させる必要がある |
| 決まらないと後工程で何が起きるか | 影響は限定的。ただし「未決のまま」だと基本設計レビューで再度議論になる |

**推奨：システム的な期限・料金制御は設けない**。理由：**決済機能は実装しない**と明記されておりキャンセル料の徴収手段が存在しない。キャンセルポリシーは自由記述のまま、当事者間の運用に委ねる。この方針を要求機能に明記して A-2 の当該項目をクローズすることを推奨する。

### R-08 予約時間の粒度・最小/最大長・予約可能期間

**優先度：中**

| 項目 | 内容 |
|---|---|
| 既存記述 | スイムレーンは30分刻み・10:00〜22:00（要求機能）。画面ワイヤーに「時間ズーム（30分/1時間）」 |
| 欠落している点 | ① 予約の時間粒度が30分固定か（15分予約を許すか）<br>② 最小予約時間・最大予約時間（補足に「ほとんどの場合2時間」とあるが上限規定ではない）<br>③ 何日先まで予約できるか（予約可能期間）<br>④ 過去日時への予約可否<br>⑤ 営業時間外・休業日への予約可否 |
| なぜ必要か | 予約フォームのバリデーション仕様。また予約可能期間はデータ量とスイムレーン取得クエリの範囲を決める |
| 決まらないと後工程で何が起きるか | ③が未定だと、悪意なく1年先まで予約を埋められる。④が未定だと過去日への登録が通り、日付経過による物理削除（BR-RET-001）で即座に消えるデータが生まれる |

**推奨**：粒度は30分固定、最小30分・最大は当日の利用可能時間いっぱい、予約可能期間は**登録日から90日先まで**、過去日時への予約は不可（拠点スタッフの店舗予約も含めて不可）、休業日・営業時間外への予約は不可（利用不可設定は営業日・営業時間内でのみ設定可能）。いずれも一次情報から一意には導けないため、**決定が必要**。

### R-03 予約への参加申請の承認フローが未定義

**優先度：高**

| 項目 | 内容 |
|---|---|
| 既存記述 | メンバー「フリーで募集されている予約への参加登録」、チームリーダー「他のチームが予約した空チーム欄の**参加申請**」 |
| 欠落している点 | ① 「参加登録」（メンバー）と「参加申請」（チームリーダー）は同じものか別か。「申請」なら承認者は誰か<br>② 予約者に承認権があるのか、自動承認か<br>③ 「フリーで募集されている」の判定条件（予約種別ごとに参加を受け付ける／受け付けないの区別があるか） |
| なぜ必要か | 参加が即時成立するか承認待ちを経るかで、定員の消費タイミング（R-10）と競合判定（BR-CNC-001）が変わる |
| 決まらないと後工程で何が起きるか | 参加の状態モデル（`参加確定` のみか `申請中/承認済/却下` を持つか）が決まらず、参加登録テーブルを設計できない。既存の残タスク A-6「参加申請の承認フロー（自動承認 or リーダー承認など）」が未解決のまま基本設計に流れる |

**選択肢**

| 案 | 内容 |
|---|---|
| 案A | 個人の参加登録・チームの空チーム枠参加ともに**自動承認**（先着順で即時確定）。用語も「参加登録」に統一する |
| 案B | 個人は自動承認、チーム枠参加は予約者（＝主催チームのリーダー）の承認を要する |
| 案C | 両方とも予約者の承認を要する |

**推奨：案A**。理由：(1) 承認を挟むと定員が「仮押さえ」状態を持つことになり、先勝ち判定（BR-CNC-001/002）の適用範囲が複雑化する、(2) 参加承認に関する通知は要求機能に一切記載がなく、承認フローを採ると「記載されていない通知機能」を追加せざるを得ない。案B/Cを選ぶ場合は通知要件の追記が必須である。

### R-06 拠点スタッフの共有アカウントと二重ログイン後勝ちが両立しない

**優先度：高**

| 項目 | 内容 |
|---|---|
| 矛盾箇所 | 要求機能「ユーザー認証・登録機能」：**「各アカウントは2重ログイン不可とし、すでにログインされている場合は後勝ちとする（既存接続は強制切断される）」**<br>要求機能「拠点スタッフ」：**「拠点スタッフの登録は各拠点1アカウントとし、拠点のスタッフ間で共有する」** |
| なぜ必要か | 拠点に2名以上のスタッフがいる場合、後からログインした者が前の作業者を強制ログアウトさせる。営業中の拠点で操作の取り合いが起きる |

| 案B | 拠点スタッフも1拠点1アカウントのままで制限を適用し、「同時に操作するのは1名」という運用ルールで回避する |
| 案C | 拠点スタッフをスタッフ個人ごとのアカウントに変更する（要求機能の変更を伴う） |

**推奨：案A**。案Cは監査ログの操作者特定（R-07）も同時に解決するが、一次情報「各拠点1アカウント」の明示的な変更となるため、まず案Aで矛盾を解消し、案Cは別途検討する。**なお、案Aは認証方式の決定（既存残タスク B-1）に対する制約となるため、B-1 の決定前に確定させること。**

**優先度：中**

| 項目 | 内容 |
|---|---|
| 既存記述 | 要求機能「拠点スタッフ」：**「拠点スタッフの操作は全てログに記録される（誰が操作したかはログイン時刻から推測）」** |

### R-11 通知の対象・手段が全ケースで確定していない

**優先度：高**

| 項目 | 内容 |
|---|---|
| 確定している通知 | `業務要件_要件定義書.md` 3.8 の BR-NTF-001〜010（10件） |
| 欠落・不明確な点 | ① **BR-NTF-002（予約削除通知）の手段が未記載**。他の通知はすべて「メールおよびアプリ上」と明記されているのに、予約削除だけ「参加登録者全員に通知される」としか書かれていない<br>② システム管理者／拠点スタッフが他人の予約を編集・削除した場合、**予約者本人**に通知するか（BR-NTF-001/002 の通知先は「参加登録している利用者」であり、予約者本人が含まれるか不明）<br>③ 参加登録・参加取消が発生したとき、予約者に通知するか（R-04 と連動）<br>④ 利用不可設定により既存予約が中止になった場合の通知（R-05 と連動）<br>⑤ アプリ内通知の既読管理・保持期間・表示件数 |

**推奨（決定が必要）**

| 論点 | 推奨 | 根拠 |
|---|---|---|
| ① 予約削除通知の手段 | **メール＋アプリ内**に統一 | 他のすべての通知が同じ手段であり、削除だけ弱める理由がない |
| ② 予約者本人への通知 | 通知先を「**当該予約に紐づく予約者および参加登録者全員（操作者本人を除く）**」と定義し直す | 既存通知の対象拡張であり、新しい通知種別の追加ではない |
| ③ 参加登録・取消時の予約者通知 | **実装しない** | 要求機能に記載がなく「記載されていない通知機能」に該当する。予約詳細画面の参加者リストで確認可能 |
| ④ 利用不可による中止 | BR-NTF-002（削除通知）を再利用する | 新規通知種別を追加しない |
| ⑤ アプリ内通知の保持 | 保持期間90日、既読フラグを持つ | **要決定**（一次情報に記載なし。監査ログ180日とは別物） |

| 既存記述 | チーム：「リーダーが1名＋9名までメンバーを登録する」<br>リーグ戦チーム：「通常のチームと異なる編成をとることがある」（**人数上限の記載なし**） |
| なぜ必要か | 「異なる編成」の具体が不明。上限なしなら無制限にメンバーを登録できる |
| 決まらないと後工程で何が起きるか | バリデーション条件が書けず、実装者が通常チームと同じ10名上限を暗黙に適用する可能性がある |

**推奨**：リーグ戦チームも**リーダー1名＋メンバー9名（最大10名）**とし、通常チームとの違いは「所属関係が独立していること」と「システム管理者の承認が必要なこと」のみと定義する。上限を変える必要がある場合は具体値の指定を求める。

## 7. 次アクション（推奨順）

1. **一次情報の矛盾3件を先に解消する** — R-01（拠点スタッフの予約編集権）、R-02（承認者）、R-14（お気に入り上限）。文書間の食い違いであり、決定というより「どちらを正とするか」の確認で片付く
2. **予約成立ロジックを確定する** — R-10（定員／チーム枠の充足判定）、R-17（同一ユーザー重複予約）、R-03（参加承認）。この3件は初回マイグレーションの制約設計に直結するため、Prisma スキーマ着手前に必須
3. **運用の破綻要因を潰す** — R-06（共有アカウント×二重ログイン）、R-05（利用不可設定）。R-06 は認証方式の決定（既存残タスク B-1）より先に確定させること
4. **通知の網羅表を確定する** — R-11。「記載のない通知は実装しない」制約があるため、確定表がそのまま実装スコープになる
5. 残りの中／低優先度項目を基本設計と並行して確定する
