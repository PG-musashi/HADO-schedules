# 画面UI 要件定義残タスク

作成日：2026-07-26
担当領域：画面UI（UI/UX・アクセシビリティ設計）
対応する確定事項集：`画面UI_要件定義書.md`

---

## 0. 本書の目的と読み方

【残タスク A-1「画面設計・UI要件」】は現状「ワイヤーフレーム／画面遷移図／スイムレーン詳細仕様」の3行しかなく、**基本設計に着手できる粒度になっていない**。本書はこれを画面UI領域として実務レベルまで分解したものである。

各項目は以下の4点で記述する。

1. **なぜ必要か**
2. **決まらないと後工程で何が起きるか**
3. **選択肢と推奨案**
4. **優先度（高／中／低）**

優先度の定義：

| 優先度 | 意味 |
|---|---|
| **高** | 基本設計着手前に決定が必要。決めずに進むと画面設計そのものが手戻りする、または WCAG 2.1 AA という**契約上の必須要件**を満たせなくなる |
| **中** | 基本設計中に決定すればよいが、実装着手前には必要 |
| **低** | 実装フェーズで決定しても影響が局所的 |

### 優先度別サマリ

| 優先度 | 件数 | ID |
|---|---|---|
| 高 | 12 | U-01 〜 U-12 |
| 中 | 16 | U-13 〜 U-28 |
| 低 | 5 | U-29 〜 U-33 |

# A. 優先度：高

---

## U-01 画面遷移図が存在しない（未ログイン時の遷移を含む）

**優先度：高**

### なぜ必要か

現在ある【ワイヤ】は画面の**静的な内容の列挙**であり、画面と画面のつながりが定義されていない。特に以下が完全に欠落している。

- 未ログインで保護されたURLに直接アクセスしたときの挙動（ログイン画面へリダイレクトするのか、公開閲覧を許すのか）
- パスワードリセットの一連の流れ（申請 → メール受信 → 再設定 → ログイン）
- **2重ログイン後勝ちによる強制切断**が発生したときに、切断された側の画面がどこへ行くのか【要求「ユーザー認証・登録機能」】
- **セッション30分タイムアウト**時の遷移先【要求「セキュリティ」】
- 権限のない画面（例：メンバーが `/admin`）にアクセスしたときの遷移
- 予約作成 → 確認 → 完了 → どこへ戻るか
- モーダルとページ遷移の使い分け（予約作成は【ワイヤ】で「モーダル / 画面」と両論併記のまま）

### 決まらないと後工程で何が起きるか

- ルーティング設計（Next.js の App Router 構成、認証ガードの配置）が確定できず、**フロントエンドの骨格を作れない**。
- モーダルかページかが決まらないと、URL 設計・ブラウザバックの挙動・共有可能なリンクの有無が決められず、後から変更すると全画面に波及する。
- 認証ガードの抜けはそのままセキュリティ欠陥になる。UI で隠すだけの実装になり、サーバ側検証と対にならない危険がある。
- E2E テストのシナリオが書けない（【残タスク B-5】の Playwright 導入判断にも影響）。

### 選択肢と推奨案

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| 未ログインでのメイン画面閲覧 | (a) 全面ログイン必須 / (b) スイムレーンは閲覧可・操作は要ログイン | **(a) 全面ログイン必須**。【要求】に「アプリケーションにアクセスする際はログイン認証をする」と明記があり、(b) は要件逸脱。→ U-12 と併せて確定させる |
| 予約作成 | (a) モーダル / (b) 独立ページ / (c) デスクトップはモーダル・モバイルはフルスクリーン | **(c)**。項目数が多くモバイルのモーダルは破綻するため。URL は `?reservation=new` 等で持ち、ブラウザバックで閉じる |
| 権限なしアクセス | (a) 403画面 / (b) メイン画面へリダイレクト | **(a) 403画面**。(b) は「なぜ戻されたか」が伝わらず、支援技術利用者に特に不親切 |
| 強制切断・タイムアウト | (a) 無言でログイン画面 / (b) 理由を明示してログイン画面 | **(b)**。「別の端末でログインされたため、このセッションは終了しました」等、理由が分かる文言を出す |

**成果物**：画面遷移図（Mermaid 記法で `画面UI_要件定義書.md` に追記可）。未ログイン領域・ログイン後領域・権限別領域の3レイヤで描く。

## U-02 スイムレーンのモバイル代替表示が未設計

**優先度：高**

### なぜ必要か

スイムレーンは「横 = 10:00〜22:00 を30分刻み（**24コマ**）」×「縦 = コート数」の二次元表である。1コマを最低 40px としても横幅 960px 超となり、**モバイル（≦640px）では確実に破綻する**。

【ワイヤ】には「モバイル：スイムレーンは日別縦表示へ」という一行があるのみで、

- 「日別縦表示」が具体的に何を指すのか（時間を縦軸にしたレーンか、予約のリストか）
- コートが複数ある拠点でコートをどう切り替えるのか
- 空き枠がモバイルでどう見え、どうタップして予約するのか

が一切定義されていない。レスポンシブ対応は【要求】の必須事項であり、**中核画面がモバイルで使えないことは要件未達に直結する**。

### 決まらないと後工程で何が起きるか

- 実装者が「デスクトップ版を横スクロールさせるだけ」で済ませ、モバイルで実質使用不能な中核画面ができあがる。
- スイムレーンは【ワイヤ】で**最優先実装コンポーネント**に指定されている。最初に作るものが作り直しになる。
- デスクトップ版とモバイル版でデータの持ち方（コート単位 or 時間単位）が変わるため、API のレスポンス形状にも影響しうる。

### 選択肢と推奨案

| 案 | 内容 | 評価 |
|---|---|---|
| (a) 横スクロール継続 | デスクトップと同一 DOM を横スクロール | 実装は最小。二軸スクロールで現在位置を見失う。**非推奨** |
| (b) 時間縦軸レーン（コート切替タブ） | 縦軸に 10:00〜22:00、コートは上部タブで1つずつ切替 | 時間の連続性が保たれ、予約の重なりも見える。コート横断比較はできない |
| (c) 予約リスト表示 | 「10:00-12:00 Aコート チーム予約 残り3名」を時系列カードで縦に並べる | 実装が軽く、スクリーンリーダーとの相性が最良。**空き枠の可視化が弱い** |
| (d) (b) + (c) のハイブリッド | 既定は (b)、「リストで見る」トグルで (c) | 実装コストは上がるが、視覚・非視覚の双方に最適 |

**推奨：(b) を既定とし、(c) をトグルで併設（＝(d)）。**
理由：予約は「空いている時間を探す」タスクであり (c) 単独では空き枠が見えない。一方 (c) は WCAG 対応（U-05）でキーボード・スクリーンリーダー向けの代替手段としてそのまま流用でき、二重投資にならない。

**併せて決めること**：
- ブレイクポイントの切替は 640px でよいか（タブレット 641〜1024px はどちらを使うか → U-24）
- 空き枠のタップ領域（WCAG 2.5.5 相当、最低 44×44px を推奨）

## U-03 状態バリエーション（空／読込中／エラー／権限なし／オフライン）が全画面で未定義

**優先度：高**

### なぜ必要か

現在の【ワイヤ】は**すべて「データが正常に存在する状態」しか描いていない**。実運用では以下が必ず発生する。

| 状態 | 発生例 |
|---|---|
| 空 | 予約が1件もない日、お気に入り拠点0件、所属チームなし、コート0件の新規拠点、参加者0人の予約 |
| 読込中 | 【要求】の応答時間目標が「画面表示3秒以内」であり、**最大3秒間は何かを表示し続ける必要がある** |
| エラー | 通信失敗、サーバエラー、定員超過による予約失敗、同時アクセスによる後勝ち敗北（【要求「エラーハンドリング」】でマイクロ秒比較の先勝ちが定義済み＝**後発ユーザーは必ず失敗する**） |
| 権限なし | 拠点スタッフが他拠点を開いた、メンバーが管理画面URLを直接叩いた |
| オフライン | モバイル利用時のネットワーク断 |
| 業務上の特殊状態 | **満席**、**利用不可コート**、**営業時間外**、**休業日** |

特に「同時アクセス時は先勝ち、敗者は失敗」というルールが要件で確定している以上、**予約失敗時のUIは必須**である。

### 決まらないと後工程で何が起きるか

- 実装者ごとに「読込中はスピナー」「いや骨組み表示」とバラバラになり、UI の一貫性が失われる。
- 空状態が未定義だと、初期リリース直後（予約0件・拠点20件・お気に入り0件）の画面が真っ白になり、第一印象が最悪になる。
- 予約失敗のUIがないと、後勝ちで負けたユーザーは「押したのに何も起きない」と認識し、二重送信を繰り返す。
- 動的更新（他ユーザーの予約で満席化）をスクリーンリーダーに伝えないと WCAG 4.1.3（ステータスメッセージ）違反になる。

### 選択肢と推奨案

**全画面共通の状態設計テンプレートを1枚作り、各画面はそれを参照する形にする**ことを推奨する。

| 状態 | 推奨表現 |
|---|---|
| 読込中 | スケルトン（骨組み）表示。スピナーは全画面ブロックのみに限定。`aria-busy="true"` を付与 |
| 空 | 「表示できる〇〇はありません」＋**次の行動への導線**（例：「拠点をお気に入りに追加すると、ここに表示されます」＋拠点一覧へのリンク） |
| エラー | エラー種別ごとの文言（U-06）＋**再試行ボタン**。全画面エラーと部分エラーを区別する |
| 権限なし | 403 画面。「この拠点を管理する権限がありません」＋自拠点へ戻る導線 |
| オフライン | 画面上部に固定バナー「オフラインです。接続が回復すると自動で再読み込みします」 |
| 満席 | 参加ボタンを `disabled` にせず、押下時に理由を伝える／または「満席（9/9名）」ラベル＋ボタン非活性＋`aria-describedby` で理由を紐付け |
| 利用不可コート | レーン全体を斜線パターン＋「利用不可」テキスト（色のみに依存しない） |
| 営業時間外・休業日 | 該当レンジをグレーアウト＋「営業時間外」テキスト。休業日は日付選択時点で明示 |

**成果物**：状態バリエーション定義表（画面 × 状態のマトリクス）。

## U-04 権限別の画面表示差分マトリクスが未作成

**優先度：高**

### なぜ必要か

【要求「利用者」】にはロール別の**操作**は列挙されているが、それが**どの画面のどの要素として現れるか**が対応付けられていない。【残タスク A-3】にも「機能ごとのCRUD権限マトリクス」が未完として残っている。

画面UI領域として特に未解決なのは以下。

- 予約詳細モーダルの「編集」「削除」ボタンは、**予約者本人**にしか出さない。では拠点スタッフが自拠点の他人の予約を見たときはどうか（【要求「拠点スタッフ」】には「コートの予約状況を登録/削除/編集する」とあり、【要求「予約」】の「予約の編集・削除は予約者のみ」と**衝突する可能性がある**）
- **拠点スタッフは各拠点1アカウントの共有**である。この共有アカウントにマイページ（プロフィール画像・自己紹介・プレースタイル）は存在するのか
- システム管理者はメイン画面で全拠点を横断表示できるのか、拠点を1つ選ぶのか
- メンバーはチーム管理画面を閲覧できるのか（【ワイヤ 5】は編集前提の記述のみ）
- 参加者リストで、他ユーザーのどこまで（実名・画像・プロフィール）が見えるか（【個情】6.2 で「チームリーダーが所属チーム員の予約情報を確認する場合」が第三者提供の例外に挙がっている＝**表示範囲は個人情報の論点でもある**）

### 決まらないと後工程で何が起きるか

- 実装者が推測でボタンの出し分けを実装し、**権限昇格の穴**が生まれる。特に「UIで隠しただけでAPIは誰でも叩ける」状態は典型的な脆弱性で、【要求】のペネトレーションテストで指摘される。
- 拠点スタッフと予約者の権限衝突が未解決のまま実装されると、業務が回らないか、逆に他人の予約を勝手に消せる事故になる。
- テストケースが作れない（ロール4種 × 画面13種の組み合わせ検証ができない）。

### 選択肢と推奨案

**「画面 × 要素 × ロール」の3軸マトリクスを作成する。** セルの値は「表示＋操作可 / 表示のみ / 非表示」の3値とする。

権限衝突については以下を推奨する。

| 論点 | 推奨案 |
|---|---|
| 拠点スタッフと予約者の編集権限 | 拠点スタッフは自拠点の予約を**削除できるが編集はできない**（利用不可設定・営業都合のキャンセルという実務に必要な最小権限）。削除時は参加者全員に通知される既存フロー【要求「予約」】に乗せる |
| 共有アカウントのマイページ | 拠点スタッフはマイページを持たず、**拠点管理画面のみ**。プロフィール系項目は非表示（共有アカウントに個人プロフィールは不整合） |
| 参加者リストの表示範囲 | 表示は**プレイヤーネームとプロフィール画像のみ**。メールアドレスは誰にも表示しない（【個情】の最小限利用の原則に整合） |
| UI と API の対 | UI の出し分けは**利便性のためであり権限制御ではない**旨を要件に明記し、同じ判定をサーバ側にも必ず置くことを設計原則とする |

## U-05 WCAG 2.1 AA を満たすための具体基準が未定義

**優先度：高**

### なぜ必要か

【要求】は「アクセシビリティは WCAG 2.1 AA に準拠する」と**必須要件として明記**しているが、それを満たすための具体基準が一切ない。「AA準拠」は宣言だけでは達成できず、以下を要件として数値・ルール化しないと必ず未達になる。

本システム固有の高リスク箇所は明白である。

| リスク箇所 | 該当する達成基準 | なぜ危険か |
|---|---|---|
| 予約種別（個人/チーム/イベント/店舗）の区別 | **1.4.1 色の使用** | 色分けだけで4種を表すのが最も自然な実装であり、放置すると確実に違反する |
| 満席・利用不可・営業時間外の表示 | **1.4.1** | 同上。グレーアウトだけでは伝わらない |
| 予約ブロックの文字と背景 | **1.4.3 コントラスト（最低限）** | 種別ごとに背景色を変えると、白文字が乗らない色が必ず出る |
| **スイムレーンのセル操作** | **2.1.1 キーボード** | 24コマ × コート数のグリッドをキーボードで走査する設計は自明でなく、放置すればマウス専用UIになる。**AA違反として最も重い** |
| 予約ブロックの読み上げ | **4.1.2 名前・役割・値** | 「██」としか読まれない block が量産される |
| 他ユーザーによる満席化・予約追加 | **4.1.3 ステータスメッセージ** | 動的更新が無言だと支援技術利用者は状況変化に気づけない |
| フォーカス表示 | **2.4.7 フォーカスの可視化** | `outline: none` は多くの UI ライブラリの既定挙動に含まれる |
| 拠点画像・プロフィール画像・チーム画像 | **1.1.1 非テキストコンテンツ** | 【個情】で3種の画像の存在が確定済み |
| 予約フォームのエラー | **3.3.1 / 3.3.3** | エラーを入力欄に紐付けないと、どこが悪いか読み上げられない |
| モバイルの横スクロール | **1.4.10 リフロー** | 320px 幅で二軸スクロールを強制すると違反（→ U-02 と直結） |

### 決まらないと後工程で何が起きるか

- 実装完了後の ui-ux-reviewer レビューで**重大度「高」の指摘が大量発生**し、スイムレーンの作り直しになる。キーボード操作の後付けは DOM 構造の変更を伴うため、最も高くつく手戻りである。
- 「AA準拠」を満たしたかを**誰も判定できない**。受入テスト（UAT）の合否基準がない。
- 【要求】の明記事項であるため、未達は**要件未達＝納品物の欠陥**になる。

### 選択肢と推奨案

**「WCAG 2.1 AA 実装基準書」を要件定義成果物として作成する。** 最低限、以下を確定させる。

| 項目 | 推奨基準 |
|---|---|
| 色以外の情報伝達 | 予約種別は **色＋アイコン＋テキストラベル**の3重で示す。満席は「満席」テキスト、利用不可は斜線パターン＋テキスト |
| コントラスト比 | 通常文字 **4.5:1 以上**、18pt(24px)以上または14pt(18.66px)太字は **3:1 以上**、UIコンポーネントの境界は **3:1 以上**（1.4.11）。カラーパレット確定時に全組み合わせを検証し、検証結果を残す |
| キーボード操作 | スイムレーンを `role="grid"` として実装し、**矢印キーでセル移動 / Enter で予約作成 or 詳細表示 / Home・End で時間端へ / PageUp・PageDown でコート移動**。Tab はグリッド全体で1ストップ（ロービングtabindex） |
| アクセシブル名 | 予約ブロックは「**10:00-12:00 Aコート チーム予約 残り3名**」相当の名前を持つ。空き枠は「10:00 Aコート 空き 予約する」 |
| ライブリージョン | 予約の追加・満席化・削除は `aria-live="polite"` で通知。エラーは `role="alert"` |
| フォーカス | `outline: none` の単独使用を禁止（代替の可視表示が必須）。フォーカス順序＝視覚順序。モーダルはフォーカストラップ＋閉じたら呼出元へ復帰 |
| 代替テキスト | 拠点画像＝「〇〇店の外観」、プロフィール画像＝「〇〇さんのプロフィール画像」、装飾画像は `alt=""` |
| フォーム | 全入力に `<label>` を関連付け。エラーは `aria-describedby` で入力欄に紐付け、`aria-invalid` を付与 |
| タッチターゲット | 44×44px 以上（2.5.5 は AAA だがモバイル前提のため AA 相当の運用基準として採用を推奨） |
| 検証方法 | axe DevTools 等の自動検査＋**キーボードのみでの予約完了**手動テストを受入基準に含める |

## U-06 エラーメッセージ・確認ダイアログの文言方針が未定義

**優先度：高**

### なぜ必要か

【残タスク A-7】に「エラーコード設計」「クライアント向け/管理者向けのメッセージ方針」が未完として残っているが、**画面に実際に出す日本語文言**は誰も書いていない。

本システムには「ユーザーが必ず遭遇するが原因が自明でない失敗」が要件レベルで確定している。

| 状況 | 要件上の根拠 |
|---|---|
| 同時アクセスで先勝ちに負けた | 【要求「エラーハンドリング」】マイクロ秒比較で先勝ち |
| 定員に達していて予約できない | 【要求「予約」】定員となった場合は予約不可 |
| 定員とチーム枠の整合性エラー | 【ワイヤ 2】動的バリデーション |
| ログイン3回失敗でアカウントロック（30分） | 【要求「セキュリティ」】 |
| 別端末でログインされ強制切断された | 【要求】2重ログイン後勝ち |
| セッション30分タイムアウト | 【要求】 |
| パスワードが要件を満たさない | 【要求】8文字以上・大小英字・数字 |
| 所属チーム申請が既に1件ある | 【要求「メンバー」】1つのみ申請可能 |
| チーム定員（リーダー1＋9名）超過 | 【要求「チーム」】 |
| 利用可能時間を 10:00〜22:00 より短縮しようとした | 【要求「コート」】 |
| 予約削除（参加者全員に通知が飛ぶ） | 【要求「予約」】→ **確認ダイアログ必須** |

### 決まらないと後工程で何が起きるか

- 実装者が「エラーが発生しました」で埋め、ユーザーが次に何をすればいいか分からなくなる。特に「後勝ちで負けた」ケースは、原因を説明しないと**同じ操作を繰り返してサーバ負荷を上げる**。
- 「参加者全員に通知が飛ぶ削除」に確認ダイアログがないと、誤操作で不可逆な通知メールが全参加者に送信される。
- 文言がバラバラだと、システム全体の信頼感が損なわれる。
- 【残タスク A-7】のエラーコードと画面文言が対応付かず、問い合わせ対応（システム管理者宛メールのみ）で原因特定ができない。

### 選択肢と推奨案

**「エラーコード ↔ 画面文言 ↔ 次の行動」の対応表を作る。** 文言は次の3要素を必ず含める方針を推奨する。

> **① 何が起きたか ② なぜ起きたか ③ 次に何をすればよいか**

具体案（抜粋）：

| 状況 | 推奨文言 |
|---|---|
| 同時予約に負けた | 「この枠は、ほぼ同時に他の方が予約されました。別の時間帯をお選びください。」＋ 再読込ボタン |
| 定員到達 | 「この予約は定員（9名）に達しているため、参加登録できません。」 |
| チーム枠不整合 | 「定員はチーム枠を除いた人数で入力してください。現在チーム枠2枠が設定されています。」 |
| アカウントロック | 「パスワードを3回続けて間違えたため、このアカウントは30分間ロックされています。30分後に再度お試しいただくか、パスワードをリセットしてください。」＋ リセットへのリンク |
| 強制切断 | 「別の端末でログインされたため、このセッションは終了しました。続けて利用するには再度ログインしてください。」 |
| セッションタイムアウト | 「30分間操作がなかったため、自動的にログアウトしました。入力中の内容は保存されていません。」 |
| 権限なし | 「この拠点を管理する権限がありません。管理できるのは〇〇店のみです。」 |
| 予約削除の確認 | 「この予約を削除します。**参加登録している3名全員に削除通知メールが送信されます。**この操作は取り消せません。」［削除する］［キャンセル］ |
| 通信失敗 | 「通信に失敗しました。ネットワーク接続を確認して、もう一度お試しください。」＋ 再試行ボタン |

**禁止事項として要件化する**：「エラーが発生しました」「不正な値です」など、原因も次の行動も示さない文言は使用しない。

**併せて決めること**：敬体（です・ます）で統一、ユーザーを責める表現（「〜が間違っています」）を避ける、といったライティング方針（→ U-29）。

## U-07 コート数増加時のスイムレーン挙動・ヘッダ固定が未定義

**優先度：高**

### なぜ必要か

【残タスク A-1】に「表示列数、スクロール挙動」として挙がったまま未決。【要求「スケーラビリティ」】では **3年後に50拠点**を想定しており、1拠点あたりのコート数も「1つの拠点に複数コート存在する場合もある」としか書かれていない。**1拠点の最大コート数が定義されていない。**

決めるべきは以下。

- 1拠点あたりのコート数の想定上限（レーン行数の上限）
- 行数が画面に収まらないときの挙動（縦スクロール / ページング / 仮想化）
- 横方向：10:00〜22:00 の24コマを常時全表示するか、横スクロールさせるか
- **スクロール時に時間軸ヘッダ（上）とコート名（左）を固定するか**
- 「すべての拠点」を選んだときに複数拠点のコートを縦に並べるのか、拠点は必ず1つ選ぶのか

### 決まらないと後工程で何が起きるか

- 「1画面に収まる前提」で実装した後にコート10面の拠点が現れ、レイアウトが崩壊する。
- ヘッダ固定は CSS の `position: sticky` の入れ子構造に依存し、**DOM構造を後から変えることになる**。テーブル要素かグリッドかという根本的な選択にも波及する。
- 仮想化（react-window 等）を後付けするとキーボード操作（U-05）と衝突する（DOM に存在しない要素にフォーカスできない）。**U-05 と同時に決める必要がある。**
- 【要求「パフォーマンス要件」】の「画面表示3秒以内」を満たせるかの見積りができない。

### 選択肢と推奨案

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| 横方向 | (a) 24コマ全表示（1コマ可変幅） / (b) 固定幅＋横スクロール | **(a) デスクトップは全表示**。時間全体を俯瞰できることがスイムレーンの価値。1コマ最小40px × 24 = 960px はデスクトップ（≧1025px）で成立する |
| 縦方向 | (a) 全行表示＋ページ縦スクロール / (b) 領域内スクロール / (c) 仮想化 | **(b) 領域内スクロール**。当面のコート数（現実的に1拠点10面以下）では仮想化は不要。**仮想化は採用しない**ことを明記し、キーボード操作の設計を単純に保つ |
| ヘッダ固定 | (a) 固定する / (b) しない | **(a) 時間軸ヘッダ（上）とコート名（左）の両方を `sticky` で固定** |
| コート数上限 | — | 業務側に確認し、**1拠点あたりの想定最大コート数を要件に明記する**（未定なら暫定10面として設計） |
| 複数拠点同時表示 | (a) 不可（1拠点のみ） / (b) 可 | **(a) 1拠点のみ**。【要求】は「拠点を選択するとコートごとに」と単数を前提にしている |

## U-08 ズーム単位が 30分固定か可変かで記述が矛盾

**優先度：高**

### なぜ必要か

- 【要求 概要】：「拠点を選択するとコートごとに**30分刻み**のスイムレーンが表示される」
- 【ワイヤ 1】：「上部に日付ピッカーと**時間ズーム（30分/1時間）**」

30分固定なのか、30分と1時間を切り替えられるのかが確定していない。これはスイムレーンの**データ構造とレンダリングの前提そのもの**である。

### 決まらないと後工程で何が起きるか

- 可変を後から足すと、コマ幅・ブロック位置計算・キーボード移動単位・アクセシブル名の全てを作り直すことになる。
- 1時間ズームでは 30分単位の予約（10:00-10:30）を1コマ内に表現する必要があり、**予約ブロックの描画ロジックが根本的に変わる**。
- ズーム状態を保存するか（フィルター条件保存 → U-15 の対象か）も決まらない。

### 選択肢と推奨案

| 案 | 内容 | 評価 |
|---|---|---|
| (a) 30分固定 | ズーム機能を持たない | 【要求】本文に忠実。実装が単純でキーボード操作（U-05）も素直。**24コマはデスクトップで全表示可能**なため、ズームの実用的必要性が薄い |
| (b) 30分/1時間 可変 | 【ワイヤ】通り | 1時間表示の利点は「一覧性」だが、そもそも全時間帯が1画面に収まるため利得が小さい。実装コストとアクセシビリティ対応コストが増える |

**推奨：(a) 30分固定。** 【要求】が上位ドキュメントであり、【ワイヤ】の「時間ズーム」は下書き段階の案と解釈する。ズームの代わりに **U-02 のモバイル切替**へリソースを振るべきである。
決定後は【ワイヤ】側の記述も更新するか、本決定が優先することを明記する。

## U-09 予約ブロックの視覚表現ルールが未定義

**優先度：高**

### なぜ必要か

スイムレーン上の予約ブロックは、以下**5種類の情報を同時に**伝える必要があるが、その表現ルールが存在しない。

1. **予約種別**（個人 / チーム / イベント / 店舗）— 4値
2. **定員の充足状態**（例：6/9名、満席）
3. **チーム枠の残り**（例：チーム枠2枠中1枠空き）
4. **利用不可コート**（拠点スタッフが予約として登録したブロック）
5. **自分が関与しているか**（自分の予約 / 参加中 / 無関係）※補完だが実用上必須

【ワイヤ 1】は「開始時間/終了時間/タイトル/定員」としか書いておらず、種別・チーム枠・利用不可の表現が抜けている。

### 決まらないと後工程で何が起きるか

- 実装者が色分けだけで4種を表現し、**WCAG 1.4.1（色の使用）違反**になる（→ U-05 と直結）。
- 「他チームの空きチーム枠に参加申請する」というチームリーダーの主要操作【要求「チームリーダー」】が、**画面上でどのブロックに空きがあるか分からず実行できない**。要求機能が画面で実現できていない状態になる。
- 30分ブロック（幅40px程度）に4種の情報を詰め込めず、実装時に場当たり的な省略が発生する。

### 選択肢と推奨案

**「ブロック幅に応じた段階的な情報省略ルール」を定義する**ことを推奨する。

| 情報 | 推奨表現 |
|---|---|
| 予約種別 | **左端の色帯＋アイコン**（個人=人、チーム=複数人、イベント=旗、店舗=工具）＋アクセシブル名内のテキスト。色は補助であり単独で意味を担わせない |
| 定員充足 | 「6/9名」テキスト。満席時は背景をハッチングし「満席」を明示 |
| チーム枠残り | 「チーム 1/2枠」。空きがある場合のみ強調表示 |
| 利用不可 | 斜線パターン＋「利用不可」テキスト。クリック不可 |
| 自分の関与 | 左端に太いアクセントボーダー＋アクセシブル名に「（参加中）」 |
| 幅が狭い場合 | 幅60px未満：種別アイコンのみ。ホバー/フォーカスでツールチップに全情報。**ただしアクセシブル名は常に完全な文字列を保持する** |

**アクセシブル名の統一書式（推奨）**：
`{開始}-{終了} {コート名} {予約種別} {タイトル} 定員{現在}/{上限}名 チーム枠{残}枠空き{（参加中）}`
例：`10:00-12:00 Aコート チーム予約 週末練習 定員6/9名 チーム枠1枠空き`

## U-10 空き枠から予約作成への導線が未定義

**優先度：高**

### なぜ必要か

「空いている枠を見つけて予約する」が本システムの**最も基本的なユーザーフロー**であるにもかかわらず、【ワイヤ 1】には「ブロッククリックで詳細モーダル表示」（＝既存予約の話）しか書かれておらず、**空き枠側の操作が定義されていない**。

決めるべきは以下。

- 空き枠は1コマ（30分）単位でクリックできるのか
- ドラッグで時間範囲を選択できるのか（実務上「2時間予約が多い」【要求 補足】ため、30分1コマから始まると必ず終了時刻の修正が必要になる）
- クリックした位置の拠点・コート・日付・開始時刻が予約作成フォームに**初期値として引き継がれるか**
- **キーボードのみで同じ操作ができるか**（→ U-05）
- 営業時間外・休業日・利用不可コートの枠はクリックできないことをどう伝えるか

### 決まらないと後工程で何が起きるか

- 引き継ぎが実装されないと、ユーザーはスイムレーンで見つけた枠を予約フォームで**もう一度手入力する**ことになり、中核体験が破綻する。
- ドラッグ選択の有無は、スイムレーンのイベントハンドリング設計（mousedown/mousemove/mouseup vs click）を根本から変える。後付け不可に近い。
- キーボードでの空き枠選択が設計から漏れると、WCAG 2.1.1 違反（U-05）。

### 選択肢と推奨案

| 論点 | 推奨 |
|---|---|
| 起動方法 | 空きコマの**クリック／Enterキー**で予約作成を開く |
| 初期値 | 拠点・コート・日付・開始時刻を引き継ぐ。**終了時刻の既定は「開始+2時間」**（【要求 補足】に「ほとんどの場合2時間」と明記があるため、これを既定値にすることが要件に整合する） |
| ドラッグ選択 | **初期リリースでは実装しない**。クリック＋フォーム上での終了時刻変更で足りる。実装するならキーボード代替（Shift+矢印での範囲拡張）を同時に設計すること |
| 操作不可の枠 | 営業時間外・休業日・利用不可は**フォーカス可能だが操作不可**とし、フォーカス時に理由を読み上げる（`aria-disabled="true"` ＋ 説明）。`disabled` にしてフォーカス不能にすると理由が伝わらない |
| 空きコマのアクセシブル名 | 「10:00 Aコート 空き 予約を作成」 |

## U-11 お気に入り上限の記述が矛盾している（10件 / 上限なし）

**優先度：高**

### なぜ必要か

同一ドキュメント【要求】内で相反する記述がある。

- 【要求「メンバー」】：「メイン画面から拠点のお気に入りを行う（**上限10件**）」
- 【要求「予約検索・フィルター機能」】：「お気に入り**上限は設けない**」

### 決まらないと後工程で何が起きるか

- 画面側：上限がある場合、**11件目を追加しようとしたときのUI**（ボタン非活性化、エラーメッセージ、上限到達の事前表示）が必要になる。上限なしなら不要。
- 左ペインの拠点リスト設計に影響する。上限なしの場合、3年後50拠点すべてがお気に入りになりうるため、**お気に入りセクションのスクロール／折りたたみ**が必要になる。
- API・DB のバリデーションにも波及する（本書の担当外だが、要件矛盾として上位に上げる必要がある）。

### 選択肢と推奨案

| 案 | 評価 |
|---|---|
| (a) 上限10件 | 左ペインが常に一覧可能な長さに収まり、UI設計が単純になる。上限到達時の文言が必要 |
| (b) 上限なし | 制約が減る一方、お気に入り数に応じた左ペインの可変設計が必要 |

**推奨：(a) 上限10件。** 「メンバーの操作」節の記述の方が具体的であり、初期20拠点・3年後50拠点という規模に対して10件は実用上十分。上限到達時の文言は U-06 の対応表に含める（例：「お気に入りは10件までです。他の拠点を解除してから追加してください。」）。

**いずれにせよ、要件ドキュメント側の記述を一本化する必要がある。**

## U-12 未ログイン時にメイン画面を閲覧できるかが未確定

**優先度：高**

### なぜ必要か

【要求】は「アプリケーションにアクセスする際はログイン認証をする」としているが、【ワイヤ】のメイン画面はヘッダに「検索ボックス」を持ち、公開閲覧を想定しているようにも読める。**メイン画面が公開かログイン必須かで、システムの表面積が根本的に変わる。**

また【要求】は「メイン画面の初期表示は**ログインユーザーの**お気に入り拠点」としており、未ログインユーザーの初期表示が定義されていない。

### 決まらないと後工程で何が起きるか

- ルーティング／認証ガードの配置（U-01）が確定しない。
- 公開する場合、未ログインユーザーに他人の予約タイトル・参加者が見えることになり、**【個情】の第三者提供の原則に抵触する**。個人情報保護方針の改訂が必要になる。
- SEO・OGP・キャッシュ戦略の要否が決まらない。
- 未ログイン時の初期表示（お気に入りがない状態）の仕様が空白になる。

### 選択肢と推奨案

**推奨：全画面ログイン必須。** 未ログインでアクセスした場合は SCR-A01 ログイン画面へリダイレクトし、ログイン後に元のURLへ戻す。
理由：【要求】本文に明記があること、および【個情】との整合。公開閲覧を採用する場合は、**個人情報保護方針の改訂が必須の前提条件**となる旨を明記すること。

## U-13 通知UI（ヘッダのベル・通知一覧・既読管理）が未設計

**優先度：中**

**なぜ必要か**：【ワイヤ 1】ヘッダに「通知」があるのみ。一方【要求「キャンセルポリシー管理・通知機能」】は**7種類の通知**（予約編集、チーム申請、承認/却下×2系統、システム管理者宛、メンテナンス）を「メールおよび**アプリ上で**」通知すると定めている。アプリ内通知の受け皿が設計されていない。

**決まらないと**：通知が実装されず要件未達になるか、実装者が独自に作って未読管理・保持期間・通知の削除がバラバラになる。「記載されていない通知機能は実装しない」【要求】という制約があるため、**通知の種類を確定させないと実装範囲が決まらない**。

**選択肢と推奨案**：
- 形態：(a) ヘッダのドロップダウンパネルのみ / (b) 独立した通知一覧画面 / (c) 両方 → **推奨 (c)**：パネルで直近5件＋「すべて見る」で一覧画面へ
- 未読管理：未読バッジ（件数）＋既読/未読の区別。バッジは `aria-live` で更新を通知
- 保持期間：**要決定**（【要求】に記載なし。予約データは日付経過で物理削除されるため、関連通知の扱いを決める必要がある）
- 通知種別ごとの遷移先を対応表にする（例：チーム申請通知 → SCR-T01）

## U-14 ヘッダ検索ボックスの検索対象が未定義

**優先度：中**

**なぜ必要か**：【ワイヤ 1】に「検索ボックス」があるが、**何を検索するのかが書かれていない**。候補は拠点名、コート名、予約タイトル、ユーザー名、チーム名など。【要求「予約検索・フィルター機能」】は拠点選択と日付指定のみを定義しており、フリーテキスト検索は要求されていない。

**決まらないと**：実装者が推測で作り、要件にない機能を実装する（＝スコープ膨張）か、飾りの検索ボックスが残る。ユーザー名の検索は【個情】上の論点にもなる。

**選択肢と推奨案**：
- (a) **検索ボックスを削除する** — 【要求】に検索要求がない。**推奨**
- (b) 拠点名のみのインクリメンタル検索に限定 — 3年後50拠点で左ペインが長くなることへの対策として合理的。採用する場合は左ペイン内の絞り込みとして配置し、ヘッダには置かない
- ユーザー名・予約タイトルの横断検索は**要件外のため実装しない**ことを明記する

## U-15 フィルター条件の保存仕様が未定義

**優先度：中**

**なぜ必要か**：【要求】に「各拠点を選択し、フィルター条件を保存する」とあるが、**何を（拠点だけか、日付・ズームも含むか）／どこに（サーバかブラウザか）／いつまで**保存するかが不明。お気に入り機能との役割の違いも曖昧。

**決まらないと**：お気に入りと重複した似た機能が2つできる。保存先が未定だと、端末をまたいだときの挙動が非決定になる。

**選択肢と推奨案**：
- 保存対象：**最後に選択した拠点のみ**（日付は常に当日に戻す方が事故が少ない）
- 保存先：(a) サーバ（ユーザー設定） / (b) localStorage → **推奨 (a)**。端末をまたいでも一貫し、【個情】の設定Cookie（保持12ヶ月）とも整合させやすい
- お気に入りとの関係：お気に入り＝**リストの並び順と初期表示の決定**、フィルター保存＝**最後の選択状態の復元**と役割を明確に分離して要件に書く

## U-16 日付ピッカーの仕様が未定義

**優先度：中**

**なぜ必要か**：選択可能な日付範囲（過去は見られるか／何日先まで予約できるか）が要件に存在しない。【要求「データ保持・削除ポリシー」】は「**予約データは日付が過ぎた時点で物理削除する**」としており、**過去日を選んでも何も表示されない**という重要な帰結がある。

**決まらないと**：過去日を選べる UI にすると必ず空表示になり、ユーザーは不具合と誤認する。予約可能な上限日が未定だと、1年先の予約が入る事故が起きうる。

**選択肢と推奨案**：
- 過去日：**選択不可にする**（当日より前をグレーアウト）。物理削除の仕様と整合
- 未来日：**要決定**（業務側確認事項）。暫定案として**90日先まで**。上限を超える日はグレーアウト
- 休業日：日付ピッカー上で休業日を視覚的に区別する（色のみに依存しない → U-05）
- 前日／翌日への1タップ移動を併設（【ワイヤ】の日付ピッカーに加え、実用上必須）

## U-17 確認ダイアログの適用範囲が未定義

**優先度：中**

**なぜ必要か**：不可逆かつ副作用のある操作が要件上いくつも存在する。特に**予約削除は参加登録者全員へ通知メールが飛ぶ**【要求「予約」】ため、確認なしの削除は事故になる。

**決まらないと**：誤操作による不可逆な通知送信が発生する。逆に確認過多だと日常操作が煩わしくなる。

**選択肢と推奨案**：確認ダイアログを出す操作を要件として列挙する。
- **必須**：予約の削除（参加者への通知が発生）、チームメンバーの追放、コートの削除、拠点の削除、ユーザーの削除、退会
- **不要**：お気に入りのON/OFF、参加登録（取り消し可能なため）
- 破壊的操作のダイアログは**影響範囲を数値で明示**する（「参加者3名に通知されます」）
- ダイアログはフォーカストラップ＋`role="alertdialog"`＋Escで閉じる。既定フォーカスは**キャンセル側**に置く

## U-18 フォームバリデーションの表示方式が未定義

**優先度：中**

**なぜ必要か**：【ワイヤ 2】に「参加者上限の動的バリデーション」とあるのみで、いつ検証するか（入力中／フォーカスアウト／送信時）、どこにエラーを出すか（項目直下／画面上部サマリ／両方）が未定。パスワード要件（8文字・大小英字・数字）の提示方法も未定。

**決まらないと**：画面ごとに検証タイミングがバラバラになる。エラーを入力欄に紐付けない実装になると WCAG 3.3.1 違反（→ U-05）。

**選択肢と推奨案**：
- タイミング：**フォーカスアウト時に検証、エラー表示後は入力中に再検証して解除**（入力中にいきなり赤くしない）
- 表示位置：**項目直下に個別エラー ＋ 送信失敗時は画面上部にサマリ**（サマリの各項目は該当欄へのリンク）
- 紐付け：`aria-describedby` でエラーを入力欄に関連付け、`aria-invalid="true"` を付与
- パスワード：入力前から要件を静的に提示し、満たした項目にチェックを付ける
- 送信ボタン：**未入力でも押せる状態にする**（押せないボタンは理由が伝わらない）。押下時に最初のエラー項目へフォーカスを移す

## U-19 強制ログアウト（2重ログイン後勝ち）のUIが未設計

**優先度：中**

**なぜ必要か**：【要求】は「すでにログインされている場合は**後勝ち**（既存接続は強制切断される）」と明記。切断される側の画面で**何が起きるか**が未定義。予約入力中に切断される可能性がある。

**決まらないと**：ユーザーは操作中に突然エラーになり、原因が分からない。入力中データが無言で失われる。

**選択肢と推奨案**：
- 検知方法：(a) API 呼び出しが401を返した時点 / (b) ポーリング / (c) WebSocket → **推奨 (a)**。追加インフラ不要（Redis 不採用・単一VM構成【残タスク B-0】と整合）
- 表示：全画面のモーダルで理由を明示（文言は U-06 参照）＋ログイン画面への導線。背後の画面は操作不能にする
- 入力中データ：**破棄する旨を文言で明示する**（保存する設計は複雑度に見合わない）

## U-20 セッションタイムアウト（30分）のUIが未設計

**優先度：中**

**なぜ必要か**：【要求「セキュリティ」】で30分無操作の自動ログアウトが確定。予約フォーム入力中にタイムアウトすると入力が失われる。

**決まらないと**：長文のキャンセルポリシーを入力中に無言で失われ、ユーザーが離脱する。

**選択肢と推奨案**：
- **タイムアウト前の警告を出す**（残り2分で「まもなく自動ログアウトします」ダイアログ＋「ログインを継続する」ボタン）。WCAG 2.2.1（タイミング調整可能）への対応としても有効
- タイムアウト後：ログイン画面へ遷移し、理由を明示（文言は U-06）
- 警告ダイアログは `role="alertdialog"` とし、スクリーンリーダーにも確実に伝える

## U-21 営業時間外・休業日・利用不可コートの表示ルールが未定義

**優先度：中**

**なぜ必要か**：スイムレーンは常に 10:00〜22:00 を描画するが、【要求「拠点」「コート」】より、**拠点ごとに営業日・営業時間が異なり、コートごとに利用可能時間も異なる**。よって「レーン上に描かれているが予約できない領域」が常に存在する。

**決まらないと**：ユーザーは営業時間外の枠をクリックして初めてエラーに遭遇する。休業日を選んでも「予約0件」との区別がつかない（→ U-03 の空状態と混同される）。

**選択肢と推奨案**：
- 営業時間外：グレー背景＋斜線＋「営業時間外」テキスト。フォーカス可能・操作不可（`aria-disabled`）
- 休業日：**日付を選んだ時点で画面全体に「本日は休業日です」を表示**し、レーン自体を描画しない
- 利用不可コート：別パターン（濃い斜線）＋「利用不可」。営業時間外と視覚的に区別できること
- 3種を**色のみで区別しない**（→ U-05 / WCAG 1.4.1）
- 凡例をスイムレーン付近に常時表示する

## U-22 画像アップロードUIの仕様が未定義

**優先度：中**

**なぜ必要か**：【個情】および【要求】より、**プロフィール画像・チーム画像・拠点画像**の3種、加えて【ワイヤ 2】の予約への画像/ファイル添付が存在する。許容形式・サイズ上限・トリミング・代替テキストの扱いが未定。

**決まらないと**：巨大画像がアップロードされサーバ容量（単一VMのデータディスク【残タスク B-0】）を圧迫する。代替テキストが空のまま WCAG 1.1.1 違反になる。

**選択肢と推奨案**：
- 形式：JPEG / PNG / WebP。サイズ上限：**5MB**（要決定）
- プレビューとトリミング：プロフィール・チームは正方形にトリミング、拠点は 16:9
- 代替テキスト：**ユーザーに入力させず、システムが生成する**（「〇〇さんのプロフィール画像」）。入力を求めると大半が空になるため
- 予約への添付：【ワイヤ】に「任意」とあるが、**用途が不明**。ファイル種別を画像に限定するか、そもそも削除するかを要決定（要件本文に記載がないため、削除も選択肢）
- アップロード中・失敗時の状態表示（→ U-03）

## U-23 デザインシステム／UIライブラリ／デザイントークンの方針が未定義

**優先度：中**

**なぜ必要か**：カラーパレット、タイポグラフィスケール、余白、角丸、影、アイコンセットが未定。**特にカラーパレットは U-05 のコントラスト検証の前提**であり、これが決まらないと AA 準拠の検証ができない。

**決まらないと**：画面ごとに色や余白がバラつく。後からパレットを変えるとコントラスト検証をやり直すことになる。UIライブラリ（MUI / Chakra / shadcn 等）の選定が遅れると、フォーカスリングやモーダルのアクセシビリティ挙動を自前で作り込む羽目になる。

**選択肢と推奨案**：
- UIライブラリ：**アクセシビリティ対応済みのヘッドレス系（Radix UI / React Aria）＋ Tailwind** を推奨。フォーカストラップ・キーボード操作・ARIA が実装済みで、U-05 の達成コストを大きく下げる。ただし**スイムレーンは既製品がないため自前実装が前提**
- カラー：予約種別4色＋状態色（満席・利用不可・営業時間外）を先に確定し、**背景×文字の全組み合わせのコントラスト比を検証した表**を成果物とする
- ダークモード：**初期リリースでは対応しない**ことを明示（対応するなら全色の再検証が必要）
- アイコン：1セットに統一（種別アイコンは U-09 の必須要素）

## U-24 タブレット（641〜1024px）のレイアウト方針が未定義

**優先度：中**

**なぜ必要か**：【ワイヤ】はモバイルとデスクトップの方針のみ記載し、**タブレットの行が空白**。しかし【要求】はタブレット対応を必須としている。

**決まらないと**：タブレットでデスクトップ版が縮小表示され、左ペイン＋24コマのレーンが窮屈になるか、モバイル版が引き伸ばされて間延びする。

**選択肢と推奨案**：
- **左ペインを折りたたみ式（ドロワー）にし、レーンは全幅で表示**する案を推奨。1024px であればレーン24コマ（1コマ約40px）が成立する
- 縦向き（768px 幅）ではモバイル代替表示（U-02）へ切り替える案も検討。**判定は幅ベースで行い、デバイス種別で分岐しない**
- ブレイクポイントの境界値を確定し、各境界での実機確認を受入基準に含める

## U-25 パスワード再設定・アカウント設定のフロー画面が未設計

**優先度：中**

**なぜ必要か**：【要求】は「マイページからパスワードを再設定する」「初回/パスワード再設定時はランダムな文字列をシステムがメール通知する」と定めるが、画面としての流れが未設計。**ログイン前のリセット（忘れた場合）とログイン後の変更（マイページ）の2系統がある**が、【ワイヤ 4】は「アカウント設定（メール、パスワード変更）」の一行のみ。

**決まらないと**：2系統のどちらかが実装漏れになる。「ランダム文字列をメール通知」がリセットトークンなのか仮パスワードなのかで画面数が変わる（トークン＝URLクリック後に新パスワード入力、仮パスワード＝仮でログイン後に強制変更）。

**選択肢と推奨案**：
- **リセットトークン方式**を推奨（メール内リンク → 新パスワード設定画面）。仮パスワード方式は平文パスワードがメールに残るためセキュリティ上不利
- 【個情】5節でリセットトークンの保持期間が**24時間**と確定済みのため、**有効期限切れ時の画面**が必須
- メールアドレス変更時は新アドレスへの確認メールを挟むか要決定
- 変更完了後の挙動（他セッションを切るか）を U-19 と整合させる

## U-26 拠点管理のカレンダーUI・CSVインポートUIが未設計

**優先度：中**

**なぜ必要か**：【要求「拠点」】は「カレンダー表示を行い、**月/週/曜日を一括で営業/休業を設定**」「営業日の管理は**CSVインポートも行う**」と要求しているが、【ワイヤ 6】は「営業日・営業時間設定カレンダー」の一行のみ。**一括設定と CSV インポートは、それ自体が独立した画面設計を要する機能**である。

**決まらないと**：拠点スタッフの主要業務が実装できない。CSVのフォーマット・エラー時の表示・部分成功の扱いが未定だと、実装後に運用で破綻する。

**選択肢と推奨案**：
- 一括設定：カレンダー上でドラッグ範囲選択 →「選択範囲を営業/休業に設定」。加えて「毎週月曜を休業」のような曜日ルール指定UIを別途設ける
- CSVインポート：**アップロード → プレビュー（差分表示）→ 確定**の3ステップを推奨。無検証の即時反映は事故のもと
- CSVエラー：行番号と理由を一覧表示。**部分適用は行わず、全件成功か全件却下か**を明確にする（要決定）
- フォーマット定義（列名・日付形式・文字コード）を要件に明記。**テンプレートCSVのダウンロード**を提供
- 既存予約と衝突する休業設定をした場合の扱い（→【残タスク A-2】の「利用不可設定の副作用」と同根。**業務ルール確定が前提**）

## U-27 管理者ダッシュボードのログ検索UIが未設計

**優先度：中**

**なぜ必要か**：【ワイヤ 7】に「ログ検索（監査ログ）」の一行のみ。監査ログは**180日間保持**【要求「データベース要件」】され、【要求「拠点スタッフ」】は「操作は全てログに記録される（誰が操作したかは**ログイン時刻から推測**）」という運用を前提にしている。この「推測」を成立させるUIが必要。

**決まらないと**：ログが記録されても実務で追跡できない。共有アカウント運用（【残タスク A-3】）の説明責任が果たせない。

**選択肢と推奨案**：
- 検索条件：期間、ユーザー/アカウント、操作種別、対象エンティティ（予約/拠点/コート/ユーザー）、拠点
- 一覧：日時（JST・秒まで）、アカウント、IPアドレス、操作、対象、結果
- **ログイン記録と操作記録を時系列で並べて表示**できること（「ログイン時刻から推測」を実際に可能にするため）
- 件数が大きくなるためページネーション必須（【残タスク A-5】のAPI仕様と整合が必要）
- CSVエクスポートの要否を要決定

## U-28 予約確認画面（SCR-R02）の要否と内容が未確定

**優先度：中**

**なぜ必要か**：【ワイヤ 2】に「送信ボタン（**確認画面へ**）」とあるのみで、確認画面の表示項目・戻り方・独立ページかモーダルかが未定。

**決まらないと**：実装者が確認ステップを省略するか、独自に作る。予約作成は【要求】で5秒以内の完了が求められており、ステップ数は応答時間の体感に直結する。

**選択肢と推奨案**：
- (a) 確認ステップを設ける / (b) フォームから直接送信し、**完了後に取り消し可能**とする → **推奨 (b)**。予約は編集・削除が可能【要求「予約」】であり不可逆でないため、確認ステップの価値が低い。ステップ削減は 5秒以内の要件にも有利
- (a) を採る場合：全入力項目を読み取り専用で表示、[修正する][この内容で予約する] の2ボタン、モーダル内でのステップ切替（URLは変えない）
- いずれの場合も**完了後のフィードバック**（完了メッセージ＋作成した予約へのリンク＋スイムレーンへの反映）を定義する

## U-29 UIライティングガイド（用語・語調）が未整備

**優先度：低**

**なぜ必要か**：画面上の用語が【要求】の用語定義（チーム枠、リーグ戦チーム、イベント予約、店舗予約、拠点、コート）と揺れると、ユーザーが混乱する。語調（敬体/常体）、ボタンラベルの動詞形も未統一。

**決まらないと**：「拠点」と「店舗」、「メンバー」と「参加者」が混在する。翻訳（ブラウザ言語依存）時にも影響。

**推奨**：用語対訳表を作り、**【要求】の用語定義をUI上の正式名称とする**。ボタンは動詞（「予約する」「保存する」）、敬体で統一。ユーザーを主語にした否定表現を避ける。

## U-30 アイコン体系・イラスト（空状態）の方針が未定義

**優先度：低**

**なぜ必要か**：U-09 の種別アイコン、U-03 の空状態表現に必要。ただしパレット（U-23）確定後で足りる。

**推奨**：単一のアイコンセットに統一。空状態はイラストなしのテキスト＋導線で開始し、必要に応じて後から追加する。**アイコンは常にテキストラベルを伴う**（U-05 の色以外の情報伝達と整合）。

---

## U-31 多言語（ブラウザ設定依存）時のレイアウト方針が未定義

**優先度：低**

**なぜ必要か**：【要求】は「言語対応はブラウザに依存する」「デフォルトは日本語」とするのみ。**実際に翻訳リソースを用意するのか、日本語固定でブラウザの自動翻訳に任せるのかが不明。**

**決まらないと**：i18n ライブラリ導入の要否が決まらない。後から入れると全文字列の抽出作業が発生する。

**推奨**：初期リリースは**日本語のみ**を明言する。ただし文字列を直接JSXに埋め込まず、将来の抽出に備えて分離しておく方針だけ決めておく（実装コストはほぼゼロ）。`<html lang="ja">` は必須（WCAG 3.1.1）。

---

## U-32 プライバシーポリシー・利用規約への画面導線が未定義

**優先度：低**

**なぜ必要か**：【個情】が既に整備されているが、**アプリのどこからアクセスするかが未定**。ユーザー登録時の同意取得の要否も未定。

**推奨**：フッターに常時リンク。ユーザー登録画面（SCR-A02）で同意チェックボックスを設ける。【個情】11節で「重要な変更の場合はサービス内での通知」とあるため、**変更時の通知UI**（U-13 の通知種別に含まれるか）を確認する。【個情】内の `[会社名]` `[電話番号]` 等のプレースホルダも未確定。

---

## U-33 ダークモード対応の可否

**優先度：低**

**なぜ必要か**：要件に記載がないため実装対象外と考えられるが、明示されていない。

**推奨**：**初期リリースでは対応しないことを要件に明記する。** 対応する場合は全色の組み合わせでコントラスト再検証（U-05）が必要となり、コストが二倍になる。

## E. 推奨される着手順

1. **U-11 / U-08 / U-12 の記述矛盾・未確定を先に潰す**（決定コストが小さく、他項目の前提になる）
2. **U-01 画面遷移図** を作成する（U-03 / U-04 / U-12 の受け皿になる）
3. **U-05 WCAG 2.1 AA 実装基準書** を作成する（U-02 / U-07 / U-09 / U-10 のすべてに制約を与えるため、これらより先に決める）
4. **U-07 / U-09 / U-10 / U-02** のスイムレーン4点を一括で設計する（相互依存が強く、分割すると手戻りする）
5. **U-03 状態バリエーション定義表** と **U-06 エラー文言対応表** を作成する
6. **U-04 権限差分マトリクス** を作成し、【残タスク A-3】と突き合わせる
7. 以降、優先度「中」を基本設計中に順次消化する
