作成日：2026-07-26
対象領域：認証 / 認可 / 通信・データ保護 / 個人情報保護 / 監査ログ

## 本書の位置づけ

`認証セキュリティ_要件定義書.md` が「決まっていること」を整理したのに対し、本書は**要件定義工程として決まっていないこと**を洗い出したものです。

- 各項目に「なぜ必要か」「決まらないと後工程で何が起きるか」「選択肢と推奨案」を記載しています。
- **推奨案は提案であり決定ではありません。** 承認を得るまで確定要件として扱わないでください。
- 多要素認証は要求機能で「行わない」と決定済みのため、本書では提案しません。
- 本書はドキュメント上の抜け漏れの指摘であり、実際の攻撃・脆弱性検証は一切行っていません。

## No.1 認証方式（NextAuth.js 採用可否）とセッション保存先【優先度：高】

**現状**
`技術スタック提案.md` 6章および `要件定義残タスク.md` B-1 で未決。「NextAuth.js を採用するか、独自実装にするか」「セッション保存先（Redis 不採用のため PostgreSQL を推奨）」がいずれも未確定。

**なぜ必要か**
認証は全画面・全APIの前提となる横断機能で、後から差し替えると認証・認可・セッション・パスワードリセット・監査ログのすべてに波及します。DBセッション方式を採る場合はセッションテーブルがER図の必須エンティティになるため、A-4（ER図）より先に決める必要があります。

**決まらないと後工程で何が起きるか**
- ER図（残タスク A-4）にセッションテーブルを含められず、初回マイグレーションを確定できない
- API設計（A-5）の「認証方式」欄が埋まらず、共通エラーフォーマットも決まらない
- 画面遷移図（A-1）のログイン/未ログイン遷移が確定できない
- 最悪ケース：JWT前提で実装した後に二重ログイン後勝ちが成立しないと判明し、認証基盤の作り直しになる

**最重要の制約（再掲・確定事項）**
> **二重ログイン後勝ち（要求機能）は、ステートレスJWT単独では実現できない。**
> 発行済みJWTはサーバー側で無効化できないため、新規ログイン時に既存接続を強制切断できず、旧トークンは有効期限まで使い続けられます。
> したがって「ユーザーごとの有効セッションは1つ」をサーバー側の状態として保持する方式（DBセッション方式）が**必須**です。
> （出典：`技術スタック提案.md` 6章、`要件定義残タスク.md` B-1、`.claude/agents/auth-security-engineer.md` 実装上の要点1）

この制約は選択肢を実質的に絞り込みます。以下の選択肢はすべて「サーバー側セッション状態を持つ」ことを前提とします。

**選択肢**

| 案 | 内容 | 利点 | 欠点・注意 |
|---|---|---|---|
| A | NextAuth.js（Auth.js）＋ Database session strategy（PostgreSQL アダプタ） | Cookie発行・CSRF・セッション管理の実績ある実装を流用できる。実装量が最小 | `session strategy: "database"` を明示的に選ぶ必要がある（JWT戦略では要件を満たせない）。「後勝ちで旧セッションを削除する」処理はコールバックでの追加実装になる。Next.js 16 との対応バージョンを事前検証すること |
| B | NextAuth.js ＋ JWT strategy | Next.js の標準的な構成例が多い | **要件を満たせないため不可。**選択肢から除外すること |
| C | 独自実装（セッションIDをHttpOnly Cookieに入れ、実体をPostgreSQLに保持） | 「有効セッションは1つ」を最も素直に実装できる。挙動を完全に制御できる | Cookie属性、CSRF、セッション固定化対策、タイムアウト処理をすべて自前で設計・検証する必要がある。レビュー負荷が高い |
| D | ステートレスJWT ＋ 失効リスト（denylist）をDBに持つ | 既存のJWT前提設計を活かせる | 結局DBを毎回引くためJWTの利点が消える。実質的にCが単純で優位 |

**推奨案**：**A（NextAuth.js の Database session strategy）**。ただし採用の可否は「Next.js 16.2.6 で動作すること」「セッション作成時に同一ユーザーの既存セッションを削除できること」の2点を技術検証（スパイク）で確認してから確定する。検証がNGなら C にフォールバックする。

**あわせて決めること**
- セッション保存先：PostgreSQL（技術スタックで推奨済み。Redis不採用・メモリ非保持の方針と整合するため、これを追認するだけでよい）
- OAuth（Google / Facebook）の要否：`要件定義残タスク.md` B-1 に「要求機能に記載がないため原則不要と考えられる。要確認」とある。**不要**で確定させることを推奨（採用するとパスワードポリシー・ロック要件・二重ログイン制御が外部IdP側の挙動に依存し、要件充足の証明が難しくなる）

## No.2 初回パスワード / リセットの通知方式とトークン有効期限【優先度：高】

**現状**
要求機能は「初回/パスワード再設定時はランダムな文字列をシステムがメール通知する」「リセットを行い、メール通知して再認証してログインを行う」とのみ記載。**「ランダム文字列＝新パスワードそのもの」なのか「リセット用URLに埋め込むワンタイムトークン」なのかが未定義**。
`個人情報保護方針.md` 5章には「パスワードリセットトークン：24時間（期限後は自動削除）」とあり、**トークン方式を想定した記述が存在する一方、有効期限としての24時間が妥当かは検討されていない**。

**なぜ必要か**
パスワードリセットは攻撃者にとって最も狙われるアカウント乗っ取り経路であり、方式が決まらないとメール文面・画面・DB設計・有効期限のすべてが決まりません。また保護方針の「24時間」は**保持期間**の記述であり、**有効期限**と混同したまま実装すると、24時間有効なリセット手段がメールボックスに残り続けることになります。

**決まらないと後工程で何が起きるか**
- パスワードリセット画面の有無・遷移が決まらず、画面遷移図（A-1）が完成しない
- リセットトークンのテーブル設計ができない（A-4）
- メール本文テンプレートが作れず、メール送信基盤（B-2）の要件も固まらない
- 方式を後から「文字列直送」→「トークンURL」に変更すると、画面・API・メール・DBのすべてを作り直すことになる

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 生成したランダム文字列を**新パスワードとしてメール本文に直接記載**し、それでログインさせる | 要求機能の字面には最も近い。ただし平文パスワードがメールボックスに恒久的に残る。メール転送・端末紛失・メールアカウント侵害でそのまま乗っ取られる。「初回ログイン後に強制変更」を必ず組み合わせる必要がある |
| B | 有効期限付きの**ワンタイムトークンURL**をメールで送り、遷移先の画面で本人が新パスワードを設定する | メールに恒久的な認証情報が残らない。保護方針5章の「パスワードリセットトークン」の記述とも整合する。標準的な方式 |
| C | A と B の併用（初回登録＝A＋初回ログイン時に強制変更、リセット＝B） | 要求機能の「初回はランダム文字列を通知」を満たしつつ、リセット経路の安全性を確保できる |

**推奨案**：**C**。ただし A の経路にも次を必須とする。
- 初回発行文字列にも**有効期限**を設ける（推奨：72時間。期限切れ後は再発行させる）
- 初回ログイン直後に**パスワード変更を強制**する
- 生成する文字列は AUTH-08（8文字以上・大小英数）を満たし、かつ暗号論的乱数で生成した十分な長さ（推奨：16文字以上）とする

**トークン有効期限の推奨値**

| 項目 | 推奨値 | 理由 |
|---|---|---|
| リセットトークンの有効期限 | **30分**（許容範囲 15〜60分） | 業界標準。24時間は長すぎる |
| リセットトークンの使用回数 | **1回限り**（使用後は即無効化） | 再利用による再乗っ取りを防ぐ |
| 新規リセット要求時の旧トークン | **すべて無効化** | 有効なトークンが並存しない |
| DB上のレコード保持 | 保護方針どおり24時間（期限切れ後の監査用に残し、自動削除） | 保護方針5章と整合。**「有効期限」と「保持期間」を別物として明記すること** |

> 保護方針5章の表現は「有効期限＝24時間」と読めるため、**保護方針側の記述も「保持期間24時間・有効期限は別途定義」と補記する必要があります**（保護方針の改訂要否を判断してください）。

## No.3 アカウントロックの解除手段とロック判定の単位【優先度：高】

**現状**
要求機能は「3回連続で失敗した場合、該当アカウントを30分間ロックする」のみ。**30分の経過を待つ以外の解除手段があるかどうかが未定義**。また、失敗回数のカウント単位・リセット条件も未定義。

**なぜ必要か**
- 3回という閾値は非常に厳しく、正規ユーザーが日常的にロックされます。解除手段がないと「30分待つ」しかなく、問い合わせ窓口も**ユーザーサポート対応は行わない**（要求機能・運用保守要件）ため、救済経路が存在しません。
- とりわけ**拠点スタッフは1拠点1アカウントの共有**です。1人が3回ミスするとその拠点のスタッフ全員が30分間業務停止します。営業時間中に発生すると拠点運用に直接影響します。
- **システム管理者アカウントがロックされた場合、解除できる上位者が存在しません**（完全ロックアウト）。

**決まらないと後工程で何が起きるか**
- ロック解除の管理画面機能（システム管理者向け）が機能要件から漏れ、リリース後に「解除できない」障害として顕在化する
- 攻撃者が他人のメールアドレスに3回失敗を送るだけで任意アカウントを継続的に締め出せる（サービス拒否）ことに設計段階で気づけない
- 管理者ロックアウト時の復旧手順が運用手順書に載らない

**選択肢（解除手段）**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 30分経過による自動解除のみ（現状の字面どおり） | 実装は最小。ただし上記の運用リスクを全面的に受容することになる |
| B | 自動解除＋**システム管理者による手動解除**（管理画面から即時解除） | 拠点スタッフの業務停止を救済できる。管理者自身のロックは解決しない |
| C | 自動解除＋**パスワードリセット成功による解除**（リセット完了時にロック状態と失敗カウンタをクリア） | 本人が自力で解決できる。メール受信が本人確認の代替になる |
| D | B＋C の併用、加えて**管理者アカウント用の非常用復旧手順**（サーバー上での直接解除手順を運用手順書に明記） | 全ケースを救済できる |

**推奨案**：**D**。あわせて次を要件化することを推奨します。

| 論点 | 推奨 | 理由 |
|---|---|---|
| ロック判定のキー | メールアドレスを**正規化（小文字化・前後空白除去）した値**で判定 | 大文字小文字違いのメールでカウンタを分散させる回避を防ぐ |
| IPアドレス単位の制限 | アカウント単位のロックに**加えて**IP単位のレート制限を併用（No.12） | アカウント単位ロックだけでは、多数アカウントへの横断的な試行（パスワードスプレー）を止められない |
| 失敗カウンタのリセット | ログイン成功時にリセット。加えて最終失敗から30分経過でリセット | 過去の失敗が無期限に累積しない |
| ロック中のレスポンス | ロック中である旨は返すが、**アカウントの存在有無は区別できない表現**にする（No.17と整合） | ユーザー列挙対策 |
| ロック発生の記録 | 監査ログに記録し、短時間に多発した場合はアラート | 攻撃検知（No.9 / No.21） |
| 拠点スタッフ共有アカウントの緩和 | ※要検討：閾値を3回のままとするか、共有アカウントに限り緩和するか | 要求機能は一律3回と読めるため、変更する場合は要件変更として合意が必要 |

## No.4 二重ログイン後勝ちの「強制切断」の具体挙動【優先度：高】

**現状**
要求機能は「すでにログインされている場合は後勝ちとし、既存接続は強制切断される」とのみ記載。**切断された側に何が起きるかが未定義**。

**なぜ必要か**
「強制切断」はサーバー側でセッションを無効化することを指しますが、既存セッションの利用者は**次のリクエストを送るまで切断に気づきません**。その間に画面上で入力していた内容（予約作成フォーム等）がどうなるかは、画面設計とAPI設計の両方に関わります。

**決まらないと後工程で何が起きるか**
- 「切断された側の画面がエラーのまま操作不能になる」「入力中の予約が消える」といった不具合が受入テストで初めて発覚する
- 切断検知にサーバーへのポーリングを使う場合、そのポーリング自体がセッションのアクティビティとみなされ、**30分無操作タイムアウト（No.5）が永久に発火しなくなる**という相互矛盾が生じる（この2件はセットで決めること）
- API設計（A-5）の共通エラーフォーマットに「セッション失効」の区別が定義されない

**決めるべき論点と選択肢**

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| 切断の通知タイミング | (a) 次のリクエスト時にエラーで気づく（受動） / (b) 定期ポーリングで能動検知 / (c) SSE・WebSocketで即時通知 | **(a) 受動**。同時接続100人規模でポーリングやWebSocketを追加する必要性が薄く、No.5との矛盾も生じない |
| 切断時のレスポンス | 専用のエラーコードを定義し、クライアントはログイン画面へ遷移させる | エラーコード設計（A-7）に「別端末でログインされたためログアウトされました」を追加 |
| 入力中データの扱い | (a) 破棄 / (b) 下書き保存して復帰後に復元 | **(a) 破棄**（画面に警告文言を出す）。(b)は実装コストが大きい |
| 切断された旧セッションへの通知メール | 送る / 送らない | **送らない**。要求機能「実装しない機能：記載されていない通知機能」に抵触するため |
| 同一ブラウザでの複数タブ | 同一セッションIDを共有するため切断対象外 | 「二重ログイン」の定義は**セッション単位**であることを明記する |
| 拠点スタッフ共有アカウントへの影響 | 1拠点1アカウントのため、**2人目のスタッフがログインすると1人目が切断される** | 仕様として明記し、拠点運用側に周知が必要。運用上の重大な制約であり、要件として合意を取ること |

**推奨案**：受動検知（次リクエスト時に専用エラー → ログイン画面へ）。あわせて上表の各論点を要件として明文化する。特に**拠点スタッフの共有アカウントで発生する相互切断は、要件どおりに作ると業務影響が出る**ため、事業側の合意を明示的に取ることを推奨します。

## No.5 セッション30分タイムアウトの計測方法と絶対有効期限【優先度：高】

**現状**
要求機能は「30分間のアクティビティがない場合に自動ログアウト」。**「アクティビティ」の定義が未定義**。また `個人情報保護方針.md` 8.1 のセッションCookie保持期間は「ブラウザを閉じるまで」であり、30分タイムアウトとの関係が未整理。

**なぜ必要か**
「アクティビティ」に何を数えるかで、実際のログアウト挙動がまったく変わります。

**決まらないと後工程で何が起きるか**
- 画面が自動更新（ポーリング）を行う設計にすると、ユーザーが席を外していてもセッションが延命され続け、**要件を満たさないまま満たしているように見える**
- 逆に厳しく取ると、スイムレーンを眺めているだけのユーザーが予約入力中にログアウトされ、入力が消える
- セキュリティレビュー時に「30分タイムアウトが実装されているか」を判定する基準がない

**決めるべき論点と選択肢**

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| アクティビティの定義 | (a) 認証が必要な全リクエスト / (b) ユーザー起因の操作リクエストのみ（自動ポーリング・ヘルスチェックを除外） / (c) ブラウザ側のマウス・キー操作 | **(b)**。(a)は自動更新で延命され要件が形骸化する。(c)はサーバー側で検証できない |
| 延長方式 | スライディング（操作のたびに30分を再セット） | 「30分間アクティビティがない場合」という文言はスライディング方式を指す |
| 絶対有効期限（Absolute timeout） | 設ける / 設けない | ※補完：**設けることを推奨**（例：ログインから24時間で無条件失効）。要求機能に記載がないため要判断。長期間操作し続けるセッションの乗っ取りリスクを限定できる |
| 期限切れの検出方式 | サーバー側のセッションレコードの `lastAccessedAt` で判定（Cookieの有効期限に依存しない） | クライアント側のCookie期限は改ざん可能なため、**サーバー側判定を必須**とする |
| 期限切れセッションの削除 | バッチ（タスクスケジューラ）で定期削除 | 残タスク B-6 の運用バッチに追加する |
| 画面側の予告 | タイムアウト前に警告を出す / 出さない | ※補完：出すことを推奨（画面設計 A-1 に反映が必要） |
| Cookie 有効期限の整合 | セッションCookieは「ブラウザを閉じるまで」（保護方針8.1）を維持しつつ、サーバー側で30分判定 | 保護方針の記述と矛盾しない。ただし**両者の関係を保護方針側に補記すること**を推奨 |

**推奨案**：サーバー側 `lastAccessedAt` によるスライディング30分＋絶対有効期限24時間。アクティビティは「ユーザー起因のリクエストのみ」と定義し、除外対象（ヘルスチェック、自動更新）を一覧化する。

## No.6 メールアドレスの一意制約と「複数アカウント可」の解釈【優先度：高】

**現状**
要求機能に「メールアドレスによるユーザー認証とし、**複数アカウント登録は可能**とする」「同一人物の複数アカウント登録は可」とある。一方でログインの識別子はメールアドレスである。**同一メールアドレスで複数アカウントを作れるのかが未定義**。

**なぜ必要か**
- 同一メールアドレスで複数アカウントを許すと、ログイン時に「どのアカウントか」を特定できません。パスワードリセットも「どのアカウントのリセットか」が決まりません。
- アカウントロック（3回失敗で30分）の判定対象も一意に定まりません。
- これは認証の根幹であり、DB設計（ユニーク制約）に直結します。

**決まらないと後工程で何が起きるか**
- User テーブルに `email` のユニーク制約を張るか判断できず、初回マイグレーション（技術スタック 7章 次アクション3）を確定できない
- ログインAPIの仕様が書けない（A-5）
- 後から一意制約を追加する場合、既存データの重複解消が必要になる

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | メールアドレスは**全体で一意**。「複数アカウント登録可」は「1人が複数のメールアドレスを使えば複数アカウントを持てる」という意味と解釈する | 認証が一意に定まる。標準的。要求機能の文意とも矛盾しない |
| B | 同一メールで複数アカウントを許し、ログイン時にアカウントを選択させる | ログイン画面が複雑化。リセット・ロック・二重ログイン制御がすべて複雑化。パスワードが同一の場合の識別も困難 |

**推奨案**：**A**。あわせて次を要件化する。
- メールアドレスは**正規化して保存・照合**する（小文字化、前後空白除去）。正規化しないと「User@example.com」と「user@example.com」で別アカウントが作れてしまい、ロック回避（No.3）にも利用される
- メールアドレスの**到達確認（確認メールによる有効化）**を行うか要判断。要求機能は「初回はランダム文字列をメール通知」としているため、**そのメールを受信できること自体が到達確認になる**（改めて確認メールを送る必要はない）と整理できる
- メールアドレスの変更手段の有無：要求機能に記載がない。変更を許す場合は「変更先アドレスへの確認」「旧アドレスへの通知」の要否を決める必要がある（通知は「記載されていない通知機能」に抵触しないか要確認）

## No.7 ログアウト時の挙動とセッションCookieの属性【優先度：中】

**現状**
要求機能に**明示的なログアウト機能の記述がない**（自動ログアウトの記述のみ）。Cookie属性（`Secure` / `HttpOnly` / `SameSite`）に関する記述も要件定義側にない。

**なぜ必要か**
- 手動ログアウトはほぼ必須の機能ですが、要件に書かれていないため画面設計・API設計から漏れるおそれがあります。とりわけ**拠点スタッフの共有アカウント**では、交代時に確実にログアウトできることが運用上の前提になります。
- Cookie属性は認証の安全性を左右する基本設定でありながら、要件定義に一言もありません。

**決まらないと後工程で何が起きるか**
- ログアウトボタンが画面設計（A-1）に含まれず、共有端末で前の人のセッションが残る
- 「ログアウトしたのにブラウザバックで画面が見える」（キャッシュ）といった指摘がセキュリティレビューで出る
- Cookie属性の指定漏れがリリース直前のペネトレーションテスト（SEC-06）で初めて指摘される

**決めるべき論点と推奨**

| 論点 | 推奨 |
|---|---|
| 手動ログアウト機能 | **要件として明記する**（全ロールの全画面から到達可能なこと） |
| ログアウト時のサーバー側処理 | セッションレコードを**削除**する（無効フラグではなく削除、または即時失効） |
| ログアウト時のクライアント側処理 | セッションCookieを削除する。クライアント側に保持した個人情報を破棄する |
| ブラウザバック対策 | 認証必須ページに `Cache-Control: no-store` を付与する |
| Cookie `HttpOnly` | **必須**（JavaScriptからセッションIDを読めないようにする） |
| Cookie `Secure` | **必須**（TLS必須の要件 SEC-01 と整合） |
| Cookie `SameSite` | **`Lax` 以上**（CSRF対策の基礎。No.18と併せて決定） |
| Cookie の `Path` / `Domain` | 必要最小限のスコープに限定する |
| セッション固定化（Session Fixation）対策 | **ログイン成功時にセッションIDを再生成する**ことを要件に含める |

## No.8 退会フローの定義とデータ削除範囲【優先度：高】

**現状**
`個人情報保護方針.md` 7.4 に「ユーザーは任意の時点で退会できる」とあるが、**要求機能の利用者操作一覧に「退会」が存在しない**。削除範囲についても記述が矛盾している。

| 出典 | 記述 |
|---|---|
| 要求機能（データ保持・削除ポリシー） | 退会ユーザーの情報は**退会時点で物理削除**する。ただし紛争解決に必要な情報（予約登録者、参加者等）は**12ヶ月間**保持する |
| 保護方針 5章 | アクティブユーザー情報：ユーザー退会時まで。予約履歴：予約日から**24ヶ月** |
| 保護方針 7.4 | 退会時、個人情報は「保持期間」に従って管理される |

**なぜ必要か**
- 退会機能が機能要件になければ実装されず、方針で約束した権利（7.4）を果たせません。これは APPI 準拠（PRIV-09）の観点で問題になります。
- 「物理削除」と「12ヶ月/24ヶ月保持」を両立させるには、**どのカラムを消してどれを残すか**を要件レベルで定義する必要があります。定義がないまま実装すると、外部キー制約違反で削除できない、または残すべき記録まで消える、のどちらかが起きます。

**決まらないと後工程で何が起きるか**
- ER図（A-4）で `Reservation.userId` を必須にするか NULL 許容にするか決められない
- 退会ユーザーが登録した予約に参加中の他ユーザーがいる場合の扱いが決まらず、削除バッチ（B-6）が書けない
- リリース後に「退会したのにデータが残っている / 消えすぎた」という問い合わせが発生し、対応窓口も存在しない（PRIV-10：従業者なし）

**決めるべき論点と選択肢**

| 論点 | 選択肢 | 推奨 |
|---|---|---|
| 退会の実行主体 | 本人（マイページ）/ システム管理者のみ | **本人＋管理者代行の両方**。保護方針7.4「任意の時点で退会できる」を満たすには本人操作が必要 |
| 退会時の本人確認 | パスワード再入力を求める / 求めない | **求める**（誤操作・セッション乗っ取りによる削除を防ぐ） |
| 削除方式 | 物理削除 / 論理削除 / **匿名化（個人特定情報のみ削除し、記録行は残す）** | **匿名化**を推奨。要求機能「物理削除」と「12ヶ月保持」を両立させる唯一の現実解。「個人情報を物理削除し、紛争解決に必要な記録は個人を特定できない形で残す」と定義し直す |
| 匿名化で削除する項目 | メールアドレス、パスワードハッシュ、プレイヤーネーム、プロフィール画像、自己紹介、プレースタイル | 保護方針2.1の「基本情報」「プロフィール情報」 |
| 匿名化で残す項目 | 予約ID、予約日時、拠点・コート、参加関係（匿名化済みIDで） | 要求機能「紛争解決に必要な情報（予約登録者、参加者等）」 |
| 保持期間 | 12ヶ月（要求機能）/ 24ヶ月（保護方針） | **矛盾の解消が必要**。どちらかに統一し、両ドキュメントを改訂する |
| 退会者が予約者である未来の予約 | 自動キャンセル / 参加者へ通知 / 管理者に引き継ぎ | **自動キャンセル＋参加登録者への通知**を推奨。要求機能「予約者が予約を削除した場合、参加登録者全員に通知」の準用として整理できる |
| チームリーダーの退会 | チームの扱い（解散 / リーダー移譲 / 管理者対応） | 要決定。リーダー不在のチームが発生すると承認フロー（AUTHZ-L-02）が止まる |
| 拠点スタッフ・管理者アカウントの退会 | 本人退会の対象外とし、管理者による削除のみ | 共有アカウントであり本人の概念がないため |
| 同一メールでの再登録 | 可 / 不可（クーリング期間） | **可**を推奨（匿名化でメールが解放されるため） |

## No.9 監査ログの記録項目・改ざん対策・閲覧権限【優先度：高】

**現状**
「監査ログを180日保持する」「拠点スタッフの操作は全てログに記録される」「誰が操作したかはログイン時刻から推測する」とあるが、**記録項目・記録対象操作・改ざん防止・閲覧手段のいずれも未定義**。

**なぜ必要か**
共有アカウント（拠点スタッフ1拠点1アカウント）を採用している以上、監査ログは**唯一の追跡手段**です。「ログイン時刻から推測する」という運用は、監査ログの各操作行が特定のログインセッションと結びついていなければ成立しません。記録項目が決まらないまま実装すると、事後に「誰がやったか推測すらできない」ログが180日分溜まることになります。

**決まらないと後工程で何が起きるか**
- AuditLog テーブルの設計ができない（技術スタック 7章 次アクション3 に AuditLog が挙がっているが、カラムが決まらない）
- インシデント発生時（保護方針3章「セキュリティインシデント調査」）に必要な情報が残っていない
- 管理画面にログ閲覧機能が実装されず、システム管理者がサーバーに直接ログインしないと確認できない

**決めるべき論点と推奨**

| 論点 | 推奨 |
|---|---|
| 記録項目 | 操作日時、**ログイン日時**、**セッション識別子**、アカウントID、ロール、所属拠点ID、送信元IPアドレス、ユーザーエージェント、操作種別、対象リソース種別・ID、結果（成功/失敗）、変更前後の値（個人情報を除く） |
| 記録対象操作 | 認証イベント（ログイン成功/失敗、ロック発生/解除、ログアウト、二重ログインによる強制切断、パスワード変更/リセット）＋データ変更操作（作成/更新/削除）＋権限昇格に関わる操作（ロール変更、承認） |
| 参照操作の記録 | ※要判断。全参照を記録すると量が膨大。**個人情報の一覧閲覧・エクスポートのみ記録**を推奨 |
| 個人情報の非出力 | 監査ログにパスワード・トークン・メールアドレス本文を出さない（LOG-07）。対象者は**IDで参照**する |
| 改ざん防止 | アプリケーションのDBユーザーに監査ログテーブルへの UPDATE / DELETE 権限を与えない（追記専用）。削除は保持期間バッチ専用のロールで行う |
| 保存先 | ファイルログとDB監査ログの役割分担を定義する（要求機能はログファイル、データベース要件は監査ログ180日と記述が分かれている）→ No.22 |
| 閲覧手段 | システム管理者向けの管理画面から検索・閲覧できること（機能要件への追加が必要） |
| 拠点スタッフのログ閲覧 | ※要判断。自拠点分のみ閲覧可とするか、閲覧不可とするか。PRIV-02（業務範囲内のみ）に照らして決める |
| ログイン時刻からの追跡運用 | 拠点側で「誰がいつログインしたか」を台帳等で管理する運用ルールを定める必要がある（システム側だけでは追跡が完結しない）。運用ポリシー（A-10）に追記すること |

| 対応記録 | 請求受付〜対応完了の記録を残す | APPI 対応の証跡として必要。監査ログ（No.9）とは別に管理台帳を定義する |

## No.11 権限マトリクスと個人情報の表示範囲【優先度：高】

**現状**
`要件定義残タスク.md` A-3 に「機能ごとのCRUD権限マトリクス」が未作成として挙がっている。加えて、**ロールごとに「他人の個人情報をどこまで見られるか」が全く定義されていない**。

**なぜ必要か**
保護方針6.2は「チームリーダーが所属チーム員の予約情報を確認する場合」「拠点スタッフが自拠点のユーザー情報を確認する場合」を第三者提供の例外として認めていますが、**確認できる項目**は書かれていません。またメンバー同士（同じ予約に参加する者同士）で何が見えるかも定義がありません。プロフィール画像・自己紹介・プレースタイルは公開前提に見えますが、**メールアドレスが見えてよいかは明らかに要判断**です。

**決まらないと後工程で何が起きるか**
- API のレスポンス項目が設計者ごとにばらつき、あるエンドポイントだけメールアドレスを返すといった漏洩経路が生まれる
- 画面設計（A-1）で「予約詳細に参加者の何を表示するか」が決められない
- セキュリティレビューで「機微情報の露出」として大量の指摘が出る

**推奨アクション**
以下2つの表を要件定義成果物として作成する。

1. **機能×ロールのCRUD権限マトリクス**（A-3 と同一。本領域として認可の観点でレビューする）
   - 行：機能（拠点管理、コート管理、営業日設定、予約作成、予約編集、予約削除、参加登録、チーム申請、承認、ユーザー管理、監査ログ閲覧 等）
   - 列：メンバー / チームリーダー / 拠点スタッフ / システム管理者
   - セルには C/R/U/D と**スコープ**（自分のみ / 自チーム / 自拠点 / 全体）を書く。スコープを書かないとIDOR対策の判定基準にならない

2. **個人情報項目×閲覧者ロールの可視性マトリクス**

## No.12 レート制限の具体値【優先度：中】

**現状**
`要件定義残タスク.md` B-4 に「レート制限の実装方式（ログイン / パスワードリセット / 予約登録）」が未決として挙がっているのみで、**具体値が一切ない**。

**なぜ必要か**
アカウントロック（3回/30分）はアカウント単位の防御であり、**IP単位・全体単位の防御にはなりません**。多数のアカウントに1回ずつ試行するパスワードスプレー、リセットメールの大量送信（メール送信コストとレピュテーションへの影響）、予約登録の連打による在庫荒らしは、レート制限がなければ止まりません。

**決まらないと後工程で何が起きるか**
- 実装者ごとに判断がばらつき、エンドポイントによって防御の有無が変わる
- パスワードリセットの乱発でメール送信サービスの上限に抵触する（残タスク B-2「送信上限・レート制限への対策」と直結）
- 非機能要件（スループット：予約登録5件/分）とレート制限値の関係が検証されない

**選択肢と推奨初期値（※補完：いずれも要求機能に記載がないため、承認が必要）**

| 対象 | 単位 | 推奨初期値 | 根拠 |
|---|---|---|---|
| ログイン試行 | IPアドレス | 10回 / 5分 | アカウント単位ロック（3回）の補完。共有IP（拠点のWi-Fi等）を考慮してやや緩め |
| ログイン試行 | アカウント | 3回 / 30分ロック | 要求機能で確定済み |
| パスワードリセット要求 | メールアドレス | 3回 / 1時間 | メール大量送信の抑止 |
| パスワードリセット要求 | IPアドレス | 10回 / 1時間 | 同上 |
| 新規ユーザー登録 | IPアドレス | 5回 / 1時間 | 大量アカウント作成の抑止（複数アカウント登録可のため無制限になりやすい） |
| 予約登録 | アカウント | 10回 / 分 | 要求機能のスループット要件（5件/分）に対し余裕を持たせた値 |
| API全般 | アカウント | 300回 / 分 | 想定同時接続100人に対する上限 |

**あわせて決めること**
- 制限超過時のレスポンス（HTTP 429 と `Retry-After` の返却方針、エラーコード設計 A-7 への追加）
- カウンタの保持先：Redis 不採用のため **PostgreSQL** またはアプリのプロセス内。単一VM構成のためプロセス内メモリでも成立するが、技術スタック5章「セッション・キューをサーバーのメモリ上に持たない」方針と整合させるなら PostgreSQL を推奨
- IIS（リバースプロキシ）側で行うか、アプリ側で行うか。**送信元IPの取得**にあたり、IIS 経由で `X-Forwarded-For` が正しく渡ること、および**クライアントが偽装したヘッダを信用しない**ことを要件に含める

## No.13 CAPTCHA 等ボット対策の要否【優先度：中】

**現状**
`要件定義残タスク.md` B-4 に「CAPTCHA 等のボット対策を入れるか」が未決として挙がっている。

**なぜ必要か**
判断を先送りすると、リリース直前に「入れる」と決まった場合、ログイン画面・登録画面・リセット画面の設計変更と外部サービス連携（＝新たな第三者提供の検討、保護方針6.3）が発生します。逆に「入れない」と決めるなら、その代替（レート制限 No.12）が十分であることを明示する必要があります。

**決まらないと後工程で何が起きるか**
- 画面設計（A-1）にCAPTCHA領域を確保できず、後から画面レイアウトを変更することになる
- CAPTCHA提供元（reCAPTCHA 等）へのIPアドレス送信が発生する場合、**保護方針6.3（サービス提供業者への提供）の記載追加が必要**になる。方針改訂は公開文書の変更であり手戻りが大きい
- アクセシビリティ要件（WCAG 2.1 AA、要求機能）との適合検討が漏れる

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 導入しない。レート制限（No.12）＋アカウントロックのみで対応 | 追加の第三者提供が発生しない。方針改訂不要。アクセシビリティ上の懸念もない。想定規模（初期500ユーザー・20拠点）では現実的 |
| B | 外部CAPTCHAサービスを導入（reCAPTCHA / hCaptcha / Cloudflare Turnstile） | ボット対策として強力。ただし外部への通信が発生し、保護方針の改訂とWCAG適合の検討が必要 |
| C | 段階的導入：通常は出さず、**同一IP/アカウントで失敗が続いた場合のみ**表示 | 正規ユーザーの体験を損なわない。実装はやや複雑 |

**推奨案**：**A（初期リリースでは導入しない）**とし、「導入しない」ことを**明示的な決定として記録**する。ただし次の発動条件を定めておく。
- リリース後に自動化された試行が観測された場合、または C の段階的導入に切り替える判断基準（例：1日あたりのログイン失敗が一定数を超えた場合）
- 導入する場合は Cloudflare Turnstile 等、個人情報送信が少なくアクセシビリティ配慮のある選択肢を優先し、**保護方針6.3の改訂とセットで行う**

## No.14 APIトークン認証の仕様【優先度：中】

**現状**
要求機能は「API通信は認証トークンによる認証を行う」のみ。**トークンの種類・発行方法・有効期限・失効方法・ブラウザセッションとの関係が未定義**。

**なぜ必要か**
「APIトークン」が指すものが、(a) ブラウザのセッションCookieと同じもの、(b) 外部連携用に別途発行するトークン、のどちらかで設計がまったく変わります。(b) であれば、トークンはセッションタイムアウト（30分）や二重ログイン制御の対象外になり、要件の適用範囲を定義し直す必要があります。

**決まらないと後工程で何が起きるか**
- API設計（A-5）の「認証方式」欄が書けない
- 外部連携トークンを実装した場合、そのトークンが二重ログイン後勝ちを迂回する抜け道になる
- トークンの失効手段がなく、漏洩時に無効化できない

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 「APIトークン認証」＝**同一オリジンのブラウザセッションCookieによる認証**と解釈する（本システムのAPIはフロントエンドからのみ呼ばれる） | 要求機能に外部連携の記述がないため整合的。二重ログイン制御・30分タイムアウトが自動的に適用される。CSRF対策が必要（No.18） |
| B | セッションとは別に Bearer トークンを発行する | 外部連携が可能。ただし外部連携の要件が現時点で存在しない。トークン管理の実装コストが増える |

**推奨案**：**A**。「本システムのAPIは自サービスのフロントエンドからのみ利用され、認証はセッションCookieで行う」と定義し、外部公開APIは現時点でスコープ外とすることを明記する。将来外部連携が必要になった時点で B を別途設計する。

**A を採る場合にあわせて決めること**
- CSRF 対策（No.18）が必須になる
- Cookie の `SameSite` 属性（No.7）
- 「APIトークン」という要求機能の用語を、決定内容に合わせて読み替える旨を要件定義書に注記する

## No.15 拠点スタッフ・システム管理者のパスワード変更経路【優先度：中】

**現状**
要求機能は「**メンバー / チームリーダー**のマイページからパスワードを再設定する」と記載。拠点スタッフとシステム管理者の変更経路が書かれていない。

**なぜ必要か**
拠点スタッフのアカウントは共有されており、スタッフの入退社時にパスワードを変更する必要が生じます（共有アカウント運用の基本的な要求）。変更経路がなければ、退職者が拠点の予約を操作し続けられます。

**決まらないと後工程で何が起きるか**
- 拠点スタッフのパスワード変更ができず、人の入れ替わりのたびにシステム管理者へ依頼が発生する。しかしその依頼を受ける窓口も「ユーザーサポート対応は行わない」ため存在しない
- 管理画面の機能一覧から漏れる

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 拠点スタッフも自身の管理画面からパスワード変更できる | 拠点側で自律的に運用できる。共有アカウントのため「誰が変更したか」は監査ログ（No.9）に依存する |
| B | システム管理者のみが拠点スタッフのパスワードをリセットできる | 統制は効くが、依頼の受け口が必要 |
| C | A＋B の併用 | 現実的 |

**推奨案**：**C**。あわせて次を定める。
- 拠点スタッフのパスワード変更時、**その拠点の既存セッションをすべて失効させる**（他のスタッフが継続利用できてしまうのを防ぐ）
- 拠点スタッフ用メールアドレスの位置づけ（個人のアドレスか拠点の共有アドレスか）。リセットメールの宛先になるため要決定
- システム管理者のパスワード変更経路（No.20 と併せて決定）

## No.16 パスワードポリシーの補足事項【優先度：低】

**現状**
「最小8文字、大文字・小文字・数字を含む」のみが確定。それ以外の論点は未定義。

**なぜ必要か**
実装時に判断を迫られる論点が複数あり、決めておかないと実装者の裁量で決まってしまいます。

**決めるべき論点と推奨**

| 論点 | 推奨 | 備考 |
|---|---|---|
| 最大文字数 | 128文字程度の上限を設ける | 極端に長い入力によるハッシュ処理負荷（DoS）を避ける |

| ハッシュアルゴリズム | bcrypt / argon2 等の実績あるライブラリ。自前実装・SHA単体・可逆暗号は不可 | 実装方針として `.claude/agents/auth-security-engineer.md` に定義済み。要件定義としては「ハッシング・ソルト」で足りる |

## No.17 ユーザー列挙対策の方針【優先度：中】

**現状**
要件定義に記述なし。

**なぜ必要か**
「このメールアドレスは登録されていません」「このメールアドレスは既に使われています」といったレスポンス差分から、攻撃者は登録済みメールアドレスの一覧を作成できます。本サービスは**メールアドレスが唯一のログイン識別子**であり、かつ**アカウントロックがアカウント単位で発動する**ため、有効なメールアドレスが判明すると、そのアカウントを狙って継続的にロックさせる嫌がらせが可能になります。

**決まらないと後工程で何が起きるか**
- 画面のエラーメッセージ文言を後から全面的に見直すことになる（画面設計 A-1、エラーコード設計 A-7 に影響）
- 「登録済みメールでの新規登録」時の画面遷移が決まらない

**決めるべき論点と推奨**

| 経路 | 推奨 |
|---|---|
| ログイン失敗 | メールアドレス誤り／パスワード誤りを**区別しない**共通メッセージにする |
| パスワードリセット要求 | 登録の有無にかかわらず**同一のメッセージ**（「ご登録のアドレスであればメールを送信しました」）を返し、応答時間の差も小さくする |
| 新規登録（重複メール） | 「登録済み」と画面に出さず、**登録済みアドレス宛に「既に登録があります」メールを送る**方式を推奨。ただし要求機能「記載されていない通知機能は実装しない」との整合を要確認。整合しない場合は、利便性を優先して画面に表示する判断もあり得る（**トレードオフとして明示的に決定すること**） |
| アカウントロック中 | ロック中である旨は返してよいが、未登録アドレスでも同様の挙動になるよう配慮する |

**推奨案**：ログインとパスワードリセットは**列挙対策を必須**とする。新規登録は利便性とのトレードオフを事業側と合意のうえ決定する。

## No.18 CSRF対策とセキュリティヘッダの方針【優先度：中】

**現状**
要件定義に記述なし。`.claude/agents/security-reviewer.md` にはレビュー観点として挙がっているが、要件としては定義されていない。

**なぜ必要か**
No.14 で Cookie ベースの認証を採用する場合、CSRF 対策は必須です。またセキュリティヘッダは、実装後に追加すると既存画面が動かなくなる（特に CSP）ため、要件段階で方針を決めておく必要があります。

**決まらないと後工程で何が起きるか**
- CSP を後から導入するとインラインスクリプト・スタイルが全滅し、画面の作り直しが発生する
- ペネトレーションテスト（SEC-06）で必ず指摘され、リリース直前の修正になる

**決めるべき論点と推奨**

| 項目 | 推奨 |
|---|---|
| CSRF 対策 | Cookie 認証を採るなら**必須**。`SameSite=Lax` に加えてトークン方式（Double Submit または Synchronizer Token）を併用する。NextAuth.js を採用する場合は組み込みのCSRF機構を利用する |
| CSP（Content-Security-Policy） | **設計初期から適用**する。`unsafe-inline` を避ける方針を最初に決めておく。適用先は IIS（リバースプロキシ）かアプリのどちらかに統一する |
| HSTS | 有効化（TLS必須の SEC-01 と整合） |
| X-Content-Type-Options | `nosniff` |
| Referrer-Policy | `strict-origin-when-cross-origin` |
| X-Frame-Options / frame-ancestors | クリックジャッキング対策として自サイト以外への埋め込みを禁止 |
| エラーレスポンス | スタックトレース・内部パス・SQL文をクライアントに返さない。共通エラーフォーマット（A-5 / A-7）に反映する |

## No.19 非アクティブアカウント（12ヶ月）の扱い【優先度：中】

**現状**
保護方針5章に「非アクティブユーザー情報：最終ログインから12ヶ月」、付録に「非アクティブユーザー＝最近12ヶ月以上ログインしていないユーザー」と定義されている。**12ヶ月経過時に何が起きるのかが未定義**（削除されるのか、アカウントが無効化されるのか）。要求機能側には対応する記述が一切ない。

**なぜ必要か**
方針に保持期間として明記されている以上、12ヶ月経過後は何らかの処理が必要です。処理がなければ方針違反の状態になります。また、認証の観点では「無効化されたアカウントでログインを試みたとき」の挙動を定義する必要があります。

**決まらないと後工程で何が起きるか**
- 該当バッチが実装されず（残タスク B-6 の運用スクリプトに含まれていない）、方針どおりに運用されない
- 12ヶ月ぶりにログインしたユーザーが原因不明のエラーになる

**選択肢**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 12ヶ月経過で**自動的に退会扱い（匿名化）**とする | 方針どおり。ただし予告なく消えるとユーザー影響が大きい |
| B | 12ヶ月経過でアカウントを**無効化**し、さらに一定期間後に匿名化 | 段階的で安全 |
| C | 事前通知（例：11ヶ月時点でメール通知）→ 12ヶ月経過で削除 | 最も丁寧。ただし要求機能「記載されていない通知機能は実装しない」に抵触するため、通知を追加するなら要件変更が必要 |

**推奨案**：**A または B**。通知を伴わない前提で、保護方針の記述（既に公開文書として12ヶ月と明記されている）を根拠とする。あわせて次を定める。
- 無効化/削除の判定日時と実行タイミング（削除バッチ B-6 に追加）
- 無効化アカウントでのログイン試行時のレスポンス（No.17 の列挙対策と整合させる）
- 拠点スタッフ・システム管理者アカウントは対象外とするか（長期間ログインしない拠点がある可能性）

## No.20 システム管理者アカウントの初期発行と保護【優先度：中】

**現状**
要求機能に「拠点の新規登録はアプリ管理者が行う」「拠点スタッフの登録は各拠点1アカウント」とあるが、**システム管理者アカウント自体をどう作るかが未定義**。

**なぜ必要か**
システム管理者は全ユーザー・全予約・全拠点のデータにアクセスできる最高権限であり、侵害された場合の被害が最大です。初期発行方法（マイグレーションでの投入、初回起動時のセットアップ画面、手動INSERT）を決めないと、実装者が初期パスワードをコードやマイグレーションSQLにハードコードするおそれがあります。

**決まらないと後工程で何が起きるか**
- 初期パスワードがリポジトリに残る（`.claude/agents/auth-security-engineer.md`「秘密情報をコード・ドキュメントにハードコードしない」に違反）
- 管理者が1人しかおらず、ロックアウト（No.3）や退職で誰もアクセスできなくなる

**決めるべき論点と推奨**

| 論点 | 推奨 |
|---|---|
| 初期発行方法 | 環境変数から初期管理者のメールアドレスを読み、初回起動時にランダムパスワードを生成してメール送信する（AUTH-05 と同じ流れ）。パスワードをコード・SQL・ドキュメントに書かない |
| 管理者アカウント数 | **2つ以上**を推奨（1つがロック・失効しても復旧できるように） |
| 管理者アカウントの追加・削除 | 既存のシステム管理者のみが可能。監査ログに必ず記録（No.9） |
| ロールの昇格 | メンバー→システム管理者の昇格経路を設けるか、管理者は専用アカウントのみとするか要決定 |
| 非常用復旧手順 | 全管理者がロックアウトされた場合のサーバー上での復旧手順を運用手順書に明記（No.3 の D と同一） |
| PRIV-02 との整合 | 保護方針4.3は「システム管理者も業務範囲内のみアクセス可能」としている。要求機能は「すべての情報を登録・編集・削除する」。**両者の整合を取ること**（例：アクセス自体は可能だが監査ログに記録し、業務目的外のアクセスを運用ルールで禁止する、と整理する） |

## No.21 セキュリティインシデント発生時の対応・通知手順【優先度：中】

**現状**
保護方針3章に「セキュリティインシデント調査」が利用目的として挙がり、要求機能にインシデント対応SLA（重大度1〜3）があるが、**個人情報漏えい時の対応手順・本人通知・監督官庁への報告が定義されていない**。

**なぜ必要か**
APPI 準拠（PRIV-09）を掲げる以上、個人情報の漏えい等が発生した場合には、個人情報保護委員会への報告と本人への通知が求められます。手順が定義されていなければ、発生時に期限内対応ができません。また要求機能のインシデントSLA（重大度1で「3日以内に初期対応」）は、漏えい報告に求められる速報の期限感と整合しない可能性があります。

**決まらないと後工程で何が起きるか**
- 漏えい発生時に判断基準・連絡先・記録様式がなく、対応が遅れる
- 「本サービスは従業者を有しません」（PRIV-10）ため、対応する体制自体が定義されていない

**決めるべき論点と推奨**

| 論点 | 推奨 |
|---|---|
| インシデントの定義と重大度判定基準 | 個人情報の漏えい・滅失・毀損、不正アクセス、認証情報の漏えい等を定義し、要求機能の重大度1〜3にマッピングする |
| 検知手段 | 監査ログの異常検知（ログイン失敗多発、深夜の管理者操作等）を Zabbix のアラート項目に追加する（技術スタック4.3） |
| 個人情報保護委員会への報告 | 報告の要否判断基準と担当者を定める |
| 本人通知 | 通知の要否判断基準と通知手段（メール）。「記載されていない通知機能は実装しない」との関係を整理し、**法令に基づく通知は例外**として明記する |
| 対応体制 | 従業者がいない前提のため、責任者（システム管理者）と連絡経路を明記する |
| 記録 | インシデント記録の様式と保管期間 |

## No.22 ログ保持期間の記述矛盾の解消【優先度：中】

**現状**

| 出典 | 対象 | 保持期間 |
|---|---|---|
| 要求機能（データベース要件） | 監査ログ（ユーザーの操作・データ変更） | **180日** |
| 保護方針 5章 | アクセスログ | **90日** |
| 要求機能（データ保持・削除ポリシー） | ログファイル | 月〜日で記録し5世代（＝約35日） |
| 技術スタック 4.4 | 監査ログ | 180日 |

**なぜ必要か**
「監査ログ」「アクセスログ」「ログファイル」が同一物なのか別物なのかが定義されておらず、保持期間が 35日 / 90日 / 180日 と三様になっています。同一物であれば矛盾であり、別物であれば定義が必要です。公開文書である保護方針に「90日」と書いてある以上、実際の保持期間がそれを超える場合は方針違反にもなり得ます。

**決まらないと後工程で何が起きるか**
- ログ削除バッチ（B-6）の実装で、どの期間を採用すべきか判断できない
- インシデント調査（No.21）時に、必要なログが既に消えている
- 保護方針で約束した期間より長く保持し、方針との不整合が発生する

**推奨案**：ログを次の3種類に分類し、それぞれの保持期間を定義する。

| 種別 | 内容 | 保持期間（推奨） | 保存先 |
|---|---|---|---|
| 監査ログ | 認証イベント・データ変更・権限操作（No.9） | 180日（要求機能に従う） | DB（AuditLog テーブル） |
| アクセスログ | HTTPリクエストログ（IIS / アプリ） | 90日（保護方針に従う） | ファイル |
| アプリケーションログ | INFO以上の動作ログ | 5世代（約35日、要求機能に従う） | ファイル |

この分類を採る場合、**保護方針5章に「監査ログ180日」の行を追加**して整合を取る必要があります。

## No.23 個人情報の「暗号化保管」の適用範囲と鍵管理【優先度：中】

**現状**
要求機能「個人情報に関するデータは暗号化して保管する」、保護方針4.2「データベースは厳格なアクセス制御下に保管されます」とあるが、**どのデータを、どのレイヤで暗号化するのかが未定義**。

**なぜ必要か**
「暗号化保管」は次のいずれを指すかで実装も効果もまったく異なります。決めないまま実装すると、要件を満たしたつもりで満たしていない状態になります。

| レイヤ | 内容 | 効果 | 影響 |
|---|---|---|---|
| ディスク暗号化（BitLocker） | ボリューム全体を暗号化 | ディスク盗難・廃棄時に有効。稼働中のDB侵害には無効 | アプリへの影響なし |
| DB全体の透過的暗号化（TDE） | DBファイルを暗号化 | 同上 | PostgreSQL 標準では未提供（拡張・OS機能に依存） |
| カラム単位の暗号化 | メールアドレス等を暗号化して保存 | DB内容が漏れても復号鍵がなければ読めない | **検索・ソート・一意制約が使えなくなる**。メールアドレスをログイン識別子に使う本システムでは影響が大きい |
| ハッシュ化 | パスワードのみ（AUTH-09、確定済み） | 復元不可 | 確定済み |

**決まらないと後工程で何が起きるか**
- ER図・テーブル設計（A-4）でカラムの型・インデックスを決められない
- メールアドレスを暗号化すると、ログイン時の検索・一意制約・正規化（No.6）が成立しなくなる。実装途中でこれに気づくと設計変更になる
- 暗号鍵の置き場所が決まらず、`.env` に平文で置かれる

**推奨案**（※補完・要承認）

| 対象 | 方式 |
|---|---|
| パスワード | ハッシュ＋ソルト（確定済み） |
| メールアドレス | 平文保存（検索・一意制約のため）＋ ディスク暗号化＋DBアクセス制御で保護。加えてログ・APIレスポンスへの非出力（No.11 / SEC-08）で漏洩経路を塞ぐ |
| パスワードリセットトークン | ハッシュ化して保存（DBが漏れてもトークンを使えないようにする） |
| セッションID | ハッシュ化して保存 |
| その他の個人情報（自己紹介、画像パス等） | ディスク暗号化＋アクセス制御 |
| 保管全体 | **BitLocker 等のボリューム暗号化を必須**とし、これをもって「暗号化保管」の要件充足とする |
| バックアップ | pg_dump 出力とオブジェクトストレージ上の退避データも暗号化する（技術スタック4.2 の退避処理に追加） |
| 鍵管理 | 鍵・秘密情報は `.env`（NTFS ACL で保護、技術スタック3章）とし、リポジトリに含めない。鍵のローテーション手順を運用手順書に定める |

**この方針を採る場合、「暗号化保管」の解釈をドキュメント上に明記すること**。「カラム単位で暗号化していない＝要件違反」という指摘を後工程で受けないためです。

## No.24 認証・認可の受入基準（テスト観点）【優先度：低】

**現状**
要求機能に「初回リリース前にペネトレーションテストを実施」「SAST/DASTで継続監視」「コードカバレッジ80%以上」とあるが、**認証・認可要件が満たされたことをどう確認するかの受入基準がない**。

**なぜ必要か**
「3回失敗で30分ロック」「30分無操作でログアウト」「二重ログイン後勝ち」はいずれも**時間とセッション状態に依存する**要件で、通常の単体テストでは検証が漏れやすい領域です。受入基準がなければ、UAT で確認されないままリリースされます。

**決まらないと後工程で何が起きるか**
- テスト計画（A-9）に認証・認可のシナリオが含まれない
- 「実装したつもり」の要件が本番で機能していないことがリリース後に判明する

**推奨アクション**
テスト計画（A-9）に、少なくとも次の受入シナリオを含めることを要件化する。

| # | シナリオ | 期待結果 |
|---|---|---|
| 1 | 3回連続でパスワードを誤る | アカウントがロックされ、30分間は正しいパスワードでもログインできない |
| 2 | 30分経過後に正しいパスワードでログイン | ログインできる |
| 3 | 大文字小文字を変えたメールアドレスで失敗を重ねる | 同一アカウントとしてカウントされ、回避できない（No.3） |
| 4 | 端末Aでログイン中に端末Bで同一アカウントにログイン | 端末Aが次のリクエストで失効し、ログイン画面に遷移する（No.4） |
| 5 | ログイン後30分間何も操作せずリクエストを送る | 失効している（No.5） |
| 6 | 拠点スタッフAが他拠点のコート・予約を操作しようとする（URLのID差し替え） | 拒否される（IDOR） |
| 7 | メンバーが他人の予約を編集・削除しようとする | 拒否される。システム管理者は成功する（AUTHZ-R-01） |
| 8 | パスワードリセットトークンを2回使う／有効期限後に使う | いずれも拒否される（No.2） |
| 9 | 未登録メールアドレスでリセットを要求する | 登録済みの場合と区別できないレスポンスが返る（No.17） |
| 10 | ログアウト後にブラウザバックする | 認証必須ページが表示されない（No.7） |
| 11 | ログ出力・APIレスポンスにパスワード/トークン/他人のメールアドレスが含まれないこと | 含まれない（No.11 / SEC-08） |
