## 2. ビジネスロジック・制約条件の詳細

### 2.1 予約に関するルール
- [ ] **キャンセル可能期限**
  - 例：予約日の何日前まで可能か？
  - キャンセル料金発生時期は？（実装しない項目だが、ルール定義は必要）

- [ ] **参加者追加・削除のタイミング**
  - 予約成立後いつまで可能か？
  - キャンセルポリシーとの関連

- [ ] **同一ユーザーの重複予約ルール**
  - 同日同時間帯に複数の予約に参加可能か？
  - チーム予約 + 個人予約の同時参加は可能か？

- [ ] **予約の最小/最大期間**
  - 最短何分の予約が可能か？（例：30分？）
  - 最長何時間連続予約が可能か？

- [ ] **定員に達した場合の処理**
  - 自動的に予約不可にするのか、それとも管理者通知か？
  - キャンセルが出た場合の自動通知機能

### 2.2 チーム・ユーザーに関するルール
- [ ] **チームメンバー脱退時の予約への影響**
  - 脱退ユーザーは自動削除されるか？手動削除か？
  - 脱退ユーザーが予約者の場合の処理

- [ ] **チームリーダー交代時の処理**
  - 旧リーダーの権限はどうなるか？
  - チーム情報（チーム名、画像等）の管理権限

- [ ] **リーグ戦チーム**
  - 複数チーム所属時、メインのリーグ戦チーム以外への変更ルール
  - リーグ戦チーム削除時の既存予約への影響

### 2.3 拠点・コートに関するルール
- [ ] **営業日設定の優先度**
  - CSVインポート vs 画面操作：どちらが優先か？
  - 過去の営業日変更は可能か？

- [ ] **コート利用不可設定の表示**
  - UIでどう表示するか？（グレーアウト？バッジ？）
  - ユーザーへの通知タイミング

- [ ] **営業時間変更時の既存予約への影響**
  - 営業時間外の予約が存在する場合、どう対応するか？

### 2.4 通知に関するルール
- [ ] **通知タイミング**
  - 予約作成時：即座に通知か？
  - 予約編集時：具体的な変更内容も含めるか？
  - メール + アプリ内通知の順序

- [ ] **通知受信者の確定方法**
  - 予約時点の参加者のみか、後から参加した人も含めるか？

- [ ] **facilities テーブル**

- [ ] **audit_logs テーブル**
  - id, user_id, action, entity_type, entity_id, changes, created_at 等

- [ ] **user_favorite_venues テーブル**
  - id, user_id, venue_id, created_at 等
  - 複合ユニーク制約：(user_id, venue_id)

## 6. ビジネスプロセス・ワークフロー

### 6.1 予約フロー
```
1. ユーザーが拠点・コート・日時を選択
2. 予約タイプ（個人/チーム/他）を選択
3. 定員・チーム枠・キャンセルポリシーを入力
4. 参加者を確認
5. 予約確定
6. 参加者へメール/アプリ通知
7. 予約実施日に自動的に履歴に移行
8. 予約日経過後、物理削除（スケジュール処理）
```

- [ ] 各ステップの詳細な条件分岐
- [ ] エラーケースの処理

### 6.2 チーム登録申請フロー
```
1. メンバーがチーム登録を申請
2. チームリーダーに通知
3. チームリーダーが承認/却下
4. メンバーに結果通知
5. 同時にシステム管理者に通知
（管理者が最終承認？）
```

- [ ] 承認フローの最終責任者
- [ ] 却下時の理由表示

### 6.3 リーグ戦チーム登録申請フロー
```
1. メンバーがリーグ戦チーム登録を申請
2. システム管理者が承認/却下
3. メンバーに結果通知
```

- [ ] 承認基準の詳細

## 優先度による実装順序

### Phase 1: 最小限の実装
1. ユーザー認証（登録・ログイン）
2. 拠点・コート管理
3. 個人予約・参加管理
4. 基本的な通知機能

### Phase 2: チーム機能
1. チーム作成・管理
2. チーム予約
3. チームメンバー管理

### Phase 3: 拠点スタッフ向け
1. 営業日管理
2. CSV インポート
3. イベント予約・店舗予約

### Phase 4: その他
1. リーグ戦チーム
2. 高度な検索・フィルター
3. 分析・レポート機能（現状実装しない）
